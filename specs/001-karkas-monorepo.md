# 001. Каркас монорепо: запускаемый скелет

> **Статус:** черновик (решения по открытым вопросам приняты 15.08.2026) · **Фаза:** 0 (02-tech §23) · **Тип:** chore-каркас
> **Опирается на:** 04-conventions §1 (стек), §2.1 (раскладка), §2.3 (переезд документации) · 02-tech §2.3 (слои), §15 (окружение), §20 (тесты и CI)

Первые три шага фазы 0: репозиторий, поднимающееся окружение, база с одной таблицей, фронт, который видит бэк. Дальше каждая фича идёт своей спекой.

---

## 1. Границы

**Входит:**

- скелет монорепо: корневые пины версий, `backend/`, `frontend/apps/app`, `deploy/`, `docs/`;
- dev-окружение в compose: PostgreSQL 16, MinIO, Mailpit;
- FastAPI-приложение с `/api/v1/health`, конфигурация из env;
- Alembic с первой миграцией и таблицей `kernel.users` (только структура, без логики);
- SPA-заготовка на Vite + React + Mantine с темой из `ui-kit/theme.ts`, показывающая ответ `/health`;
- CI: линтеры, типы, тесты, проверка границ слоёв;
- переезд документации в `docs/`.

**Не входит** (каждое — своей спекой):

- вход, сессии, пароли, OTP — спека 002;
- права, роли, `/config`, меню — спека 003;
- манифесты модулей и реестры расширения — спека 004;
- шина событий, outbox, worker — спека 005;
- любые доменные сущности: курсы, группы, записи;
- прод-развёртывание и провижининг (02-tech §16–17) — отдельная спека фазы 2.

**Контекст:** WP-плагин заморожен — в нём остаются только исправления багов (актуальный код: `FS-LMS/wordpress/wp-content/plugins/fs-lms`, референс поведения 1.0). Риск «поддержка старой платформы съедает новую» из 02-tech §23 закрыт.

**Почему каркас идёт отдельной спекой, а не «просто настройкой»:** решений здесь больше, чем кажется — раскладка слоёв, порядок миграций, состав CI, границы импортов. Они принимаются один раз и потом дороги в пересмотре.

## 2. Поведение: три шага, у каждого проверяемый результат

### Шаг 1 — «оно запускается»

Создаётся минимум файлов; ничего лишнего, чтобы в репозитории нечего было искать.

```
fs-lms/
├── .python-version              3.12
├── .nvmrc                       22
├── .gitignore  .editorconfig  README.md
├── deploy/compose.dev.yml       postgres:16, minio, mailpit
└── backend/
    ├── pyproject.toml           poetry, requires-python >=3.12,<3.13
    ├── .env.example             с комментарием у каждой переменной
    └── app/
        ├── main.py              FastAPI, роут /api/v1/health
        └── settings.py          Pydantic Settings из env
```

**Результат:** `docker compose -f deploy/compose.dev.yml up -d` поднимает три контейнера, `uvicorn app.main:app --reload` из `backend/` отвечает на `/api/v1/health` строкой со статусом и версией.

### Шаг 2 — база и первая таблица

Добавляются `alembic.ini`, `migrations/`, `app/db.py` (движок и сессия), `app/kernel/users/models.py`.

**Таблица `kernel.users`** — только структура, по 02-tech §5: `id uuid PK` (UUIDv7, генерирует приложение), `login text UNIQUE`, `email`, `phone`, `last_name`, `first_name`, `middle_name`, `password_hash text?`, `password_enc bytea?`, `status`, `created_at`, `updated_at`. Логики входа и хэширования в этом шаге нет — они в спеке 002.

**Результат:** `alembic upgrade head` создаёт схему `kernel` и таблицу; `alembic downgrade base` откатывает чисто. Тест поднимает БД, накатывает миграции, вставляет строку.

### Шаг 3 — фронт видит бэк

```
frontend/
├── package.json  pnpm-workspace.yaml  (в корне монорепо)
├── apps/app/
│   ├── src/main.tsx  src/App.tsx  src/lib/http.ts
│   ├── index.html  vite.config.ts  tsconfig.json
└── packages/ui/theme.ts          переезд из ui-kit/theme.ts
```

Одна страница: заголовок, статус подключения к API, версия с бэкенда. Тема Mantine и токены — из `ui-kit` (03-design §1.13), чтобы каркас с первого дня жил на принятых значениях, а не на дефолтах Mantine.

**Результат:** `pnpm dev` открывает страницу, на которой виден ответ `/api/v1/health`. Прокси Vite на бэкенд настроен, CORS в dev не нужен.

## 3. Модель данных

Одна таблица `kernel.users` (см. шаг 2). Схема `kernel` создаётся первой миграцией.

**Правила миграций** (02-tech §19) действуют с первой: одна цепочка на весь продукт, имя ревизии осмысленное, `downgrade` пишется всегда и проверяется в CI.

## 4. API-контракт

| Метод | Путь | Ответ | Права |
|---|---|---|---|
| GET | `/api/v1/health` | `{ status: "ok", version: str, db: "ok" \| "down" }` | без авторизации |

`version` — версия продукта из настроек (одна на весь парк, 02-tech §17). `db` — результат тестового запроса к БД: healthcheck, который не ходит в базу, бесполезен.

Префикс `/api/v1` и правило «весь функционал только через него» (02-tech §1.1.5, §9) закладываются сразу — переносить потом дороже.

## 7. CI/CD

### 7.1. CI (каждый PR и push в main) — GitHub-hosted раннеры

- **backend:** ruff (линт и формат), mypy, pytest;
- **frontend:** eslint, tsc, prettier-проверка;
- **границы слоёв:** import-linter (`kernel` не знает про `core` и `modules`, `core` не знает про `modules`) и eslint-boundaries на фронте;
- **миграции:** `upgrade head` + `downgrade base` на чистой базе.

Границы вводятся **сразу, пока нарушать нечего**: введённые позже, они требуют разбора уже написанного кода.

### 7.2. Сборка образов (только push в main, после зелёного CI)

Docker-образы `api`, `worker`, `frontend` (статика в nginx) собираются и публикуются в **GHCR** с тегами `latest` и `sha-<короткий>`. Ключевое следствие для деплоя: **в реестре не бывает образа, не прошедшего тесты** — job сборки зависит от job тестов.

### 7.3. CD на stage (Proxmox LXC, 11.11.11.24)

Деплой-workflow триггерится только `push` в `main`, исполняется на **self-hosted раннере** в отдельном LXC:

```
docker compose -f /opt/fs-lms/compose.stage.yml pull
docker compose -f /opt/fs-lms/compose.stage.yml run --rm api alembic upgrade head
docker compose -f /opt/fs-lms/compose.stage.yml up -d
curl -f http://11.11.11.24/api/v1/health   # деплой падает, если health не отвечает
```

**Правила безопасности публичного репозитория** (нарушать нельзя):

1. self-hosted раннер **никогда не используется в PR-workflow** — только в деплой-workflow по `main`. Форк-PR не может исполнить код на нашем железе: PR-джобы идут на GitHub-hosted;
2. в настройках репозитория включено «Require approval for all outside collaborators» для workflow;
3. раннер живёт в отдельном непривилегированном LXC и по сети достаёт только до stage-контейнера;
4. секреты stage (`.env`) лежат на контейнере, в репозитории — только `compose.stage.yml` и `.env.example`.

**Откат** — деплой предыдущего образа по тегу `sha-*` той же командой.

**Почта на stage** — Mailpit: письма наружу не уходят, всё видно в веб-интерфейсе `http://11.11.11.24:8025`. Релей — вопрос прода, к stage не относится.

Файл `compose.stage.yml` — тот же состав, что dev (postgres, minio, mailpit), но приложения из GHCR-образов, а не из локальной сборки.

**Пошаговая настройка контуров** — [runbooks/stage.md](../runbooks/stage.md): создание LXC, установка Docker, регистрация раннера, настройки репозитория, эталоны compose и workflow, эксплуатация и траблшутинг.

## 8. Тесты

Цена ошибки здесь низкая, поэтому тестов немного, но они есть с первого дня — иначе CI нечего запускать:

1. `/api/v1/health` отвечает 200 и содержит версию;
2. healthcheck отдаёт `db: "down"`, когда база недоступна (подмена зависимости);
3. миграции накатываются и откатываются на чистой базе;
4. вставка и чтение строки `kernel.users`;
5. import-linter проходит на пустых слоях (проверка самой конфигурации, а не кода).

## 9. Решения (15.08.2026)

1. **Репозиторий — публичный, на GitHub.** Локальный путь — `~/fs-lms`. Оговорка, принятая осознанно: вместе с `docs/` публичными становятся продуктовая стратегия и решения безопасности (включая осознанные отступления вроде обратимого хранения паролей обучающихся). Если это станет нежелательным — репозиторий переводится в приватный без изменения процесса.
2. **Документация переезжает сразу после шага 1** — правило «спека и код одним PR» работает с первой фичи. Состав переезда:

   | Из `DesDoc` | Куда |
   |---|---|
   | `01-product.md` … `04-conventions.md` | `docs/` |
   | `Mockups/` (без `Mockups.zip`) | `docs/mockups/` |
   | `specs/` | `docs/specs/` |
   | `ui-kit/ui-plan.md` | `docs/ui-plan.md` |
   | `ui-kit/variables.scss`, `ui-kit/theme.ts` | `frontend/packages/ui/src/` — это код, не документация |
   | `CLAUDE.md` | корень, с обновлённой картой путей и командами запуска |

   Не переезжают: `.obsidian`, `.idea`, `.DS_Store`, `Mockups.zip`. `DesDoc` замораживается с README-ссылкой на новый репозиторий (04-conventions §2.3).
3. **MinIO и Mailpit — в compose с первого шага**: поднять дешевле, чем вспоминать позже, зачем они были нужны.
4. **WP-плагин заморожен** (только багфиксы) — см. «Контекст».
5. **Stage-контур на Proxmox** — см. §7.3. Прод-развёртывание, релей, домены, 152-ФЗ — вне этой спеки, вернёмся к фазе 2.
