## Жёсткие ограничения (полный текст — 04-conventions §5.2)

1. **Git не трогать вообще**: не коммитить, не ветвиться, не мержить, не пушить. Только текстовые подсказки (сообщение коммита, описание PR).
2. **Нет спеки — нет кода**: feat-код только по принятой фиче-спеке; мелкие fix/chore — с полным описанием в PR.
3. **Только файлы задачи**: править лишь то, что названо задачей или входит в её границы по спеке. Читать шире можно (поиск бага), править — нет.
4. **Никаких попутных правок**: заметил опечатку или устаревший код рядом — сообщи текстом или предложи отдельной задачей, не чини молча в том же диффе.
5. Новые зависимости, архитектура, схема БД, контракт API — только предложением в обсуждение, никогда фактом в диффе.
6. Границы модулей (import-linter / eslint-boundaries) не обходятся ослаблением конфига.
7. Секреты и данные клиентов — не запрашивать, не логировать, не вставлять в код и тесты.
8. Противоречие между спекой и реальностью — остановись и подними вопрос, не выбирай трактовку сам.
9. **Роль сессии не расширяется** (04-conventions §5.7): у каждой роли свой вход и своя зона записи — кодер не правит чужие тесты, тестировщик не видит реализацию и пишет тесты по спеке, а не по коду; «зелёный любой ценой» (skip/xfail/ослабленный ассерт) запрещён.

## Правила работы с документами (04-conventions §5.6, §4.1)

- Цикл изменений: **обсуждение → краткое резюме в чате → вычитка человеком → запись в документ**. Статус «принято» — только после явного «ок».
- Расхождение между документами или документом и кодом — баг: чинится **сверху вниз** (сначала документ, потом код), можно одним PR.
- Терминология — только из глоссариев (01-product §11, 04-conventions §9); синонимы не изобретать. «Куратор» — зарезервированный термин надзорной роли (01-product §3.7), на витрине — «преподаватель набора».
- Каждое значение в вёрстке — из токенов (`ui-kit/variables.scss`); произвольных чисел и hex-цветов не существует (03-design §1.13).
