# FS-LMS 2.0 — Продуктовая часть

> **Статус:** в работе. Документ заполняется по мере принятия решений в обсуждении.
> **Связанные документы:** `02-tech.md` — техническая часть, `03-design.md` — дизайн/внешняя часть, `04-conventions.md` — соглашения по разработке.

---

## 1. Резюме продукта

FS-LMS 2.0 — веб-платформа для образовательных организаций и частных репетиторов: конструктор курсов, обучение по группам и расписанию, приём заявок и документов, учёт оплат, публичная продажа курсов.

Модель поставки — managed-хостинг по подписке, single-tenant: каждому клиенту выделяется отдельный инстанс с собственной базой данных и файловым хранилищем. Вендор разворачивает и обслуживает инстанс; клиент получает домен и доступ в админку, не занимаясь эксплуатацией. Код tenant-agnostic: различия между клиентами задаются только конфигурацией инстанса. Технологическая база — React + Python, модульный монолит; детали — в `02-tech.md`.

Продаётся подписка одного из четырёх **уровней** плюс **дополнительные модули** по желанию (раздел 2). Цена = уровень + шкала за количество пользователей + модули.

Целевая аудитория:

1. Офлайн-школы, кружки, частные и групповые репетиторы (уровень 1).
2. Авторы и продавцы онлайн-курсов (уровень 2).
3. Онлайн-школы с договорным обучением и штатом (уровень 3).
4. Гибридные школы: договорное обучение + публичные курсы (уровень 4) — сюда целится и наша собственная школа.

### 1.1. Контекст: почему новая платформа

Продукт-предшественник — плагин WordPress, накопивший принципиальные ограничения платформы, для которой LMS не является профильной задачей:

1. Контентная модель встроена в чужой каркас: курс реализован как пост, данные растянуты по meta-полям вместо нормальных связей «урок → шаг → прогресс»; выборки и отчёты требуют обходных путей.
2. Нативные инструменты WP (таксономии, медиатека, роли) спроектированы для блога — их приходится обходить или дублировать.
3. Ограниченный контроль: развёртывание тянет весь WP-стек, обновления ядра и сторонних плагинов — источник неконтролируемых поломок.
4. Конфликты стилей и скриптов WP с кодом плагина.

Это не точечные баги, а несовместимость платформы с задачей: устранение любого из ограничений по объёму сопоставимо с миграцией — поэтому новая платформа, а не доработка.

### 1.2. Цели и не-цели

Продуктовые цели:

1. Полноценная замена плагина для собственной школы — паритет по реально используемым сценариям (перечень — по инвентаризации, а не «всё, что было»).
2. Продукт для продажи по managed-подписке: клиент получает работающий адрес и админку, не занимаясь эксплуатацией.
3. Комплектация под клиента без правок кода — только конфигурацией инстанса. Возможна правка код в особых условиях по договорённости с клиентом.

Технические цели (детали — в `02-tech.md`): автоматический контроль границ модулей; выключенный модуль не существует нигде (ни в API, ни в UI); соответствие 152-ФЗ как обязательство продукта; API-first — мобильный клиент подключается без переработки бэкенда.

Не-цели (отказ намеренный): микросервисы; shared-database мультитенантность (один клиент = один инстанс); конструктор страниц со свободной вёрсткой; перенос старого PHP-кода.

## 2. Сегменты аудитории и тарифные уровни

### 2.1. Модель продажи

Продукт продаётся по подписке (месяц / год). Подписка состоит из двух частей:

1. **Уровень** — именованный набор базового функционала. Клиент покупает подписку определённого уровня и получает весь его функционал целиком.
2. **Дополнительные модули** — подключаются к уровню по желанию, за отдельную плату (см. 2.4).

Формула цены: **стоимость уровня + шкала за количество пользователей + сумма подключённых дополнительных модулей**. Расчёт и биллинг самой подписки — вендорский контур вне продукта, проектируется отдельно.

В шкале за пользователей считаются **активные ученики**: активная учётная запись, у которой есть хотя бы одна действующая или ожидающая оплаты запись на курс; завершившие и отчисленные (read-only доступ) не тарифицируются, сотрудники — тоже. Превышение порога шкалы не блокирует инстанс: регистрация и зачисление продолжаются, владелец и вендор получают уведомление, цена пересчитывается со следующего расчётного периода. Жёсткой остановки посреди учебного года не существует.

Минимальный продаваемый тариф — **уровень 1**. «Базовая LMS» (ядро + учебный минимум без кампуса) остаётся внутренней вехой разработки, но отдельно не продаётся.

Внутри продукта уровни реализуются как пресеты внутренних модулей: в коде существуют только модули и конфигурация инстанса. Уровень — сущность прайса, не кода.

**Принцип надстроек.** Уровни не порождают отдельных классов сущностей: сущность (группа, расписание, запись на курс, лицевой счёт) одна на всех уровнях и на старшем уровне обрастает функциональностью модулей, оставаясь собой. Пример: группа «ЕГЭшники-новички» в офлайн-школе и техническая «группа с ID» под капотом онлайн-курса — одна и та же сущность. При апгрейде уровня данные не мигрируют — у них появляются новые возможности. Уровень задаёт потолок функционала; модули внутри уровня можно не включать (пример: У4 без ЭДО, см. ниже).

### 2.2. Уровни

#### Уровень 1 — «Офлайн-школа / частный репетитор»

Для кого: очные школы, кружки, секции, индивидуальные и групповые репетиторы.

Состав:
- админка, конструктор курсов, плеер курса;
- **лендинг школы**: публичная страница-визитка с формой «оставить заявку» + информационная страница «Курсы» (карточки без самозаписи и оплаты, CTA — заявка). Заявки-лиды обрабатываются вручную;
- группы, зачисление учеников на курсы (вручную, администратором). **Группа может существовать без курса** — расписание, посещаемость и учёт оплат работают и без учебного контента в системе, курс добавляется, когда школа созреет;
- **кампус (упрощённый)**: расписание занятий, посещаемость, журнал. Кабинеты и замены — только с уровня 3;
- **задания с ручной проверкой** — модуль в составе уровня; проверяет преподаватель;
- **лицевой счёт и учёт оплат**: все три схемы — разовая (за курс целиком), «абонемент» (помесячно) и поурочная; отметки «оплачено / не оплачено»; платежи вне системы, без онлайн-эквайринга.

Роли: вендор, владелец, методист, преподаватель, ученик. Владелец может совмещать все внутренние роли; типичный случай — методист = преподаватель в одном лице.

#### Уровень 2 — «Онлайн-курсы»

Ориентиры: GetCourse, Stepik, Codege, Solvit.

Состав:
- админка, конструктор курсов, плеер;
- **витрина**: публичный каталог, карточки курсов, самозапись, онлайн-оплата через платёжного провайдера;
- **оплата — только разовая, за весь курс**;
- проверка заданий: по умолчанию **только автопроверка**. Задания с ручной проверкой — докупаемый модуль (см. 2.4): вместе с ним разблокируются роль преподавателя (на витрине — «преподаватель набора», см. 3.6) и роль проверяющего;
- без кампуса (расписания занятий) и без КТП;
- **намеренные ограничения уровня** (граница апгрейда на У4): нет кампуса, КТП и сводной успеваемости по организации — даже с докупленными модулями.

Роли: вендор, владелец, методист, маркетолог, технический и финансовый администраторы, ученик; с модулем ручной проверки — преподаватель (преподаватель набора) и проверяющий; при модуле «Школа» — представитель.

#### Уровень 3 — «Онлайн-школа»

Ориентиры: Умскул, 100балльный репетитор, 99баллов, Skillbox.

Состав:
- всё из уровня 1, кампус в полном объёме: расписание, кабинеты, замены — включая интеграцию с офлайном;
- докупаемый модуль **ЭДО**: оформление по договорам, зачисление и отчисление приказами, паспортные данные, документальные согласия;
- полноценный плеер курса для педагога (кокпит), проведение занятий;
- проверка работ: профильные преподаватели и приглашённые внештатные проверяющие;
- **оплата: все три схемы** (разовая, помесячная, поурочная). Онлайн-оплата начислений из кабинета через платёжного провайдера + ручное внесение платежей, поступивших вне системы. Пример: месяц в группе 10 000 ₽ + два индивидуальных занятия по 2 000 ₽ → долг 14 000 ₽ на одном лицевом счёте.

Роли: добавляются администратор учебной части, маркетолог, технический и финансовый администраторы; проверяющий — в составе уровня; представитель — при модуле «Школа»; аналитик — с модулем «Маркетинг».

Модуль "ЭДО": документы обучающегося (паспорт, инн и прочее по запросу клиента). Составление договора (для очной школы) либо его онлайн подписание.
Модуль "Школа": для обучения несовершеннолетних, добавляется родитель (представитель) со своим личным кабинетом.
Модули "ЭДО" и "Школа" вместе: для родителя добавляется дополнительная форма с данными об ученике и о родителе. Также составляются договора, подписываемые (очно или онлайн) родителем.
#### Уровень 4 — «Онлайн-школа + витрина»

Объединение уровней 2 и 3: договорное обучение и публичная продажа курсов одновременно. Наша собственная школа целится в этот уровень — он же целевая сборка переезда с WordPress.

**Вариант «У4 без ЭДО»** — крупная школа только с онлайн-курсами: записываются любые люди через витрину, документы не требуются, но есть полный педагогический контур — преподаватели, КТП, проверка заданий с подтверждением, сводная успеваемость. Технически это конфигурация У4 с выключенным модулем ЭДО. Именно ограничения У2 делают этот вариант коммерчески осмысленным.

### 2.3. Кампус и ЭДО — независимые модули

Очное обучение и документооборот — разные внутренние модули, не зависящие друг от друга:

- **Кампус**: преподаватель у группы, расписание занятий, кабинеты, замены, посещаемость, журнал.
- **ЭДО**: паспортные данные, документальные согласия, договоры, приказы. Представители — в модуле «Школа» (см. 2.4), лиды с лендинга — в ядре (см. 4.7).

Следствие: уровень 1 получает кампус без документооборота; поля группы «преподаватель», «кабинет», «расписание» принадлежат кампусу, а не ЭДО.

### 2.5. Платёжные провайдеры

Онлайн-оплата не привязана к конкретному сервису: платёжный слой — абстракция «платёжный провайдер» с подключаемыми интеграциями; первая реализация — ЮKassa. Лицевой счёт не различает, каким провайдером (или вручную) проведён платёж.

## 3. Модель ролей

### 3.1. Модель

Три уровня: **право → функциональная область → роль**.

- **Право** — атомарная разрешённая операция, регистрируется модулем при подключении. При отключении модуля его права исчезают из ролей автоматически.
- **Функциональная область** — связная группа прав вокруг одного вида работы: «Курсы: контент», «Библиотеки», «Планирование», «Проведение занятий», «Проверка», «Цены», «Расчёты», «Карточки курсов», «Лиды» и т. д. Полный перечень — матрица в 3.4: её строки и есть области.
- **Роль** — именованный набор областей, собираемый вендором. Примеры: методист = «Курсы: контент» + «Библиотеки» + «Планирование» + «Наблюдение за проведением»; финансовый администратор = «Цены» + «Расчёты» + «Финансовая отчётность».

Следствия:

- Роли фиксированные, поставляются вендором; редактор ролей на стороне клиента не предусмотрен. Но **новая роль — это сборка из существующих областей, а не разработка**: её добавление в поставку не требует изменений в правах и интерфейсах разделов (см. 3.7).
- **Кастомную роль собирает вендор по запросу клиента**, в своём интерфейсе. Школа не получает конструктор прав: собранный вслепую набор почти всегда дырявый — право оценивать без права видеть группы, право проверять без доступа к работам, — и разбирать такие 403 всё равно приходит вендор. Кастомная роль создаётся **копией ближайшего шаблона** с правкой галочек, а не с чистого листа, и наследует от него профильность (см. ниже).
- **Название роли настраивается под номенклатуру клиента**: «сисадмин» вместо «технический администратор», «куратор» вместо «методиста». Это только отображаемое имя — набор прав, поведение экранов и обновления от переименования не зависят.
- Состав доступных ролей определяется уровнем подписки и подключёнными модулями: роль, чьи функции целиком относятся к отсутствующему функционалу, в инстансе не существует.

**Экраны привязаны к правам, а не к названию роли.** Ни меню, ни главная не спрашивают «это методист?» — они спрашивают «есть ли право планировать / отмечать посещаемость / проверять работы». Поэтому переименованная или кастомная роль получает осмысленный интерфейс автоматически: главная собирается из блоков, каждый из которых требует своего права (03-design §3.1), а меню — из пунктов, каждый со своим правом и заранее заданной группой. Роль с непривычным набором прав не ломает раскладку: у неё просто другой состав, а порядок групп и названия разделов те же. Для экзотических сборок предусмотрен запасной блок «Ваши разделы» — список доступного вместо пустого экрана.

**Границы назначения.** Роль выдаётся не только с набором областей, но и с границей, в которой она действует. Лестница закреплений:

| Роль | Видит и ведёт |
|---|---|
| Преподаватель | учеников своих групп |
| Методист | закреплённых за ним преподавателей (одного или нескольких) — и, через них, их группы |
| Администратор учебной части | всех методистов и все группы организации |
| Владелец, вендор | всю организацию |

Проверяющий — особый случай: граница ещё уже, только сдачи назначенных ему групп.

**Закрепление преподавателей за методистом** — отдельная операция, выполняет владелец (там же, где назначаются роли); администратор учебной части может вмешаться. Один преподаватель закрепляется ровно за одним методистом, один методист ведёт нескольких преподавателей. Закрепление методистов за администраторами в v1 не вводится — администратор один на организацию.

**Совмещение методист + преподаватель**: человек автоматически курирует сам себя (собственные группы видны ему как методисту без отдельного закрепления) и может дополнительно вести других преподавателей. Это типовой случай малой школы: играющий тренер.

Надзор за проведением (журналы, просрочки, напоминания) — область **методиста**, а не администратора: администратор учебной части сфокусирован на приёме, зачислении и группах.

| Ученик | ✔ | ✔ | ✔ | ✔ |

| Преподаватель | ✔ | с модулем ручной проверки | ✔ | ✔ |
| Проверяющий | — | с модулем ручной проверки | ✔ | ✔ |
| Методист | ✔ | ✔ | ✔ | ✔ |
| Маркетолог | — | ✔ | ✔ | ✔ |
| Аналитик | — | с модулем «Маркетинг» | с модулем «Маркетинг» | с модулем «Маркетинг» |
| Редактор | с модулем SMM | с модулем SMM | с модулем SMM | с модулем SMM |
| Администратор учебной части | — | — | ✔ | ✔ |
| Технический администратор | — | ✔ | ✔ | ✔ |
| Финансовый администратор | — | ✔ | ✔ | ✔ |
| Владелец | ✔ | ✔ | ✔ | ✔ |
| Вендор | ✔ | ✔ | ✔ | ✔ |

Принятые решения:

- **Преподаватель** существует там, где есть проведение обучения: У1, У3, У4 — и на У2 при докупленном модуле ручной проверки. Роль собирается из модулей по принципу надстроек: без кампуса это преподаватель набора — своя группа, проверка сдач, успеваемость своей группы, уведомления; кампус добавляет занятия, посещаемость, журнал. «Методист сам проверяет свой курс» — обычное совмещение ролей методист + преподаватель, как на У1.
- **Проверяющий** приходит с модулем ручной проверки: на У2 — при докупке модуля, на У3/У4 — в составе уровня. На У1 роль не активируется — работы проверяет преподаватель. Требование «подтверждение результата проверяющего преподавателем» — настройка, существующая только при наличии преподавателей.
- **Представитель** приходит с модулем «Школа» на любом уровне (не с ЭДО): родитель несовершеннолетнего — наблюдение, уведомления, оплата там, где есть лицевой счёт.
- **Аналитик** — роль модуля «Маркетинг» (доступен с У2): без модуля маркетинговой аналитики в инстансе не существует, и смотреть аналитику некому и нечего. **Редактор** — роль модуля SMM: наёмные авторы статей получают доступ только к публичному контенту, не к маркетингу целиком.
- **Финансовый и технический администраторы** — с уровня 2 (онлайн-продажи, возвраты, настройка витрины). **Администратор учебной части** — с уровня 3 (приём, группы, расписание — там, где штат).
- **Маркетолог** — с уровня 2. На У3 (без витрины) ведёт лендинг и статьи.
- На **уровне 1** функции всех административных ролей выполняет владелец.

### 3.4. Ограничения ролей

**Профильные роли и лестница доступа.** За каждой областью закреплена профильная роль — та, для кого эта работа основная. Помимо неё, доступ на изменение имеют роли выше по лестнице:

профильный специалист → профильный администратор → владелец → вендор

Каждый следующий уровень включает возможности предыдущего в пределах своей области. Расширение идёт вверх по уровню, а не вширь по областям: администратор учебной части не получает доступа к финансам, финансовый — к учебной части. Владелец — первый уровень, объединяющий все области.

**Подъём областей по уровням подписки.** Если профильная роль на уровне недоступна, её область поднимается к ближайшей доступной роли выше по лестнице. На У1 все административные области у владельца; на У2 учебные области — у владельца, финансовые — у финансового администратора. Матрица областей едина для всех уровней — меняется только исполнитель.

**Дублирование намеренно.** Возможность вмешаться не означает, что работу выполняют двое: это защита от простоя, а не разделение обязанностей. Изменение, внесённое непрофильной ролью, журналируется с указанием автора и области.

**Преподаватель не работает с деньгами.** Отметки «оплачено / не оплачено», начисления, корректировки — финансовая область: финансовый администратор, на У1 — владелец. Задача преподавателя — вести уроки; финансовая часть ему недоступна ни на одном уровне.

**Планирование — область методиста.** Сетка занятий, привязка уроков к занятиям (КТП), индивидуальные занятия — всё планирование выполняет методист или роли выше по лестнице (администратор учебной части, владелец). Преподаватель не планирует нигде: его КТП — режим чтения, о новых и изменённых занятиях он получает уведомления; его работа — проводить уже поставленные занятия. Постановка занятия в поурочной группе порождает начисление — осознанное косвенное влияние планирования на деньги; сами операции лицевого счёта остаются финансовой областью.

**Закрепление преподавателей за методистом** описано в 3.1 (кто назначает и с какой кратностью). Здесь — что из него следует для интерфейса.

Правило видимости на экранах: **методист видит только группы закреплённых за ним преподавателей** — на экране «Группы», в КТП, в журналах и сводках; **администратор учебной части и роли выше видят все группы школы**; преподаватель — свои и те, где он замещает. Один и тот же экран показывает разный объём, отдельных «админских» экранов для этого не заводится.

Закрепление ограничивает **учебный процесс**, но не контент: группы закреплённых преподавателей, их КТП, журналы и сводки по их ученикам — да; курсы, банк задач и библиотека работ остаются общими, потому что курс не принадлежит преподавателю. Совмещение «методист = преподаватель» (частый случай малых школ) не ущемляется: свои группы методист видит всегда, независимо от закреплений.

Ограничение **включается настройкой организации** «Методист видит только закреплённых преподавателей». По умолчанию она выключена — в школе с одним методистом список закреплений был бы лишней работой. Там, где направлений несколько, её включают, и тогда методист без закреплений не видит ни одной группы: экран объясняет причину и называет, к кому обратиться, — это ошибка настройки, а не пустая школа. Изменение списка журналируется: доступ к группам появляется и исчезает вместе с закреплением, отдельных прав никто не выдаёт и не отзывает.

**Запуск набора.** Профильная роль — администратор учебной части; на У2, где его нет, — технический или финансовый администратор либо владелец. Цена в диалоге запуска предзаполнена базовой; изменить её при запуске может только финансовый администратор или роль выше — остальные запускают набор с предзаполненной ценой.

**Роли обучающихся назначает система.** Роль ученика возникает при зачислении или самостоятельной регистрации, представителя — при связывании с несовершеннолетним обучающимся. Вручную эти роли не выдаются и не отзываются; администратор управляет состоянием учётной записи, но не её ролью.

**Сотрудник заводится вручную и не удаляется.** Самостоятельной регистрации у сотрудников нет: владелец создаёт учётную запись, назначает роли и решает, выдать временный пароль сразу или позже. Удаления сотрудника не существует — он автор занятий, проверок, приказов и правок, и его исчезновение оставило бы историю без автора. Вместо этого **доступ отключается**: вход закрыт, роли сняты с работы, данные и авторство на месте; включается обратно тем же действием. Обезличивание по 152-ФЗ (4.7) — отдельная процедура, применимая после истечения сроков хранения.

**Совмещение ролей разрешено, права складываются.** Любой сотрудник может дополнительно быть учеником или представителем. Ключевые совмещения малых школ: владелец = все роли (У1); методист = преподаватель (автор сам ведёт и проверяет).

**Проверяющий и аналитик — внештатные роли, не совмещаются ни с какой другой**: обе построены на минимальном доступе, совмещение с внутренней ролью его обнуляет (права складываются). Проверяется системой при назначении.

**Модули.** Технический администратор настраивает параметры подключённых модулей; решение о подключении и отключении принимает владелец, поскольку оно изменяет условия подписки. Настройка «подтверждение результата проверяющего преподавателем» — параметр модуля ручной проверки, настраивает технический администратор.

**Уведомления.** Шаблоны писем настраивает технический администратор. Адресные уведомления и рассылки выполняет роль, к области которой относится повод: учебные — администратор учебной части, финансовые — финансовый администратор, вовлекающие и промо — маркетолог при модуле «Маркетинг» (4.10.1). Преподаватель адресных уведомлений не отправляет.

**Маркетолог изменяет содержимое в пределах заданной структуры.** Состав и порядок готовых блоков публичных страниц задаёт технический администратор; изменение дизайна, вёрстки и новые блоки — заявка вендору (допработа). Задачи публичного тренажёра относятся к содержанию обучения и находятся в ведении методиста.

**Владелец обязателен**: в инстансе всегда ровно один.

**Посетитель ролью не является** — это состояние неаутентифицированного пользователя: в матрице прав не участвует и назначению не подлежит.

| Публичные задачи-тренажёр (модуль SMM) | Методист | Адм. учебной части, владелец, вендор |

| Логи: просмотр, выгрузка | Владелец | Вендор |
| Импорт / экспорт учеников и контента | Адм. учебной части | Владелец, вендор |

### 3.5. Доступ вендора к данным клиента

1. Доступ к содержимому базы — только по обращению клиента либо при устранении инцидента. **Клиент узнаёт о доступе постфактум — из журнала**, а не уведомлением в момент действия: лента чужой работы в реальном времени порождает вопросы к каждой строке, но след при этом остаётся всегда. Записываются вход в приложение, обращения к данным (к ПД — с особой пометкой) и выгрузки; обслуживание инфраструктуры — обновления, миграции, бэкапы, перезапуски — идёт своим контуром и в клиентский журнал не попадает. Отключаемого режима «без записи» не существует: журнал вендорских действий — в равной мере алиби вендора, и именно поэтому он не имеет выключателя.
2. **Вендор работает в маскированном режиме — это состояние по умолчанию, а не настройка.** Экраны те же, что у сотрудников школы, но персональные данные подменяются при отдаче: вместо ФИО — **технический идентификатор записи**, вместо почты и телефона — прочерк; паспортные данные, документы ЭДО и содержимое лицевых счетов не отдаются вовсе, **финансовые разделы вендору недоступны**. Маскирование происходит при отдаче, а не в базе: данные клиента при этом не меняются.
   Идентификатор берётся настоящий, а не выдуманный псевдоним: при разборе всё равно смотрят и экран, и базу, и лишний слой сопоставления «Ученик #14 — это кто» только мешает. На экране он показан короткой формой (полный UUID в колонку с именем не помещается), полный копируется одним нажатием — им и ищут строку в базе.

3. **Что вендор видит полностью — структуру и контент**: экраны, статусы, даты, идентификаторы, курсы, уроки, банк задач, работы и **ответы учеников** (имя автора при этом остаётся псевдонимом). Без ответов не отладить проверку, критерии и отображение сдач, а без контента невозможна миграция. Контент — материал школы, не персональные данные; отношения по нему — предмет договора, а не режима доступа.
4. **Полный доступ к персональным данным открывает владелец** — кнопкой в разделе «Поддержка», на ограниченный срок (сутки), с указанием обращения. Вендор сам себе его не включает: разрешение, данное клиентом заранее, снимает разбирательство постфактум. По истечении срока режим возвращается к маскированному автоматически. Если владелец доступ не открыл, а баг воспроизводится только на живых данных — школа снимает экран и присылает его сама.
5. **Экспорт и импорт контента** (курсы, банк задач, работы) — отдельное право вендора с журналированием: этим переносят материалы между инстансами при миграции. **Учеников вендор не импортирует** — для этого есть самообслуживание администратора учебной части с шаблоном файла и построчной валидацией. Так миграция делится честно: контент переносит вендор, людей заводит школа.
6. Обращения к персональным данным журналируются наравне с действиями пользователей инстанса.
7. Плановые работы (обновления, бэкапы, мониторинг) выполняются без обращения к содержимому ПД.
8. Порядок доступа и распределение ролей оператора/обработчика ПД фиксируются в договоре с клиентом.

**Рабочее место вендора — не инстанс школы, а собственная консоль** над всеми инстансами: список школ, подписки и тарифы, обращения, инциденты, миграции, сборка кастомных ролей по запросу (3.1). Главной страницы внутри школы у вендора нет: он входит в конкретный раздел адресно по обращению, и этот вход журналируется. Полноценная главная сделала бы из вендора второго владельца — а он не участник учебного процесса и не должен получать сводки школы «на всякий случай».

### 3.6. Ручная проверка на У2 — принятое решение

Модуль «Задания с ручной проверкой» на У2 разблокирует роль **преподавателя** — ту же роль, что на остальных уровнях, в объёме включённых модулей (без кампуса: своя группа, проверка работ, успеваемость своей группы). Поле «преподаватель набора» в диалоге запуска — это обычное поле «преподаватель группы»; отдельного интерфейсного синонима («куратор») не вводится, чтобы термин не конфликтовал с надзорными ролями (3.7). Автор курса, проверяющий сам, — совмещение ролей методист + преподаватель. Наёмная проверка — внештатная роль проверяющего, без изменений: несовместимость сохраняется. Настройка «подтверждение результата проверяющего преподавателем» существует при наличии преподавателей — с модулем это касается и У2.

### 3.7. Разделение ролей в будущем

Модель «право → область → роль» (3.1) означает, что уточнение ролевой структуры под клиента — операция сборки, а не разработки: вендор комбинирует существующие области в новый пресет и добавляет его в поставку. Права, экраны и разграничение доступа при этом не меняются.

Заготовленный пример — разделение сегодняшнего методиста на две роли для крупной организации:

| Будущая роль | Из каких областей собирается |
|---|---|
| Автор курса | «Курсы: контент» + «Библиотеки: банк задач, работы и экзамены» |
| Куратор | «Планирование» + «Наблюдение за проведением» (с границей «закреплённые преподаватели») |

Термин «куратор» зарезервирован под эту надзорную роль и не используется как синоним преподавателя набора.

В v1 разделение не реализуется: методист совмещает обе области. Признак, по которому к нему стоит вернуться, — организация, где авторы программ и руководители преподавателей физически разные люди.

## 4. Модель учебного процесса

### 4.1. Сущности и порядок работы

Иерархия содержимого: **предмет → курс → раздел → урок → шаг**.

| Сущность | Суть |
|---|---|
| Предмет | Верхний уровень группировки содержимого и учебных коллективов (информатика, математика) |
| Учебный период | Именованный отрезок времени с датами начала и окончания (год, семестр); границы групп, каникулы, область отчётности. Курс, продаваемый непрерывно, к периоду не привязывается |
| Группа | Учебный коллектив в границах периода: название, предмет, состав, фактическая цена, признак самозаписи, расписание. Связана максимум с одним курсом того же предмета; может существовать и без курса |
| Занятие | Слот календаря кампуса: дата, время, кабинет, преподаватель. **Строго один урок на занятие** — единица контента равна единице проведения (см. 4.4) |
| Запись на курс | Связь ученика с курсом — **единственный источник ответа о наличии доступа**. Статусы: ожидает оплаты / активна / курс пройден / доступ прекращён / отменена (заказ с витрины не оплачен в срок либо зачисление отменено администратором как ошибочное). Порождается назначением курса группе, самозаписью либо приёмом через ЭДО |
| Прогресс | Состояние прохождения шагов в рамках записи. Привязан к записи, а не к ученику: повторное прохождение не смешивается с прошлой историей |
| Лента учебных событий | Сквозная запись действий обучения (просмотрел, решил, сдал, получил оценку) в едином формате; фундамент журнала, аналитики и отчётов |

Порядок работы: создаётся предмет → учебный период → группа (уже на этом шаге работают расписание, посещаемость и учёт оплат) → зачисляются ученики либо открывается самозапись → группе назначается курс (в КТП группы, методистом или выше), в этот момент у всех участников создаются записи на курс. Ученик, добавленный позже, получает запись в момент добавления.

### 4.2. Группа — одна сущность на всех уровнях

Классов групп «для офлайна» и «для онлайна» не существует. Перетекание по уровням:

| Слой | Что даёт группе |
|---|---|
| Ядро (везде) | ID, состав, курс, фактическая цена, признак самозаписи, расписание, схема оплаты |
| Витрина (У2/У4) | та же группа как «набор»: создаётся кнопкой запуска набора, закрепляется преподаватель набора |
| Кампус (У1, У3, У4) | группа как учебный коллектив: преподаватель, кабинет, замены, посещаемость, журнал |
| ЭДО (У3, У4) | договоры, приказы о зачислении/отчислении поверх той же группы |

К группе привязаны цена обучения и расписание открытия курса — это ядро, работает одинаково на всех уровнях. Индивидуальные занятия — не отдельная сущность, а занятия индивидуальной группы: у каждого ученика своя группа (состав — один человек, обычно поурочная схема, возможно без курса). Экран «Индивидуальные занятия» — агрегированный календарь всех индивидуальных групп; «Добавить занятие» доступно методисту и выше с выбором ученика. **Индивидуальные занятия — включаемая возможность кампуса** (фича конфигурации инстанса, включает и выключает вендор): школам, работающим только группами, они не нужны — при выключении раздел исчезает из меню и создать индивидуальную группу нельзя. Преподаватель занятия не планирует: **все свои занятия — групповые и индивидуальные — он видит в одном разделе «Расписание»** (только просмотр) и получает уведомления о новых и изменённых.

Поля группы:

| Поле | Содержание |
|---|---|
| Название | «КЕГЭ-1», «Программисты-1» — соглашение об именовании, не идентичность |
| Предмет | принадлежность предмету (курс — только того же предмета, проверяется системой) |
| Учебный период | может быть не задан — вечные публичные и индивидуальные группы |
| Курс | назначается в КТП; до назначения группа живёт без курса |
| Преподаватель | при кампусе или модуле ручной проверки (преподаватель набора) |
| Кабинет | кампус, с уровня 3 |
| Регулярность | дни недели + время начала и окончания занятия (+ кабинет) — поле кампуса, задаётся при создании группы; из неё в КТП генерируется сетка занятий |
| Фактическая цена | копируется из базовой при создании/запуске и дальше живёт своей жизнью |
| Схема оплаты | разовая / помесячная («абонемент») / поурочная |
| Самозапись | разрешена (витрина) либо запрещена |
| Вместимость | опционально: при заполнении самозапись автоматически закрывается — «Мест нет» + предзапись в следующий набор; администратора при зачислении система только предупреждает |
| Статус | активная / архивная |

Поля, относящиеся к отсутствующим модулям, в комплектации не существуют. Собственных полей у курса немного: название, предмет, состояние содержимого — всё витринное живёт в карточке (8.1).

### 4.3. Признаки, определяющие доступ к курсу

Способ получения доступа не является «типом курса» и не задаётся одним переключателем — он складывается из независимых признаков:

| Признак | Где задан | Значения |
|---|---|---|
| Видимость | Карточка курса | Публикуется в каталоге либо нет |
| Способ зачисления | Группа | Самозапись разрешена либо только зачисление администратором |
| Стоимость | Группа (фактическая); базовая — у карточки | Бесплатно / платно |
| Расписание | Группа | Даты открытия заданы либо весь контент доступен сразу |

Новый коммерческий сценарий описывается сочетанием признаков, а не доработкой системы. Типовые сценарии:

| Сценарий | Каталог | Самозапись | Оплата | Расписание | Уровни |
|---|---|---|---|---|---|
| Бесплатный публичный курс | да | да | бесплатно | открыт сразу | У2, У4 |
| Платный публичный курс | да | да | разовая при записи | сразу или по датам | У2, У4 |
| Обучение по договору | карточка информационная (опц.) | нет | лицевой счёт: помесячно/разово/поурочно | занятия по КТП | У1, У3, У4 |
| Индивидуальная выдача | нет | нет | бесплатно либо вручную | открыт сразу | все |

Индивидуальная выдача — постоянная группа вне периода, администратор добавляет учеников точечно: бонусные материалы, компенсация пропусков, внутренние курсы для сотрудников. Во всех сценариях доступ обеспечивает одна и та же запись на курс — различается только путь её создания.

### 4.4. Расписание группы: занятия и открытие уроков

- **Занятие** — единица календаря кампуса: дата, время, кабинет, преподаватель. **Строго одно занятие = один урок**: единица контента курса равна единице проведения в жизни (курс на 72 урока и 144 часа нельзя провести за 36 сдвоенных занятий). Занятие без урока — свободный слот; урок без занятия ученику не виден.
- **Сетка занятий генерируется** из регулярности группы (дни недели + время + кабинет) на учебный период **в момент создания группы**; смена регулярности перестраивает будущие занятия, прошедшие не трогает. Пропускаются каникулы и те праздники, которые школа отметила нерабочими: производственный календарь РФ подставляет список праздников, школа выбирает из него применимые (многие школы работают в праздники, кроме новогодних). Каникулы задаются в учебном периоде вручную. Дальше сетка правится точечно: перенос, отмена, добавление занятия вне регулярности (дата, время, кабинет, преподаватель, урок).
- Постановка занятия в кабинет на уже занятое время вызывает **предупреждение, но не блокировку** — кабинет может вмещать две группы.
- **Привязка «урок ↔ занятие» живёт в КТП группы, а не в конструкторе**: конструктор не знает ни дат, ни групп — один курс живёт у многих групп с разными расписаниями. КТП-экран группы: слева темы (уроки снимка курса), справа календарь занятий; кнопка «Распределить» расставляет уроки по свободным слотам по порядку, точечные правки — перетаскиванием. Назначение курса группе также выполняется здесь.
- На У2 (кампуса нет) тот же экран в упрощённом виде — «Расписание курса»: уроки × дата и время открытия, без слотов, кабинетов и термина «КТП».
- **Состояние урока в расписании — явное**: «открыт сразу» / «запланирован» (занятие или дата-время) / «не запланирован» (ученику не виден). Пустота не является значением — система всегда отличает «забыли запланировать» от «осознанно открыт сразу». Демо-фрагмент — уроки в состоянии «открыт сразу», в любом месте курса.
- **Урок открывается в момент начала**: своего занятия (кампус) либо назначенных даты и времени (У2). Перенос занятия или даты вперёд не закрывает урок тем, кто уже получил доступ.
- При поурочной схеме оплаты занятие, поставленное в расписание, порождает начисление (см. 6.2).
- **Планирование — методист или выше** (см. 3.4). Преподаватель видит КТП в режиме чтения и получает уведомления о новых и изменённых занятиях.
- **Утверждение — кнопка «Опубликовать» в КТП**, жмёт методист или выше. Явное действие со сводкой: «14 запланировано, 2 открыты сразу, 1 не запланирован — останется закрыт. Подтвердить?». Вариант «доступно сразу» при запуске набора = автоутверждение. На кампус-уровнях утверждение требует отсутствия незапланированных уроков (для очной группы это ошибка планирования); на У2 достаточно сводки. Утверждённое расписание — условие публикации карточки в каталог (раздел 8).
- **Дедлайн сдачи** — опциональный атрибут работы/задания в расписании группы («сдать до даты» или «до занятия N»). После дедлайна — по настройке дедлайна в расписании группы: либо приём сдач закрывается, либо сдачи принимаются с пометкой «просрочено». Штрафов к баллам нет. Дедлайн, привязанный к занятию, сдвигается вместе с его переносом; ученик и представитель видят дедлайны в плеере, календаре и на главной.
- **Рабочее время организации** — настройка технического администратора («с 08:00 до 20:00»): задаёт границы календарной сетки в расписании, КТП и индивидуальных занятиях — день не показывается круглосуточно. В дальнейшем к рабочему времени привязывается окно отправки уведомлений (не беспокоить ночью).
- **Часовые пояса**: время занятий, открытий уроков и дедлайнов задаётся в поясе организации и показывается каждому пользователю в его локальном поясе — занятие в 16:00 по Калининграду московский ученик видит как 17:00. Таймер экзамена — длительность, от пояса не зависит.

### 4.5. КТП — отчётная проекция расписания

КТП (календарно-тематический план: темы × даты занятий) — документ для отчётности, формируемый из расписания группы и тем уроков; календарное представление живёт в кабинете преподавателя/администратора. Отдельной сущностью планирования КТП не является. Появляется на У3/У4; на У2 термин «КТП» в интерфейсе не используется — там есть только расписание открытия.

### 4.6. Посещаемость и прохождение урока

Две близкие по механике, но разные по природе отметки об уроке:

- **прохождение** — автоматический факт, вычисляемый из прогресса шагов (ядро, все уровни);
- **посещаемость** («+» / «Н») — ручная отметка преподавателя о присутствии на занятии (кампус).

Журнал объединяет обе: проекция ленты учебных событий + посещаемость.

### 4.7. Появление ученика и зачисление

**Регистрация — единственный путь появления ученика.** Администратор учеников не создаёт (исключение — импорт при миграции); учётные записи сотрудников заводит владелец при назначении ролей. Публичная форма регистрации существует на всех уровнях: базовая анкета — ФИО, дата рождения, почта, телефон, логин, пароль; согласие на обработку ПД (галочка) и защита от ботов обязательны. Результат — **учётка-заглушка**: пустой кабинет без курсов.

**Требования к паролю — длина, а не состав.** Минимум 6 символов, верхняя граница техническая. Алфавит — **латиница, цифры и знаки; кириллица не принимается**: раскладка при вводе пароля не видна, и пользователь, набравший его кириллицей на одном устройстве, не войдёт с другого, где переключился на латиницу. Требований «обязательно цифра и заглавная» нет сознательно: они не добавляют стойкости, зато рождают `Parol1!` вместо длинной фразы.

**Анкета расширяется модулями.** «Школа» добавляет поля «школа» и «класс»; ЭДО добавляет документальную часть (паспортные данные, документы, согласия), которая **в публичную форму не входит** — регистрация остаётся лёгкой.

**У совершеннолетнего ученика форма одна.** Представителя у него нет, второго шага не будет — поэтому анкета, согласие и документы для договора (при ЭДО) собираются сразу, при подаче заявки. Развилка проходит **по дате рождения внутри одной формы**, а не по двум разным экранам: совершеннолетнему добавляется блок документов и галочка согласия, несовершеннолетнему — школа с классом и уведомление о том, что согласие подпишет представитель. Без модуля «Школа» представителей нет вовсе, и форма всегда одна.

**Тип документа ученика определяется возрастом**: до 14 лет — свидетельство о рождении, с 14 — паспорт (данные вписывает представитель в JOIN-форме). Тип подставляется автоматически, но остаётся переключаемым: паспорт получают не в день рождения, и какое-то время подросток живёт со свидетельством.

**Согласие на обработку данных несовершеннолетнего даёт представитель, а не сам ученик.** В форме заявки галочки согласия нет: акцепт от подростка юридически ничего не даёт. Заявка при этом обрабатывается на другом основании — по инициативе самого субъекта, для заключения договора; в форме об этом сказано строкой-уведомлением: данные уйдут в школу, а согласие подпишет представитель по ссылке. Представитель в JOIN-форме подписывает **одно согласие за себя и за ребёнка** — с номером редакции (раздел 7).

**Документальная часть заполняется по JOIN-ссылке.** Несовершеннолетний (ЭДО + «Школа»): после регистрации ученика анкета получает статус «ждёт родителя», в админке появляется JOIN-ссылка — её отправляют родителю; родитель по ссылке создаёт свою учётку представителя, связывается с учеником и вносит паспортные данные и согласия. **Ссылка живёт 24 часа**, после чего заявка помечается истёкшей: администратор генерирует новую ссылку по той же заявке — заново заводить заявку и просить ученика перерегистрироваться не нужно. Короткий срок здесь сознателен: ссылка даёт право связать чужого ребёнка с собой, и живущая неделями ссылка в родительском чате — готовая дыра. Действие «Назначить родителя» привязывает уже существующего представителя (второй ребёнок) без ссылки. Взрослый ученик при ЭДО дозаполняет документальную часть сам — на этапе оформления договора.

**Зачисление — универсальная операция**: связь «ученик → группа», создающая записи на курс. Расширения: на У2 связь создаёт покупка курса; без ЭДО администратор просто назначает связь («Иванов → группа „Программисты-1“»); с ЭДО та же операция открывает модалку приказа (номер, дата, основание), а зачислению предшествуют проверка анкеты и договор.

**Отклонение заявки не удаляет человека.** Заявку отклоняют с указанием причины (не подошёл возраст, нет мест, дубль, отказ заявителя, другое). Учётная запись при этом сохраняется: человек остаётся зарегистрированным без записей и может подать заявку снова — в том числе на другое направление. Причина видна только сотрудникам.

**Лид ≠ регистрация.** Форма «оставить заявку» на лендинге — обратная связь: имя, контакт, комментарий; учётная запись не создаётся. Лиды — отдельный пункт админки на всех уровнях (профильная роль — маркетолог). Поле «интересующее направление» в формах — справочное пожелание: связи с группами создаёт только зачисление.

**Одна учётка на все пути.** Зарегистрированный ученик может и покупать курсы с витрины, и зачисляться по договору (сценарий У4) — вторая учётная запись не создаётся, связывание по email.

**Вход через соцсети** (модуль) — только привязка к существующей учётке в профиле и последующий вход; регистрация всегда идёт через анкету.

**Доступ к учётной записи.** Вход по логину или почте; сброс пароля по почте; подтверждение почты при регистрации — кодом (OTP) из письма, на всех уровнях (для покупки с витрины — обязательно до оплаты). **Код обхода подтверждения** — один на школу, задаётся в настройках системы: когда ученик не может получить письмо (нет доступа к почте, чужой адрес, сбой доставки), администратор диктует код, и регистрация завершается. Журналируется не выдача кода, а факт: **какая заявка каким кодом подтверждена**; при смене кода прежний перестаёт действовать, но отметки в заявках и период его действия сохраняются — по ним видно, кто и когда заходил в обход почты. Далее: смена почты с подтверждением — тем же механизмом кода.

**Неудачные попытки входа — пауза, а не блокировка**: после пяти неудач вход приостанавливается на пять минут с явным указанием, когда можно повторить, и предложением восстановить пароль; при продолжении перебора пауза растёт. Учётная запись при этом не запирается: запертый человек всё равно звонит администратору, и тот всё равно вернёт доступ — а перебор пауза останавливает и так. Сообщение об ошибке одно на оба случая («неверный логин или пароль»): по разным текстам перебором выясняется, есть ли у человека аккаунт в этой школе.

**Срок сессии — скользящий.** У ученика и представителя вход живёт 30 дней с последнего захода. У сотрудника срок дольше и продлевается при каждом рабочем дне: тот, кто заходит регулярно, не встречает ни повторного ввода пароля, ни второго фактора. Абсолютный предел всё же есть — после долгого отсутствия нужен полный вход; сессия, которую нельзя завершить временем, перестаёт быть сессией. Выход из системы — явным действием в карточке пользователя, и он завершает **эту** сессию, а не все устройства (отдельный «выход везде» — при смене пароля).

**Второй фактор — у ролей с чувствительным доступом.** Обязателен тем, у кого есть хотя бы одно право из набора: финансы, приём и персональные данные, настройки инстанса, назначение ролей, надзор за преподавателями. На практике это методист и все административные роли; **преподаватель и проверяющий второй фактор не проходят** — у них нет ни денег, ни документов, ни чужих областей, а лишний барьер перед занятием стоит дороже. Правило привязано к правам, а не к названию роли: кастомная роль, собранная вендором, получает второй фактор автоматически, если ей выдали чувствительное право. Механизм — тот же код на почту (единый OTP), отдельного приложения-аутентификатора в v1 нет. **Контактная почта несовершеннолетнего может быть родительской** (помечается признаком): она служит для восстановления доступа и уведомлений, но не является логином ученика и не мешает представителю зарегистрироваться с той же почтой. Запасной путь восстановления — **временный пароль**.

**Приземление после входа — по основной деятельности.** Сотрудник попадает в «Управление», ученик и представитель — в «Обучение» (03-design §2.1). У совмещающего работу и учёбу основное — работа: он чаще заходит работать, а в своё обучение переключается осознанно.

**Смена временного пароля обязательна при первом входе сотрудника, старый пароль при этом не спрашивается**: временный вход уже подтвердил личность, а требовать повторно строку, которую человеку только что продиктовали, — лишний барьер на ровном месте. У ученика и представителя выданный пароль сразу постоянный, экрана смены нет — сменить его они могут в профиле, когда захотят.

**Пароль обучающегося можно показать и отправить — осознанное отступление от общей практики.** Пароли **учеников и представителей** хранятся в обратимо зашифрованном виде: преподаватель видит действующий пароль ученика в его карточке, и он же уходит в письме с данными для входа. Причина практическая: школьники теряют пароли постоянно, и путь «сбросить, придумать новый, запомнить новый» для них дороже, чем для взрослого — занятие уже идёт, а ребёнок не может войти.

Отступление названо отступлением, потому что у него есть цена, и её нужно понимать до, а не после:

- **журнал перестаёт быть безусловным доказательством авторства**: вход под чужим известным паролем технически неотличим от входа самого человека, поэтому спор «я эту работу не отправлял» или «оценку выставили, зайдя под мной» решается не в пользу школы. Для сдач с последствиями — экзамен с одной попыткой, итоговые баллы — это ограничение существенное;
- **утечка базы становится утечкой доступов**, а дети переиспользуют пароли: тот же пароль стоит у почты и игр. Поэтому ключ шифрования хранится вне базы и не попадает в её бэкапы (02-tech §8) — дамп без ключа паролей не раскрывает.

**Отступление ограничено пятью условиями** — они делают его свойством конкретной школы, а не продукта:

1. **Настройка организации «показывать пароли обучающихся», по умолчанию выключенная.** Включает владелец, осознанно, с предупреждением о последствиях. Пока она выключена, обратимая копия **не создаётся вовсе** — не «не показывается», а физически отсутствует; включение действует только на пароли, выданные после. Школа со взрослыми учениками живёт на чистой хэш-модели и ничего не теряет.
2. **Совершеннолетние — только хэш.** Ученик 18 лет и старше под правило не подпадает даже во включённой школе: показ недоступен, восстановление обычное. При достижении 18 лет обратимая копия затирается — тем же мягким переоформлением, что снимает представителя.
3. **Сменил пароль сам — копия стирается.** Школа видит только тот пароль, который сама выдала; собственный пароль человека недоступен никому.
4. **Показ — отдельное право**, каждый просмотр журналируется записью с пометкой ПД; частота ограничена, а массовый просмотр (десяток паролей подряд) уведомляет владельца: это признак выгрузки, а не забывчивости учеников.
5. **Пароли сотрудников — только хэш**, всегда: у них доступ к деньгам, документам и настройкам. В выгрузки и экспорт пароли не попадают ни в каком виде.

**Журнал входов с адресом и устройством** ведётся у каждого пользователя и доступен **владельцу** (и вендору при разборе инцидента). Обучающемуся и представителю он **не показывается**, уведомлений о входе с нового устройства нет: школе иногда нужно зайти в кабинет ученика, и сигнализировать об этом самому ученику школа не хочет. Отсюда прямое следствие, которое надо принять вместе с решением: **чужой вход не заметит никто, кроме того, кто специально откроет журнал** — а открывают его по факту разбирательства, то есть постфактум. Оговорка про адреса: в школе все выходят в сеть через один внешний адрес, поэтому «вход с адреса школы» сам по себе ничего не значит — работает связка «адрес + устройство + время», и она остаётся материалом для человека, а не автоматическим выводом.

**Выдать новый пароль** может преподаватель — из сводки по ученику; то же может любая роль выше (методист, администратор учебной части, владелец). Система генерирует пароль, показывает его и делает действующим **без принудительной смены при первом входе**: ребёнок пользуется им дальше. Каждая выдача журналируется: кто, кому и когда. Для **сотрудника** механизм другой — ему выдаётся временный пароль, который он обязан сменить при первом входе (его действующий пароль система не знает).

**Удаление аккаунта — право ядра (152-ФЗ), не функция ЭДО.** Запрос из настроек профиля → подтверждение → **обезличивание**: учётная запись становится «Удалённый пользователь #ID», анкета и контакты стираются, вход невозможен. Прогресс и платежи сохраняются обезличенными — финансовые данные школа обязана хранить, они же доказательная база при возвратах. **Журнал удалений** (ID → чей был аккаунт) хранится отдельно с ограниченным доступом и выгружается владельцем для сопоставления. Для обучающихся по договору удаление выполняется после истечения законных сроков хранения документов.

### 4.8. Прекращение обучения

- Образовательные отношения прекращаются **отчислением независимо от основания**: освоение программы — одно из оснований, а не альтернатива отчислению. Основание обязательно: выбор из списка либо «другое» с полем. **Список оснований ведёт школа** — формулировки попадают в приказы и должны совпадать с её локальными актами; вендор список не фиксирует. Основание обязательно и без ЭДО: оно нужно истории группы и разбору «почему ушёл», а не только приказу.
- **Отчисление закрывает запись в конкретной группе, а не учётную запись человека.** Ученик, ушедший с математики и оставшийся на гитаре, — один пользователь с двумя записями; профиль, кабинет и история сохраняются. Удаления профиля при отчислении не происходит (это отдельная операция по 152-ФЗ, см. 4.7).
- При отчислении незавершённого курса запись **замораживается**: прогресс останавливается, новые уроки не открываются, структурные изменения курса больше не доезжают (запись держит версию снимка на момент заморозки); правки живого содержимого шагов видны и замороженным записям — содержимое не версионируется (раздел 5).
- Отчисленный **сохраняет доступ к платформе**: пройденные и замороженные курсы доступны в режиме «только чтение» — без ограничения срока, если иное не потребовал клиент, и пока инстанс школы существует (см. 10.5). При повторном зачислении архив прошлых курсов остаётся у ученика.
- Ядро хранит только учебный статус записи; документальное оформление (приказ с основанием и датой) добавляет ЭДО (раздел 7). Прекращение доступа к публичному или индивидуально выданному курсу приказом не сопровождается.
- Сертификаты и дипломы по окончании обучения — часть модуля ЭДО (раздел 7).
- **Академической паузы не существует** (сознательный отказ): ученик либо продолжает оплачивать обучение, либо отчисляется — с возможностью восстановления. Индивидуальные ситуации школа решает скидкой или корректировкой (6.4).

### 4.9. Жизненный цикл группы и учебного периода

- **Группа живёт в одном периоде и между периодами не переиспользуется**: к ней привязаны состав, оценки, посещаемость, журнал и записи занятий. По окончании периода группа архивируется со всей историей; в новом периоде создаётся новая.
- **Клонирования группы не существует** (сознательный отказ). Новый набор — это новая группа, заведённая руками: курс, преподаватель, кабинет, цена и регулярность выбираются заново. Копирование выглядело экономией десяти полей, но переносило вместе с ними прошлогодние решения: цену, которую забыли поднять, преподавателя, который уже не ведёт, расписание, которое надо было сдвигать вручную и сверять с новыми каникулами. Проверка скопированного стоит дороже заполнения, а ошибка в ней обнаруживается на первом занятии. Заведение группы — операция редкая, несколько раз в год на направление; экономить на ней минуты незачем.
- **Закрытие периода** — одна операция над всеми его группами: прошедшие курс остаются в статусе «курс пройден», остальные активные записи переводятся в «доступ прекращён» с основанием «окончание учебного периода»; группы архивируются. Группы вне периода (вечные публичные, индивидуальная выдача) не затрагиваются.
- **Следующая ступень** (из группы 10 класса — в группу подготовки к ЕГЭ) — не перевод, а зачисление в новую группу нового периода по новому договору.
- **Перевод между группами одного курса** (смена формата, расписания, стоимости): доступ к контенту прошлой группы замораживается на момент перевода — ответы, статистика и записи занятий остаются читаемыми; открывается контент новой группы. Финансовый пересчёт — 6.6. Перевод между группами разных курсов переводом не является — это отчисление и новое зачисление.
- **Возврата записи «в заявки» не существует.** В плагине 1.0 перевод и правка данных делались через возврат в заявки, потому что носителем анкеты была заявка. Здесь носитель — сам пользователь: анкета, документы и история принадлежат ему и переживают любую смену группы. Поэтому перевод выполняется переводом, исправление данных — правкой анкеты, а ошибочное зачисление — отменой записи; повторно заполнять формы не приходится ни в одном из случаев.

### 4.10. Уведомления

Каналы v1: **колокольчик в кабинете** (всегда) и **почта** (управляется получателем в настройках профиля). Push заложен архитектурно — включится с мобильным приложением; SMS и мессенджеры (Telegram) — будущий модуль. Сервисные уведомления (доступы, зачисление, результаты проверки) неотключаемы; остальные пользователь может отключить. Шаблоны писем настраивает технический администратор; адресные уведомления — по областям (3.4), механика — 4.10.1.

Реестр уведомлений (базовый, пополняется при детализации):

| Получатель | События |

| Ученик | зачисление и доступы; новое занятие, перенос, отмена; дедлайн приближается / просрочен; результат проверки (зачтено / на доработку); старт потока по предзаписи; задолженность (только полный кабинет, см. 5.5); выдан сертификат |

| Финансовый администратор | сводка задолженностей; оформленные возвраты |

#### 4.10.1. Адресные уведомления

Помимо автоматических уведомлений реестра школа отправляет **адресные уведомления** — сообщения выбранным людям по конкретному поводу. Канал — **колокольчик и push**: почтой они не дублируются, почта остаётся за транзакционным потоком и событиями реестра (доставляемость общего релея не тратится на объявления).

**Два класса, различаются правовой природой, а не ролью отправителя:**

| | Служебные | Вовлекающие и промо |
|---|---|---|
| Кто отправляет | адм. учебной части (учебные поводы), финансовый администратор (финансовые), владелец | маркетолог и роли выше |
| Когда существуют | всегда, на всех уровнях | только при модуле «Маркетинг» |
| Повод | обучение и расчёты: отмена занятия, сбор документов, напоминание об оплате | вовлечение и продажи: акции, новые курсы, «давно не заходили» |
| Согласие | не требуется — часть образовательных отношений | рекламное согласие (9.2), отзыв в один клик |
| Отключение получателем | нет, сервисные | да — «Новости и предложения» в настройках профиля |
| Ограничение объёма | подтверждение при массовой отправке | плюс **частотный колпак**: не больше N промо в неделю на человека (настройка организации, по умолчанию 3) |

**Служебным каналом нельзя рекламировать.** Объявление о переносе занятия и предложение скидки — разные вещи: у второго есть рекламное согласие и отписка, и обходить их «служебным» уведомлением запрещено. Держится это не проверкой текста, а правами: промо-класс существует только у маркетолога и только с модулем.

**Получатели** набираются из рабочих экранов, где сотрудник и так работает, а не в отдельном конструкторе сегментов: отдельные люди, вся группа, несколько групп, срез «ученики / представители / и те и другие», сотрудники. Маркетологу доступны сегменты базы модуля «Маркетинг» (9.2).

**Шаблоны — общий механизм обоих классов.** Библиотека заготовок с переменными (`{{имя}}`, `{{группа}}`, `{{курс}}`, `{{дата занятия}}`, `{{сумма долга}}`); в поставке — стартовый набор (отмена и перенос занятия, сбор документов, напоминание об оплате; с модулем «Маркетинг» — вовлекающие). Шаблон — отправная точка, а не обязанность: подставленный текст можно поправить перед отправкой или написать сообщение с нуля. Шаблоны ведёт тот, у кого есть право отправки, в своём классе: администратор не правит промо-шаблоны, маркетолог не видит служебных.

**Ночью не беспокоим**: уведомление появляется в колокольчике сразу, push доставляется в рабочем окне организации (4.4) — накопленное за ночь уходит утром.

**Каждая отправка журналируется со снимком получателей** — поимённым списком на момент отправки, а не критерием отбора: через полгода вопрос «кому это ушло» должен иметь точный ответ, даже если состав группы с тех пор изменился.

**Преподаватель адресных уведомлений не отправляет.** О сроках, результатах и изменениях расписания ученику сообщает система автоматически (реестр выше) — ручная кнопка «напомнить» лишь дублировала бы её.

**Автотриггеры — не в v1, но фича полезная и её стоит добавить.** Поведенческие правила («не заходил три дня», «серия прервалась», «курс не начат неделю после покупки») — доказавшая себя механика удержания. Модель уведомлений строится так, чтобы их появление не потребовало переделки: тип, шаблон и получатель у автотриггера те же, меняется только источник повода — планировщик вместо человека. Возвращаемся к ним при детализации модуля «Маркетинг» (9.2).

## 5. Создание и проведение курса

- Структура содержимого: **курс** (минимум один раздел) → **раздел** (логический контейнер, минимум один урок) → **урок** (единица расписания) → **шаг** (единица прогресса; тип + содержимое + признак обязательности). Обязательный шаг блокирует переход к последующим шагам урока, но не к другим урокам.
- **Урок вмещает до 20 шагов** — методическое ограничение: урок из тридцати шагов не проводится за занятие. Интерфейс остаётся читаемым при любом их числе (03-design §4.1).
- **Переиспользование уроков — копированием**: «Дублировать урок» внутри курса, «Скопировать в другой курс» (пачкой уроков или целым разделом). Копия независима — правки в неё не доезжают; задачи и работы внутри копии остаются ссылками на библиотеки, поэтому их правка по-прежнему видна везде. Общих уроков, живущих сразу в нескольких курсах, не существует.
- **Скопированное содержимое помечается**: у шагов копии стоит отметка «контент не обновлён», она снимается при первой правке содержимого либо вручную. Конструктор показывает счётчик необновлённых шагов, а перевод курса в состояние «составлен» выводит предупреждение с их перечнем (предупреждение, не запрет — иногда копия и должна остаться как есть).
- **Типы шагов — открытый реестр**, пополняемый модулями: базовые — лекция (текст), видео (ссылка на внешний сервис), задача, работа, экзамен; модульные — задание с ручной проверкой, интерактивное задание по программированию, трансляция, экзамен ЕГЭ. Нет модуля — нет типа шага в конструкторе. Шаги отключённого модуля скрываются с сохранением данных и прогресса; перед отключением владельцу показывается перечень затронутых курсов.
- **Состояния содержимого: черновик / составлен / архив.** «Составлен» — прошёл проверку целостности (есть уроки, в уроках шаги, содержимое шагов валидно), можно назначать группе. Публикация в каталоге — отдельный признак карточки (раздел 8). Метки вида «набор открыт» не хранятся, а вычисляются.
- Каждая группа обучается по **снимку структуры курса**, зафиксированному при назначении: правки структуры не трогают действующие и архивные группы. Содержимое шага не версионируется — исправление опечатки видно всем. Структурные изменения в курсе, назначенном активным группам, предупреждают методиста о числе затронутых групп. Довезти структурные правки до идущей группы можно **явным действием «Обновить снимок» в КТП группы**: методисту показывается сводка изменений, новые уроки появляются в состоянии «не запланирован»; автоматически правки до групп не доезжают.
- Содержимое не удаляется физически: урок или шаг скрывается, сохраняя историю и ответы тех, кто его проходил.
- **Задача в шаге — ссылка на банк задач, а не копия**: исправление условия в банке отражается везде, где задача используется. Это принципиальное отличие банка от содержимого курса.
- **Медиахранилище** общее для инстанса: файл, загруженный в один курс, переиспользуется в других. Загрузки (и методистов, и учеников) проходят проверку по типу и объёму. Видео — ссылками на внешние сервисы; загрузка видеофайлов и записи занятий — модуль S3.
- **Предпросмотр** — прохождение курса методистом от лица ученика без создания записи и прогресса.

### 5.1. Путь курса: от конструктора до учеников

**У1 и У3 (обучение своих):**

1. **Конструктор** (методист): разделы, уроки, шаги → курс помечается «составлен».
2. **Группа** (адм. учебной части, на У1 — владелец): название, предмет, период, преподаватель, кабинет, регулярность (дни недели + время начала и окончания) → **сетка занятий генерируется сразу при создании группы**; схема оплаты и цена.
3. **КТП группы** (методист): назначение курса → «Распределить» (уроки по порядку встают в свободные слоты) → точечные правки → «Опубликовать».
4. **Зачисление** учеников — создаются записи на курс. Уроки открываются с началом занятий; преподаватель проводит занятия, его КТП — режим чтения.

**У2 (продажа с витрины):**

1. **Конструктор** (методист) → «составлен». Конструктор один на всех уровнях.
2. **Карточка курса** (маркетолог, целиком — включая базовую цену). Метки вычисляются и руками не выставляются: «В разработке» → «Ожидает описания» → **«Ожидает набора»** (карточка заполнена, но чек-лист публикации не собран) → «Готова к публикации» → «Опубликована». Отдельное состояние «ожидает набора» нужно, чтобы метка «готова» не стояла у карточки, которую опубликовать нельзя.
3. **«Запустить набор»** (техадмин, финадмин или владелец): фактическая цена (предзаполнена базовой), преподаватель набора (при шагах ручной проверки), «доступно сразу / по датам» → создаётся группа-набор. Аналог шагов 2–3 пути У1, схлопнутый в одну операцию: курс назначать не нужно, карточка принадлежит курсу.
4. **«Расписание курса»** (методист): даты и время уроков → «Опубликовать». При «доступно сразу» — автоутверждение, шаг пропускается.
5. **Публикация карточки в каталог** (маркетолог) — отдельное явное действие с проверкой чек-листа (см. 8.2).
6. **Самозапись и оплата**: «ожидает оплаты» → «активна». Повторный набор — новый запуск с витрины: та же кнопка, новая группа.

Разница путей ровно в двух местах: кто рождает группу (администратор руками / кнопка запуска с витрины) и что стоит после планирования (ничего / чек-лист и каталог). Конструктор, состояние «составлен», экран планирования и правило открытия уроков — общие.

### 5.2. Базовые типы шагов и критерии прохождения

| Тип шага | Содержимое | Критерий прохождения |
|---|---|---|
| Лекция | Форматированный текст: изображения, таблицы, формулы, ссылки, блоки кода с подсветкой синтаксиса; **файлы-материалы — отдельным блоком под текстом** | Время на шаге ≥ порога. N = число слов / 150 слов в минуту; **порог = N/2, но не менее 10 секунд и не более 2 минут**. Считаются только слова (формулы, изображения и блоки кода время не увеличивают); учитывается только активная вкладка |
| Видео | Ссылка на внешний сервис + описание (загрузка файлов — модуль S3) | **Факт открытия шага** — сети и видеохостинги ненадёжны, строже требовать нельзя. Видео-шаг может быть обязательным (ограничение плагина снято) |
| Задача | Одна задача из банка; тип ввода ответа определяет интерфейс и способ проверки | Решена верно либо исчерпан лимит попыток |
| Работа (контрольная) | Набор задач с общим результатом внутри плеера; решение — в явном «режиме решения» по кнопке | Завершён режим решения (выход из режима = фиксация результата). Попыток может быть несколько; лимит времени опционален; **навигацию по курсу не ограничивает** |
| Экзамен | Набор задач на отдельной полноэкранной странице | Завершена сдача |

**Вставка кода (принято 27.08.2026)** — инструмент редактора, а не отдельный тип шага или содержимого. Кнопка «Вставить код» доступна в двух rich-text полях: шаг «Лекция» и условие задачи (банк задач, §5.4) — там, где методисту реально нужно показать код, а не просто написать о нём. По кнопке открывается модальное окно: поле для вставки многострочного кода и выбор языка программирования (по умолчанию — Python); язык определяет подсветку синтаксиса при отображении. Блок кода — часть содержимого поля, как изображение или таблица: отдельной сущностью не хранится, копируется и экспортируется вместе с текстом. В остальных rich-text полях продукта (карточки курсов, статьи блога, комментарии проверки) кнопки нет — там показывать код не было запроса, ничего не добавляем сверх задачи.

**Файлы-материалы лекции (принято 28.08.2026)** — методист прикрепляет к шагу «Лекция» файлы: PDF, презентации, документы, таблицы, текст, архивы, изображения. Это **отдельный блок под текстом лекции**, а не вставка внутрь него: конспект, презентация занятия и раздатка нужны целиком и на скачивание, а не посреди абзаца. Порядок файлов задаёт методист. Ограничения на типы и размер — общие для загрузок (02-tech §13); исполняемое не принимается (02-tech §15.2). Материалы **не влияют на прохождение** шага: критерий лекции остаётся временны́м, скачивание не отслеживается — иначе ученик, читающий с телефона, не смог бы закрыть урок. Прикрепление доступно только на шаге «Лекция»: у задач вложения живут в условии (§5.4), другим типам шагов файлы не нужны. При копировании урока список материалов копируется вместе с шагом.

**Название шага — тема, а не тип (принято 28.08.2026).** В поле названия шага методист пишет **тему**: «Позиционные системы счисления», а не слово «Лекция» — тип и так виден по иконке. Это название работает заголовком первого уровня на странице шага, поэтому в тексте лекции остаются только подзаголовки: дублировать тему внутри текста не нужно. Для шага «Задача» название подставляется из банка при выборе задачи, для «Работы» и «Экзамена» — имя работы из библиотеки; методист вправе переписать подставленное.

Правила прохождения: урок пройден, когда пройдены все его обязательные шаги; курс — когда пройдены все обязательные уроки. По умолчанию все шаги обязательные; обязательный шаг блокирует последующие шаги урока, но не другие уроки. Последовательное прохождение уроков не навязывается — доступность определяет расписание группы.

**Экзамен — отличия от работы:**

- отдельная полноэкранная страница, а не шаг внутри плеера;
- **одна попытка**; пересдача — только повторной выдачей от преподавателя;
- **обязательный жёсткий таймер** с момента индивидуального старта: истёк — автосдача. Назначенного «окна проведения» нет — начать можно в любой момент, пока шаг доступен (пробник ЕГЭ пишут в разное время);
- навигация по курсу заблокирована; завершение сдачи — только явной кнопкой «Завершить»;
- **сбой не завершает попытку**: ответы автосохраняются по мере ввода; при обрыве связи или отключении компьютера ученик возвращается и продолжает, пока не истёк таймер (время не останавливается — как на реальном экзамене);
- показ результата — сразу либо отложенно, после проверки (настройка);
- опциональный **лог переключений вкладки** — фиксация ухода с экрана для анализа честности;
- формального контура апелляции нет: изменение выставленного результата выполняет преподаватель или администратор, с журналированием.

Модуль ЕГЭ наследует экзамен и добавляет: оформление в стиле экзаменационных бланков, таблицу перевода первичных баллов, обязательный состав позиций экзамена.

**Баллы.** Работа и контрольная: один балл за задание — максимум равен числу заданий (ручная проверка: «зачтено» = балл). При нескольких попытках итоговым считается результат **последней завершённой попытки**; все попытки хранятся и видны преподавателю.

**Критерии оценивания (модуль ручной проверки).** У задания без автопроверки есть набор критериев: по умолчанию один («Выполнение», диапазон баллов задаёт методист). Методист может добавить любое число критериев, у каждого — название, пояснение для проверяющего и максимальный балл (например: «Ход решения» — 0–5, «Верные корни» — 0–3, «Проверка» — 0–2). При проверке выставляется балл по каждому критерию; **итоговый балл — их сумма**, максимум задания равен сумме максимумов. Критерии принадлежат заданию и переиспользуются вместе с ним; ученику после проверки видна разбивка по критериям с комментарием.

**Баллы в журнал не вводятся руками** — они приходят из самих работ: автопроверяемые считает система, работы с ручной проверкой оцениваются в интерфейсе проверки. В журнале преподаватель отмечает только посещаемость; исправить выставленный результат можно из карточки сдачи, действие журналируется.

**Режим проведения задаёт вендор, тип работы — школа.** Это две разные вещи, и путать их нельзя:

- **Режим** — закрытый список от вендора, он определяет движок: работа **в плеере курса** (все задания на одной странице, оценка за работу целиком — «4 из 6», попытки по настройке) либо **на отдельной странице с таймером** (одна попытка, жёсткий таймер, шкала оценивания, §5.2 «Экзамен»). Модули добавляют свои режимы — например ЕГЭ. Школа режимы не изобретает: за каждым стоит поведение, которое надо программировать.
- **Тип работы** — «тег» школы поверх режима. Он не меняет поведение, а даёт метку в журнале и разрез в отчётности: проверить все домашние, сравнить успеваемость по самостоятельным, посмотреть, как класс пишет контрольные. Работу с таймером школа вправе назвать как угодно — «Экзамен» подставляется по умолчанию, но ничто не мешает завести «Зачёт» или «Пробник».

Тип подсказывает режим (выбрали «Экзамен» — режим переключился сам), но не диктует его: контрольную можно провести и обычной работой в плеере, и на отдельной странице с таймером. В плагине это были две несвязанные сущности с двумя конструкторами — здесь один конструктор и два независимых поля.

**Тип работы** — выбор из справочника, который ведёт методист (пункт «Типы работ» рядом со шкалами оценивания). У типа: название («Домашняя работа»), короткая метка («ДЗ») и признак **«итоговая»**. Метка используется дважды: в шапке журнала и под иконкой шага в конструкторе и плеере — три работы подряд иначе неразличимы (03-design §4.1). Свободного текста нет — иначе в одной школе появятся «ДЗ», «дз» и «Д/З», по которым не построить отчётность. При развёртывании инстанса справочник заполняется стартовым набором (ДЗ, СР, ПР, КР, Экзамен), школа правит его под себя: «Зачёт», «Аудирование», «Лабораторная».

**Нумерация заданий работы (принято 28.08.2026).** По умолчанию задания нумеруются сквозным «Задание 3 из 6». Школе с собственной системой учёта этого мало: у методиста номер задания кодирует место в программе. Поэтому у работы есть **префикс нумерации** — свободная строка, которую методист задаёт один раз на всю работу; система приклеивает к ней порядковый номер задания через дефис. Префикс «1.3. П-2» превращает третье задание в «1.3. П-2-3». Префикс пуст — остаётся обычное «Задание 3». Номер с префиксом виден везде, где задание называют: у ученика в работе и на экзамене, у преподавателя в очереди проверки — иначе они обсуждают одно задание под разными именами.

По признаку «итоговая» журнал считает два агрегата успеваемости — «текущие» и «итоговые» — в виде «набрано / максимум» и процента (сырые баллы разных работ имеют разные максимумы, поэтому складываются именно так). Взвешенных рейтингов, итоговых оценок и сводных индексов успеваемости в v1 нет. **Экзамен оценивается по шкале** — настраиваемой карте «задание → баллы», где задания имеют разный вес; шкалы — переиспользуемые сущности, модуль ЕГЭ строит на них первичные/тестовые баллы и таблицу перевода. Журнал и сводки оперируют сырыми баллами, посещаемостью и двумя агрегатами (текущие / итоговые работы, см. выше).

**Шаг «Трансляция»** (модуль S3): до начала и во время занятия шаг содержит подключение к трансляции, после завершения на его месте появляется запись из хранилища. Кнопка «Подключиться» на главной ученика и в уведомлении о начале занятия ведёт прямо на этот шаг.

### 5.3. Проведение курса: кабинет преподавателя

Отдельного «кокпита занятия» нет — день преподавателя строится вокруг трёх экранов: Главная → Журнал → Сводка по ученику. Применимость по уровням: У3/У4 — полный кабинет; У1 — тот же без кабинетов и замен; У2 (преподаватель набора) — только сводка по ученику и проверка, без занятий и посещаемости.

- **Главная** — сводка дня: виджеты «Занятий сегодня», «На проверке (работ ждут оценки)», «Не заполнено (журналов посещаемости)»; расписание на сегодня/неделю; блок «Требует внимания» — задачи вида «заполнить посещаемость за прошедшее занятие»; список моих групп.
- **Проведение занятия**: материалы урока преподаватель открывает через «Мои курсы» (плеер в режиме педагога), посещаемость отмечает в Журнале. _Возможное развитие (не v1): кнопка «Вести занятие» — полноэкранный плеер-презентация + трансляция (требует модуля S3)._
- **Режим педагога в плеере**: преподаватель видит снимок курса своей группы — то же, что видят ученики. Эталонные ответы задач скрыты; поле ввода работает (можно проверить корректность ввода), рядом — кнопка «Показать ответ».
- **Журнал** — таблица «ученики × занятия месяца» по группе: посещаемость («присутствовал»/«Н») кликом по клетке; там же сырые баллы работ за занятие (СР/ПР/ДЗ/КР/ЭКЗ). Незаполненная посещаемость прошедшего занятия попадает в «Требует внимания» на главной.
- **Сводка по ученику** — группа → ученик → лента его занятий (групповые и индивидуальные): присутствие, урок, решённые задачи и попытки, работы. Там же — карточка ученика с контактами, представителем и **доступом в систему**: логин и кнопка «Выдать временный пароль» (4.7); финансовая часть преподавателю не показывается (3.4).
- **Проверка — единый интерфейс для всех проверяющих ролей** (преподаватель группы, преподаватель набора, внештатный проверяющий); раздел существует **при модуле ручной проверки** — без него все задания проверяются автоматически: счётчик «На проверке» на главной ведёт в общий список ожидающих сдач по всем группам; открытие сдачи — та же карточка проверки, что из сводки по ученику. Роли различаются объёмом доступа (проверяющий — только работы назначенных групп) и настройкой подтверждения преподавателем. Статусы сдачи: «на проверке» → **«зачтено»** (баллы + комментарий) либо **«на доработку»** (комментарий обязателен) → ученик отправляет новую сдачу; число итераций не ограничивается.
- **Отработка пропущенного — индивидуальное занятие** с прикреплённым уроком: методист выбирает урок, и система сама решает, что это значит (см. ниже) — тема занятия в любом случае попадает в КТП и журнал.
- **Статус занятия**: «проведено» проставляется автоматически по прошествии времени. Несостоявшееся занятие решается **переносом** (методист или выше выбирает новую дату, группа уведомляется; начисление поурочной группы сохраняется за перенесённым занятием). Полная отмена — крайний случай, аннулирует начисление (6.2).
- **Замена**: оформляет администратор учебной части; заменяется преподаватель или кабинет (кабинет — при включённой фиче кампуса «кабинеты», У3+), всегда на период и с причиной. Заменяющий преподаватель получает полный «гостевой» доступ к группе на период замены — материалы, посещаемость, журнал, проверка, как у заменяемого; действия журналируются от его имени, оба преподавателя уведомляются. Замена кабинета на доступы не влияет — меняется только место занятий.
- Экран «Активность» из плагина (лента событий группы) не переносится — признан бесполезным; события фиксируются в админском аудите и ленте учебных событий.

**Источник урока для индивидуального занятия — два, в одном поле выбора:**

1. **Курс этой индивидуальной группы** — обычно служебный **курс-копилка** («Материалы индивидуальных занятий»), непубликуемый курс, наполняемый тем же конструктором. Прикрепление такого урока **открывает к нему доступ** по общему правилу расписания.
2. **Курсы, где у ученика уже есть активная запись** (его основная группа) — с пометкой «доступ уже есть». Прикрепление такого урока **только отмечает тему занятия**: доступ ученик получил по расписанию своей группы, открывать нечего. Это закрывает отработку — в КТП и журнале видно, что разбирали, а не безымянное «индивидуальное занятие».

Методисту различие объяснять не нужно: он выбирает урок из сгруппированного списка, семантику определяет источник. К занятию обычной группы прикрепляются только уроки её курса. Свободная сборка уроков вне курсов из плагина не переносится.

### 5.4. Библиотеки контента и конструктор

Контент делится на два класса:

- **Библиотеки переиспользуемого** — создаются отдельно и попадают в шаги по ссылке: **банк задач** и **библиотека работ и экзаменов** (наборы задач из банка). Правка в библиотеке отражается во всех курсах и группах, где сущность используется.

**Задача живёт только в банке.** Локальной задачи «внутри одной работы» не существует: она не попала бы в статистику по позициям экзамена, не переиспользовалась бы в тренажёре, дублировалась бы при копировании курса, а правка в одном месте не отражалась бы в другом — через полгода школа имеет три версии одной задачи с разными опечатками. Но **создавать задачу можно не выходя из контекста**: конструктор задачи открывается дровером прямо из конструктора работы и из конструктора курса, по сохранению задача уходит в банк и тут же вставляется ссылкой. Экран редактора при этом один и тот же — в банке он открывается страницей.

Условие задачи — то же rich-text поле, что и лекция, включая кнопку «Вставить код» с подсветкой синтаксиса (§5.2) — задачи по программированию часто требуют показать код в условии, а не только принять его как ответ.

**Тип ответа по умолчанию — свойство предмета (принято 28.08.2026).** У предмета есть пресет: тип ввода ответа, который подставляется в форму новой задачи. В «Программировании» это задача с кодом, в «Английском» — короткий ответ; методист не выбирает одно и то же в сотый раз, а меняет пресет там, где нужно другое. Пресет только предзаполняет форму: он ничего не запрещает, на уже созданные задачи не влияет и в самом банке ничего не фильтрует. Форма создания задачи одна и та же, поэтому пресет работает и в банке, и в дровере из конструктора работы или курса — там предмет берётся из работы или курса. Если тип относится к отключённому модулю, пресет молча игнорируется.

Обратная сторона ссылочной модели — правка задачи, которая уже где-то используется. Поэтому в редакторе всегда видно, **где она стоит** (работы, шаги, тренажёр), а при сохранении есть выбор: изменить везде или **сохранить копией** и подменить ссылку только в текущем месте. Задачу из банка правит методист своего предмета; чужой предмет — только копией.

**Таксономия задач — три разные вещи, которые нельзя смешивать:**

| Что | Кто ведёт | Зачем |
|---|---|---|
| **Автор** | никто — системное поле | ставится при создании, не выбирается; в банке по нему есть фильтр |
| **Сложность** | вендор, закрытая шкала (простая / средняя / сложная) | по ней работают подбор задач и статистика; своя шкала у каждой школы сделала бы их несравнимыми |
| **Темы** | методист своего предмета | дерево по предмету (Алгебра → Уравнения → Системы уравнений): поиск в банке, подбор в работу, а с модулем публичных задач — навигация открытого каталога |
| **Позиция экзамена** | вендор, вместе с модулем ЕГЭ | разрез «статистика ученика по позициям экзамена» |

Тема **выбирается из справочника, а не вводится текстом** — по той же причине, что и тип работы: свободный ввод рождает «уравнения», «Уравнения» и «ур-я». Если нужной темы нет, методист добавляет её прямо из поля выбора, но система сначала показывает похожие («Есть «Системы уравнений» — может быть, это оно?»). У термина сразу заводится адрес (`/trainer/sistemy-uravneniy`): он не нужен, пока не подключён модуль публичных задач, но заложен заранее — иначе подключение модуля потребует переразметки всего банка.

**Импорт и экспорт банка** — обязательная пара: импорт из xlsx/csv по шаблону с построчной валидацией и отчётом об ошибках (дубли по условию пропускаются), экспорт выбранных задач или всей выборки по фильтру вместе с темами и номерами.
- **Структура курса** (разделы, уроки, шаги) — создаётся только в конструкторе. Отдельного создания уроков и библиотеки уроков нет: вне курса у урока нет ни снимка, ни состояния, ни места для прогресса; кейс индивидуальных материалов закрывает курс-копилка, кейс повторного использования — копирование (см. 5).

Меню «Обучение» в новой версии: **Курсы** (конструктор) · **Работы и экзамены** (библиотека) · **Банк задач** (библиотека) — вместо пяти пунктов плагина (пункт «Уроки» исчезает).

Правила:

- В конструкторе при добавлении шага «задача», «работа» или «экзамен» — выбор «из библиотеки» либо «создать новую». Созданное на месте **сохраняется в библиотеку**, шаг получает ссылку: один способ хранения, два удобных входа.
- **Работа, по которой есть сдачи, блокируется от изменения состава**: текстовые правки задач допустимы, добавление и удаление задач — только через копию работы. Это защита от рассинхронизации баллов уже сдавших.

### 5.5. Кабинеты ученика и представителя

Кабинет ученика существует в двух вариантах; критерий — **наличие связанного представителя**, а не возраст сам по себе:

- **Полный кабинет** (ученик без представителя — взрослый либо самозаписавшийся с витрины): **Главная** — ближайшие занятия с кнопкой «Подключиться», «продолжить обучение» (последний открытый шаг), дедлайны, задолженность, колокольчик; **Мои курсы** (плеер); **Календарь** — занятия групповые и индивидуальные + дедлайны; **Результаты** — баллы по работам и посещаемость (показывается обязательно — прозрачность дисциплинирует); **Лицевой счёт** — баланс, онлайн-оплата начислений, история платежей и чеки. Настройки (анкета, смена пароля, привязка соцсетей) — не в главном меню, а по шестерёнке у имени пользователя.
- **Кабинет несовершеннолетнего** (есть представитель): то же самое **без финансового блока** — лицевой счёт и всё связанное с оплатами ученику не показывается, это зона представителя.

**Кабинет представителя**: переключение между детьми (выпадающий список или стрелки); по выбранному ребёнку — успеваемость, посещаемость, расписание и дедлайны (только чтение), лицевой счёт с онлайн-оплатой начислений (единственная операция записи), история платежей и чеки, уведомления.

Правила:

- **Основной представитель у ученика ровно один** — урок плагина: несколько равноправных представителей (мать, отец, бабушка) порождали постоянные проблемы с назначениями и лишними аккаунтами. Он связывается с учеником по JOIN-ссылке, отвечает за документы, согласие и является заказчиком в договоре (при ЭДО). Один представитель может быть связан с несколькими детьми.
- **Со-плательщик (принято 20.08.2026)** — второй кабинет представителя у того же ученика, для случаев вроде раздельно живущих родителей, которые платят по очереди и оба хотят видеть успеваемость. Добавляется **администратором вручную**, без JOIN-ссылки (она — часть процесса основного). Доступ идентичен основному представителю (успеваемость, лицевой счёт, история, уведомления), кроме документальной части: не редактирует документы и согласие, не может быть источником JOIN-связывания, не подменяет основного как заказчика в договоре. Урок про «лишние аккаунты» не нарушается: роль одна прежняя (основной, с документами) плюс явно более узкая новая — путаницы с тем, кто отвечает за документы, не возникает.
- **Текущий плательщик** — из представителей ученика (основной и со-плательщики) в любой момент ровно один помечен текущим плательщиком (по умолчанию — основной). Ему приходят уведомления о начислениях и просрочке, у него на главной — бейдж задолженности; остальные представители лицевой счёт видят (баланс, история — прозрачность нужна всем), но без напоминаний и бейджа, чтобы не возникало случайной повторной оплаты одного и того же начисления двумя людьми. Переключить текущего плательщика (например, с одного родителя на другого) может администратор или финансовый администратор в любой момент — не только при добавлении со-плательщика.
- **Возрастные пороги — мягкое переоформление, без автоматики**: 14 лет — замена свидетельства о рождении на паспорт в документах; 18 лет — отказ от представителей, кабинет ученика становится полным (у всех связанных представителей, не только у основного). Система заранее уведомляет администратора и представителей; переоформление выполняет администратор (при ЭДО — с документами). Автоматического отключения доступа в день рождения нет.

## 6. Оплата и расчёты

Учёт денежных обязательств между образовательной организацией (не вендором) и учеником/заказчиком.

### 6.1. Лицевой счёт

- Учёт ведётся по **лицевому счёту** обучающегося — журналу операций. Виды операций: начисление, платёж, скидка/корректировка, возврат.
- **Банковская конвенция знака: баланс = оплачено − начислено.** Минус — задолженность, плюс — переплата. Пример: месяц в группе (10 000) + два индивидуальных занятия (2 × 2 000) → на счёте −14 000.
- **Начисление имеет основание**: курс целиком, месяц группы или отдельное занятие. Каждая операция ссылается на группу — отчётность отвечает «сколько поступило по набору», «кто должен», «выручка за период».
- **Предоплата — только у витринных покупок (У2/У4)**: статус «ожидает оплаты» существует только у записей, созданных покупкой с витрины; контент открывается после подтверждения платежа. Записи договорного и офлайн-обучения (У1/У3/У4) активны сразу после зачисления — оплата идёт по лицевому счёту позже, задолженность доступ не блокирует (блокировка — только ручная, администратором).
- **Задолженность не блокирует доступ автоматически**: отображается в кабинетах ученика и представителя, уходит уведомлением, попадает в сводку администратора. Заблокировать доступ может только администратор вручную. Пороги и тексты уведомлений настраиваются.
- Переплата по умолчанию засчитывается в счёт дальнейшего обучения; возврат деньгами — по заявлению заказчика.
- **Счёт один на ученика, а не на представителя.** При нескольких представителях (5.5) лицевой счёт по-прежнему единый и общий; «кому выставляем счёт» решает не разделение счетов, а текущий плательщик — кто получает уведомления и бейдж задолженности (5.5). При онлайн-оплате чек естественным образом содержит данные того представителя, который вошёл и заплатил, — отдельно переключать нечего. При ручном внесении офлайн-платежа (6.5) администратор указывает, чьи данные использовать как плательщика в операции.

### 6.2. Схемы оплаты

Схема — настройка группы:

- **Разовая** — одно начисление на полную стоимость при записи.
- **Помесячная («абонемент»)** — график начислений по месяцам учебного периода. Месяц с каникулами стоит столько же: помесячная цена не пересчитывается по числу занятий, индивидуальные случаи решаются скидкой (6.4).
- **Поурочная** — начисление за занятие. **Начисление создаётся, когда занятие поставлено в расписание группы**; отмена занятия аннулирует начисление. Пропуск занятия учеником начисление не отменяет (место держали); спорные случаи администратор решает корректировкой. Занятия в поурочных группах ставит методист или выше — как и всё планирование, преподаватель занятия не ставит (см. 3.4).

### 6.3. Схемы и приём денег по уровням

| Уровень | Схемы | Приём денег |
|---|---|---|
| У1 офлайн | все три (разовая, помесячная, поурочная) | вне системы: отметки «оплачено / не оплачено», эквайринга нет |
| У2 витрина | только разовая за весь курс | платёжный провайдер |
| У3 / У4 | все три | платёжный провайдер (оплата начислений из кабинета) + ручное внесение |

Отметка «оплачено / не оплачено» на У1 — упрощённый интерфейс той же модели: отметка = ручной платёж, закрывающий начисление; единица отметки (месяц или занятие) определяется схемой группы. Отметки ставит владелец (финансовая область; на У3/У4 — финансовый администратор): преподаватель с оплатами не работает ни на одном уровне. При апгрейде уровня история оплат сохраняется — вместо журнала отметок открывается полный лицевой счёт.

### 6.4. Оплата вперёд и скидки

- **Момент фиксации начислений**: при обычной помесячной схеме начисление месяца создаётся в начале месяца по актуальной цене группы. При оплате вперёд (полгода, год) начисления всех оплаченных месяцев создаются сразу, в момент платежа, по действующей ставке и скидке.
- Следствие: **изменение цены группы действует только на ещё не созданные начисления**. Оплатившего год вперёд смена цены не касается; платящий помесячно получает новую цену со следующего месяца.
- **Скидка — явная операция счёта**, а не «тихо уменьшенный платёж»: начисляется полная цена, скидка фиксируется отдельно. Видны и полная стоимость, и размер скидки. Ручная корректировка суммы месяца администратором — та же операция с указанием причины.
- Варианты оплаты с прогрессией скидки («полгода −X%», «год −Y%») — настройка договорного контура У3/У4; на карточке У2 их нет.
- **Разовая оплата вперёд как ручное исключение — на любом уровне, включая У1.** Помимо настроенных пакетов со скидкой (выше), администратор (на У1 — владелец) может в любой момент вручную создать начисления на N месяцев вперёд для конкретного ученика и сразу закрыть их платежом — даже если у группы обычная помесячная схема и никаких пакетов не настроено. Механика та же, что при обычной оплате вперёд: начисления фиксируются по действующей цене сразу за все месяцы, дальнейшая смена цены группы их не касается. Кейс: родитель хочет заплатить сразу за год, хотя школа обычно берёт помесячно.

### 6.5. Проведение платежа

- Онлайн-платёж — через платёжного провайдера: данные чека передаются сервису, для лицензированных образовательных услуг — ставка «без НДС». Доступ открывается только после подтверждения платежа; неподтверждённые заказы закрываются по истечении срока, а до закрытия ученику уходит письмо «завершите оплату» со ссылкой на возврат к платежу (догон брошенной оплаты).
- **Рассрочка** — способ оплаты платёжного провайдера («Заплатить по частям», Сплит и аналоги): школа получает сумму сразу за вычетом комиссии провайдера, для лицевого счёта это обычный разовый платёж. Включает и настраивает сам клиент в кабинете провайдера — условия и удержания у провайдеров различаются.
- Платёж вне системы (квитанция, терминал, наличные) вносится вручную с указанием основания — администратором, на У1 — отметкой владельца. При нескольких представителях ученика (5.5) операция дополнительно указывает, чей это платёж, — это же значение уходит в чек и не обязано совпадать с текущим плательщиком (5.5). Лицевой счёт не различает способ поступления средств.

### 6.6. Возвраты

- Правовая рамка: заказчик вправе отказаться от договора в любой момент, возместив организации **фактически понесённые расходы**. Фиксированные формулы удержания в договоре юридически уязвимы. Задача системы — не выносить решение, а обеспечивать расчёт и доказательную базу.
- Система предлагает расчёт, решение и основание фиксирует администратор. При оплате со скидкой показываются обе цифры: по ставке со скидкой и по полной ставке.
- Договорное помесячное обучение: по приказу об отчислении аннулируются начисления месяцев, следующих за месяцем приказа; баланс пересчитывается; возврат оформляется операцией после решения администратора.
- Публичные курсы: система накапливает **выгрузку использования доступа** (открытые уроки, отправленные ответы, проверки) как доказательную базу объёма оказанной услуги.
- Возврат ссылается на исходный платёж и выполняется на тот же способ оплаты; после возврата запись переводится в «доступ прекращён», прогресс и работы сохраняются как доказательство оказанной услуги.
- Перевод между группами одного курса: начисления прежней группы пересчитываются на фактически пройденное, по новой создаются на остаток; разница отражается на балансе (доплата — задолженность, экономия — переплата).

## 7. Приём и документооборот (ЭДО)

Модуль официального оформления образовательных отношений. Механика появления ученика и зачисления — в 4.7; здесь — что добавляет ЭДО поверх неё.

- **Паспортные данные и документы** — документальная часть анкеты (взрослого ученика либо представителя), заполняется по JOIN-ссылке или при оформлении договора, никогда — в публичной форме. Хранение шифруется, обращения журналируются (152-ФЗ).
- **Согласия и оферта — версионируемые документы.** Текст один на школу, редакции нумеруются; опубликованная редакция не редактируется — правка это следующая редакция. Механизм версий — ядро: регистрационное согласие версионируется на всех уровнях (02-tech §15.2); ЭДО добавляет поверх документальные виды — согласия документальной части и оферту договора. **Заявка, договор и акцепт привязываются к той редакции, которая действовала в момент подписания, и остаются на ней навсегда**: только так можно ответить, под каким текстом подписался конкретный человек. Новая редакция применяется к тому, что оформляется после публикации; **действующие ученики ничего не переподписывают** — массовое перепринятие обесценило бы сам акцепт. Хранится состав данных, цель и дата акцепта.
- **Договор** — формируется перед зачислением; печатные формы (заявления, договоры, согласия).
- **Приказы** — зачисление и отчисление оформляются приказом (модалка: номер, дата, основание).
- **Отчисление и восстановление** — с сохранением истории обучения; указание основания обязательно (освоение программы — одно из оснований отчисления, а не альтернатива ему).
- **Сертификаты и дипломы** — выдача по окончании обучения: автоматическая для публичных курсов, печатная форма с цифровой подписью для договорного обучения.
- Работа с несовершеннолетними (представители, школа/класс) — модуль «Школа», композиция описана в 4.7.

Остаётся детализировать: перечень печатных форм, личное дело, комплаенс-процедуры (сроки хранения, право на удаление, журналы доступа к ПД).

## 8. Публичная часть

### 8.1. Карточки курса

- **Карточка курса** — витринное представление: название, описание, целевая аудитория, категория, начальные требования, объём программы (автоподсчёт из содержимого с ручной правкой), сертификат (поле существует только при модуле ЭДО — выдача сертификатов и дипломов требует документооборота и лицензии, раздел 7), базовая цена. **Карточку целиком, включая базовую цену, ведёт маркетолог** — одно поле не дробится на отдельную роль и не ждёт решения другого человека; фактические цены групп и скидки остаются областью финансового администратора.
- **Метки готовности карточки вычисляются**, а не хранятся: «В разработке» (контент — черновик) → «Ожидает описания» (контент составлен, карточка не заполнена) → «Ожидает набора» (карточка заполнена, но чек-лист публикации не собран — 8.2) → «Готова к публикации» (собраны все пункты чек-листа) → «Опубликована».
- **Курс всегда один — карточек может быть несколько.** Карточки оформляются по-разному и различаются ценой и группой (а через группу — расписанием, ответственным за проверку, периодом). Пример: «Два раза в неделю» за 2 000 ₽ и «Один раз в неделю» за 1 000 ₽ — две карточки, две группы с разными расписаниями одного курса. В каталоге это независимые плитки.
- Граница механизма: карточки различают *условия* прохождения одного курса. Если различается сам состав уроков (сокращённая программа) — это копия курса, а не вторая карточка.

### 8.2. Запуск набора и публикация

- **Запуск набора** — явная кнопка на витрине (не побочный эффект заполнения карточки). Диалог запуска: фактическая цена (предзаполнена базовой), преподаватель набора (обязателен, если в курсе есть шаги ручной проверки), учебный период (при школьном контуре), выбор «доступно сразу / по датам». По кнопке создаётся группа-набор.
- **Публикация карточки в каталог — отдельное явное действие** с проверкой состояния по чек-листу: содержимое составлено; карточка заполнена; запуск существует; расписание набора утверждено; назначен преподаватель набора (при наличии шагов ручной проверки). Витрина показывает несобранные пункты со ссылками «куда идти». Кнопку жмёт маркетолог или любая роль выше по лестнице.
- **Проверка никогда не выключается**: если курс содержит задания без автопроверки, набор не публикуется без назначенного преподавателя. Вариантов «задания засчитываются без проверки» не существует.
- **Повторный набор** — новый запуск: тот же диалог, что и в первый раз (цена, преподаватель, период, «доступно сразу / по датам») → создаётся новая группа → расписание → утверждение → публикация. Курс один, запусков много; история архивных наборов остаётся под карточкой. Прошлый набор ничего в новый не переносит: цена и преподаватель к следующему набору успевают измениться чаще, чем остаться прежними.
- **Одновременно открыта запись максимум в один набор на карточку** (решение v1).
- **Повторная покупка блокируется**: курс, на который у ученика уже есть активная запись, купить нельзя — страховка от ошибочной двойной оплаты.

### 8.3. Карточка при закрытом наборе

Закрытие набора **не снимает карточку с витрины** — ради поисковой выдачи и удержания клиента:

- если создан следующий запуск — пометка «Набор откроется <дата>» и открыта **предзапись**: обычная запись в будущую группу с разовой оплатой при записи; материалы закрыты расписанием до старта. Новых сущностей не требуется;
- если следующего запуска нет — пометка «Набор закрыт».

### 8.4. Публичные страницы и лендинг

- **Блочный лендинг, один базовый шаблон в поставке.** Набор типовых блоков с фиксированной вёрсткой: шапка, hero с CTA «оставить заявку», «О школе», направления/курсы, преподаватели, отзывы, цены, контакты с картой, форма заявки (создаёт лид), подвал. Структура типовая для школ (ориентиры: educarium.ru, 100points.ru, primusschool.ru).
- **Вендор при развёртывании** подбирает клиенту цветовую палитру (white-label) и выполняет первичное наполнение. **Клиент меняет только контент**: тексты и изображения (маркетолог), включение/выключение и порядок готовых блоков (технический администратор). Изменение дизайна, вёрстки, новые блоки — заявка вендору, допработа.
- **Палитра white-label применяется к публичным страницам и письмам.** Кабинеты, плеер и админка — единый вид продукта у всех клиентов; из клиентского там только логотип школы в шапке.
- **Страницы по умолчанию на всех уровнях**: Главная (лендинг), «Курсы», «Об образовательной организации» («О нас»), «Преподаватели» (отдельной страницей или блоком в «О нас»), служебные — оферта, политика обработки ПД; на уровнях с онлайн-оплатой — оформление покупки.
- **Страница «Курсы» есть на всех уровнях** — карточки как товары. На У2/У4 это транзакционная витрина (самозапись, оплата, наборы — 8.1–8.3); на У1/У3 — информационный каталог: карточка ведёт на форму заявки (лид), запуск наборов и оплата не участвуют.
- **Страница преподавателя** — ручное заполнение маркетологом (фото, текст): общая страница со списком и персональная страница каждого преподавателя. Данные не берутся из учётных записей автоматически — никакой автопубликации ПД сотрудников.
- **SEO-гигиена витрины (в v1, свойство, а не фича)**: человекочитаемые адреса карточек, метатеги, sitemap, OpenGraph для шаринга, разметка schema.org/Course.

### 8.5. Открытые вопросы раздела

1. Статьи и публичный тренажёр — при детализации модуля SMM.
2. Оформление покупки на витрине: корзина (несколько курсов за раз) или покупка в один клик — уточнить при детализации витрины.

## 9. Дополнительные модули — детализация

Состав и совместимость с уровнями — см. 2.4. Первые два модуля детализированы; остальные — краткие описания, подробная проработка в технической части перед реализацией.

### 9.1. SMM / публичный контент — привлечение

Верх воронки: работает наружу, с анонимной аудиторией из поиска. Состав:

- **Статьи и блог**: разделы по предметам, редактор статей, SEO-поля. Профильная роль — **редактор** (приносится модулем): пишет, правит и публикует статьи; доступ минимальный — только публичный контент, без карточек, цен и ПД (наёмным авторам не выдаётся весь маркетинг). Маркетолог и выше вмешиваются по лестнице.
- **Публичный тренажёр**: открытые задачи из банка, решаются посетителем без регистрации; CTA «зарегистрируйся, чтобы сохранять прогресс». Отбор задач — методист (содержание обучения). С модулем ЕГЭ фильтр по номерам показывает **актуальные позиции экзамена плюс архивные прошлых лет** отдельной группой «Задания прошлых лет» (9.3): архивные задачи публикуются с решениями — это живой поисковый трафик, а не балласт. Отдельного хранилища под архив нет: это те же задачи банка, отобранные по статусу позиции.
- **Перелинковка** «статья → задачи по теме → карточка курса»: контент ведёт к продаже.

Зависимости: публичная часть ядра; банк задач — опционально (без него модуль = только блог). Модуль ЕГЭ обогащает статьи и задачи привязкой к номерам экзамена. Доступен на всех уровнях — блог полезен и репетитору У1.

### 9.2. Маркетинг — конверсия

Середина и низ воронки: работает внутрь, с идентифицированными людьми — лидами, учениками, покупателями. Состав:

- **Промокоды и акции**: коды со скидкой (сроки, лимиты использования), зачёркнутая цена на карточке. Скидка ложится в чек и лицевой счёт существующей операцией «скидка». Без модуля на витрине — просто указание цены.
- **Промо-рассылки и уведомления**: сегменты базы («лиды без покупки», «выпускники курса X»), отдельное согласие на рекламу при регистрации, отписка в один клик; вовлекающие уведомления в колокольчик и push с частотным колпаком (4.10.1). Поведенческие автотриггеры — развитие модуля, не v1.
- **CRM-воронка лидов**: канбан по статусам, ответственные, напоминания, история касаний. Без модуля — простой список лидов со статусами (4.7). Интеграции с внешними CRM (amoCRM, Битрикс24) — не делаем; по запросу как допработка.
- **Аналитика**: UTM-атрибуция лидов и покупок, подключение Яндекс.Метрики с e-commerce-событиями, воронка «визит → карточка → оплата», выручка по каналам. Без модуля в базе — статистика «сколько купили какого курса». Профильные роли: маркетолог; **аналитик** (read-only, приносится модулем).
- **Отзывы и рейтинги курсов**: сбор у завершивших, модерация маркетологом, вывод на карточку. Без модуля — только ручной блок отзывов на лендинге.

Зависимости: база учеников и лиды (ядро); витринные функции (промокоды, отзывы на карточках) — при витрине. Доступен на У2/У3/У4, на У1 не продаётся (продажи там ручные). **Не делаем** (вернёмся под живого клиента): реферальные программы, подарочные сертификаты.

### 9.3. Остальные модули (кратко)

- **Задания с ручной проверкой** — описан в 2.4 и 3.6: типы задач без автопроверки, очередь проверки, роли преподавателя набора и проверяющего.
- **Школа** — описан в 2.4 и 4.7: несовершеннолетние, представители, JOIN-связывание.
- **ЕГЭ** — экзаменационная разметка поверх банка задач: справочник позиций экзамена, привязка задач и статей к позициям, тренажёры и пробники в формате экзамена (включая плеер «Компьютер» для КЕГЭ — перенос из плагина), шкалы первичных баллов и таблицы перевода, статистика ученика в разрезе позиций экзамена.
  **Смена спецификации по годам** (принято 21.08.2026): состав экзамена меняется почти ежегодно — номера переезжают, отдельные позиции исчезают, у части меняется формат ответа. Поэтому позиция экзамена — **строка справочника, за которую держатся задачи**, а номер — её изменяемый атрибут: переномерация «23 стало 13» правится в одном месте и задач не касается. Исчезнувшая позиция уходит **в архив с годом**: её задачи перестают предлагаться при подборе в новые работы, но остаются везде, где уже используются, — архив не ломает существующие курсы и прошлые результаты. Смена формата ответа (было два файла, стал один) — не правка позиции, а новая позиция: старая архивируется вместе со своими задачами, новая наполняется заново, старые и новые задачи не смешиваются. Архивирует методист предмета. Межгодовой статистики в разрезе позиций нет и не планируется — сквозь года смотрим прогресс и результаты работ и экзаменов, поэтому «редакций экзамена» как отдельной сущности в модели не заводится.
- **Интерактивные задания по программированию** — тип задания «код»: редактор в браузере, выполнение в изолированном интерпретаторе на сервере, автопроверка тестами. Первый язык — Python; дальше — другие языки и задания по БД (SQL).
- **CRM / ERP** — внутренний учёт организации: зарплаты (преподаватели, проверяющие), расходы, материальные ценности (например, наборы по робототехнике). Самый дальний по срокам.
- **S3-хранилище** — собственный видеохостинг: записи занятий, трансляции (шаг «Трансляция», 5.2), видеотека; загрузка видеофайлов вместо внешних ссылок.
- **Вход через соцсети**, **AD-синхронизация** — описаны в 2.4.

## 10. Жизненный цикл инстанса

### 10.1. Онбординг клиента

Заезд: бриф-анкета (название, лого и палитра, домен, уровень и модули) → вендор разворачивает инстанс → первичное наполнение (white-label-палитра, лендинг, шаблоны писем) → передача доступов владельцу → обучение владельца. Домен — собственный домен клиента либо поддомен вендора, по условиям договора.

**Обучение и техподдержка входят в подписку.** Отдельно оплачиваются только допработки: переработка сайта, дизайна, бизнес-логики.

### 10.2. Демо-доступ

Отдельный демо-инстанс на поддомене вендора (вида `test1.<домен вендора>`) — развёрнутая «школа» с тестовыми предметами, курсами, группами и учениками. Потенциальному клиенту выдаются доступы от всех ролей. Персональный триал-инстанс — по договорённости для отдельных лидов.

### 10.3. Импорт и экспорт данных

- **Импортируются**: пользователи (ученики; ученики с родителями; данные ЭДО) и контент (предметы с курсами). Импорт учеников из файла по шаблону — самообслуживание администратора учебной части (единственное исключение из правила «админ не создаёт учеников», 4.7). Автоматической миграции с других платформ нет: перенос — вручную штатными средствами (импорт учеников + пересоздание контента); помощь в переносе — ручная услуга вендора по запросу.
- **Не импортируются**: расписание, кабинеты, административные роли, логи — заводятся в новом инстансе заново.
- **Экспортируются**: пользователи, контент, логи (журналы — только выгрузка, обратного импорта нет).

### 10.4. Неоплата подписки клиентом

Ступени деградации — школу нельзя останавливать мгновенно:

1. Уведомления владельцу, grace-период **14 дней** — всё работает.
2. **Блокировка админки на 30 дней** — кабинеты учеников, плеер и обучение продолжают работать.
3. Полная приостановка: заглушка на домене.
4. Хранение данных **6 месяцев** после приостановки, затем удаление с уведомлением.

### 10.5. Расторжение и уход клиента

- Клиент получает выгрузку: пользователи, контент, лицевые счета, документы ЭДО — структурированные форматы + медиафайлы.
- Инстанс хранится **3 месяца** после расторжения, затем персональные данные уничтожаются с оформлением акта.
- Read-only-доступ учеников к пройденным курсам (4.8) действует, пока школа остаётся клиентом платформы; при закрытии инстанса он прекращается — это отношения школы со своими учениками.

### 10.6. Апгрейд и даунгрейд уровня

- **Апгрейд**: запрос владельца вендору; применяется без простоя, данные и сущности остаются на месте и получают новые возможности (принцип надстроек).
- **Даунгрейд**: модули выключаются; роли, чьи функции исчезли, деактивируются — учётные записи людей сохраняются; данные отключённых модулей скрываются, но не удаляются (правило «шага неизвестного типа»).
- **Модули с клиентским контентом требуют процедуры выгрузки**: перед отключением S3 клиент предупреждается о необходимости скачать видео из хранилища; шаги «трансляция» и «видео из хранилища» становятся недоступными, клиент заменяет их базовыми шагами «видео по ссылке», разместив файлы самостоятельно. Перед любым даунгрейдом владельцу показывается сводка затрагиваемого.

### 10.7. Эксплуатация

- **Обновления**: единая версия продукта для всего парка инстансов; плановые работы ночью с анонсом в админке; changelog владельцу.
- **Поддержка**: раздел «Поддержка» в админке владельца — запросы на модули, допработки, инциденты; сроки реакции — в договоре.
- **Восстановление данных из бэкапа** по запросу клиента (ошибочное удаление администратором) — операция вендора; глубина хранения бэкапов — по договору.
- **Смена владельца инстанса** — только вендором по официальному запросу клиента.

## 11. Глоссарий

_Пополняется по мере обсуждения._

**Продукт и поставка**

- **Инстанс** — отдельный развёрнутый экземпляр приложения для одного клиента: контейнер, база, хранилище, домен.
- **Вендор** — разработчик и поставщик продукта, обслуживающий инстансы. **Клиент** — организация, купившая подписку (не путать с пользователем).
- **Уровень** — именованный набор базового функционала, единица прайса. **Дополнительный модуль** — функциональность, докупаемая к уровню.
- **Комплектация** — фактический набор включённых у инстанса модулей и фич (уровень плюс докупленное). Меняется правкой конфига с перезапуском, а не действиями пользователя; не путать с **правами** (что позволено конкретному человеку внутри включённого функционала).
- **Принцип надстроек** — сущности едины на всех уровнях и обрастают функциональностью модулей; апгрейд не мигрирует данные.
- **Кампус** — модуль очного обучения: расписание занятий, кабинеты, замены, посещаемость, журнал.
- **ЭДО** — модуль официального оформления: паспортные данные, документальные согласия, договоры, приказы.
- **Школа** — модуль работы с несовершеннолетними: поля «школа/класс» в анкете, представитель (родитель), JOIN-связывание.

**Роли и доступ**

- **Право** — атомарная разрешённая операция; регистрируется модулем при подключении.
- **Функциональная область** — связная группа прав вокруг одного вида работы; строки матрицы 3.4. Роль собирается из областей.
- **Роль** — именованный набор областей, поставляемый вендором; редактора ролей у клиента нет.
- **Граница назначения** — рамка действия роли: своя группа (преподаватель), закреплённые преподаватели (методист), назначенные группы (проверяющий), организация (администратор, владелец).
- **Закрепление** — связь «преподаватель → курирующий методист»; назначает владелец.

**Учебный процесс**

- **Группа** — учебный коллектив в границах периода; универсальный носитель цены, расписания и состава. На витрине выступает как «поток»/«набор».
- **Занятие** — слот календаря кампуса: дата, время начала и окончания, кабинет, преподаватель. У занятий из сетки время берётся из регулярности группы; у добавленных вручную (включая индивидуальные) — вводится при создании. Строго один урок на занятие.
- **Запись на курс** — связь ученика с курсом, единственный источник ответа о доступе.
- **Расписание группы** — план открытия уроков: привязка к занятиям (кампус) или датам (У2); состояния урока «открыт сразу / запланирован / не запланирован»; статусы «в работе»/«утверждено».
- **Анкета** — данные ученика: базовая часть заполняется при регистрации, модули добавляют поля («Школа» — школа/класс, ЭДО — документальную часть).
- **Учётка-заглушка** — результат регистрации: учётная запись с анкетой, но без курсов; курсы появляются с зачислением.
- **Лид** — обращение с формы лендинга (имя, контакт); учётную запись не создаёт.
- **JOIN-ссылка** — ссылка-код для связывания представителя с учеником и заполнения документальной части анкеты; истекает по сроку.
- **Заморозка курса** — остановка поставки курса при отчислении: прогресс и доступ сохраняются в режиме «только чтение», новые уроки и структурные правки не доезжают (запись фиксирует версию снимка); правки живого содержимого видны, как и всем.
- **КТП** — календарно-тематический план: отчётная проекция расписания (темы × даты), У3+.
- **Снимок курса** — зафиксированная при назначении группе версия структуры курса; обновляется до текущей структуры явным действием методиста «Обновить снимок».
- **Прохождение** — автоматическая отметка об уроке из прогресса шагов. **Посещаемость** — ручная отметка преподавателя о присутствии (кампус).

**Контент и прохождение**

- **Банк задач** — самостоятельное хранилище задач с разметкой: выдаёт задачу и проверяет ответ, не зная, где она используется. Шаги ссылаются на задачи, а не копируют их.
- **Библиотека работ и экзаменов** — хранилище переиспользуемых наборов задач; шаги ссылаются на них так же, как на задачи банка.
- **Курс-копилка** — служебный непубликуемый курс («Материалы индивидуальных занятий»), уроки которого прикрепляются к индивидуальным занятиям.
- **Задача** — единица банка; тип ввода ответа определяет интерфейс решения и способ проверки. **Автопроверяемая** — проверяется системой; остальные требуют модуля ручной проверки.
- **Задание** — задача, предъявленная ученику к выполнению: в составе работы или экзамена — со своей позицией, от которой считаются нумерация («Задание 3», с префиксом школы — 5.3) и вес по шкале оценивания; отдельным шагом урока — без номера и веса. В банке хранятся **задачи**; заданием задача становится там, где её решают. Тип ввода ответа и способ проверки — свойство задачи, поэтому «типы задач без автопроверки», а не «типы заданий»; имена модулей и типов шагов («Задания с ручной проверкой», «интерактивные задания по программированию») — устоявшиеся названия и под это правило не подпадают.
- **Позиция экзамена** (модуль ЕГЭ) — строка справочника номеров экзамена: номер, название, шаблон ответа, максимальный первичный балл. Задачи держатся за позицию, а не за её номер, поэтому переномерация по новой спецификации задач не касается; исчезнувшая позиция уходит в архив с годом и питает публичный раздел «Задания прошлых лет» (9.3). Термин отдельный именно потому, что «задание» уже занято позицией внутри работы.
- **Работа (контрольная)** — набор задач с общим результатом внутри плеера; решается в явном «режиме решения», выход из которого фиксирует результат.
- **Попытка** — отдельный подход к выполнению работы. **Сдача** — отправленный на проверку результат.
- **Экзамен** — набор задач на отдельной странице: одна попытка, жёсткий таймер, заблокированная навигация.
- **Шкала оценивания** — переиспользуемая карта «задание → баллы» для экзаменов (задания разного веса); основа первичных баллов модуля ЕГЭ.
- **Режим проведения** — способ выполнения работы, определяющий движок: в плеере курса либо на отдельной странице с таймером; закрытый список вендора, модули добавляют свои (ЕГЭ). Школа режимы не изобретает.
- **Тип работы** — «тег» школы поверх режима, из справочника (ДЗ, СР, КР…): метка журнала и признак «итоговая»; поведения не меняет.
- **Тема** — термин справочника тем предмета (дерево, ведёт методист): разметка задач для поиска, подбора в работы и публичного тренажёра; свободного ввода нет.
- **Сложность** — закрытая шкала вендора (простая / средняя / сложная): подбор задач и сравнимая статистика.
- **Дедлайн сдачи** — срок приёма сдач работы в расписании группы; после него приём закрывается либо идёт с пометкой «просрочено».
- **Обязательный шаг** — блокирует переход к последующим шагам урока (но не к другим урокам); по умолчанию обязательны все шаги.
- **Замена** — временная замена преподавателя (с полным «гостевым» доступом заменяющего к группе на период) либо кабинета группы; оформляет администратор учебной части.
- **Отработка** — индивидуальное занятие для пропустившего ученика; урок прикрепляется из курса индивидуальной группы (открывает доступ) либо из курса, где у ученика уже есть запись (отмечает тему для КТП и журнала).
- **Медиахранилище** — общее для инстанса хранилище файлов курсов с проверкой по типу и объёму.

**Витрина**

- **Карточка курса** — витринное представление курса; у одного курса может быть несколько карточек с разными условиями.
- **Набор (поток)** — группа, созданная запуском с витрины; «запуск набора» — операция её создания.
- **Преподаватель набора** — преподаватель, закреплённый за набором при его запуске; на У2 существует при модуле ручной проверки. Слово «куратор» как синоним не используется — термин зарезервирован под будущие надзорные роли (3.7).
- **Предзапись** — запись в будущий набор до его старта; материалы закрыты расписанием.
- **Каталог** — публичный перечень карточек курсов.

**Оплата**

- **Лицевой счёт** — журнал денежных операций обучающегося; баланс = оплачено − начислено (минус — долг, плюс — переплата).
- **Начисление** — обязательство оплатить; основание: курс, месяц группы или занятие. **Платёж** — поступление средств (провайдер или вручную).
- **Скидка/корректировка** — явная операция уменьшения обязательства с причиной.
- **Схема оплаты** — настройка группы: разовая / помесячная («абонемент») / поурочная.
- **Платёжный провайдер** — абстракция сервиса приёма онлайн-платежей; первая интеграция — ЮKassa.
- **Выгрузка использования доступа** — сведения о фактических действиях ученика, доказательная база при возврате.

**Уведомления**

- **Адресное уведомление** — сообщение выбранным людям, отправленное человеком по конкретному поводу (в отличие от автоматических уведомлений реестра 4.10). Канал — колокольчик и push. Два класса: служебные (администраторы) и вовлекающие/промо (маркетолог, модуль «Маркетинг»).
- **Шаблон уведомления** — заготовка текста с переменными; отправная точка сообщения, а не обязательная форма.
- **Частотный колпак** — предел числа промо-уведомлений одному человеку за период; настройка организации, защищает базу от выгорания.
- **Снимок получателей** — поимённый список тех, кому ушло уведомление, сохранённый в момент отправки; отвечает на вопрос «кому это ушло» независимо от последующих изменений состава групп.
