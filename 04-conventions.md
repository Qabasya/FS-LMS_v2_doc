## 1. Стек и инструменты

_Закрепляем инструменты сборки и проверки; правила их обновления._

### 1.1. Менеджер зависимостей Python — poetry ✅

> Принято 14.08.2026. Пересмотр решения 02-tech §1.5 (был uv).

**Решение:** poetry 2.x; `pyproject.toml` по PEP 621; `poetry.lock` — единственный источник версий backend-зависимостей.

**Почему poetry, а не uv:**

1. Проект — приложение в Docker, не публикуемая библиотека: несущих преимуществ uv (скорость на больших графах, workspaces, установка Python) у нас нет — в проде Python приходит из официального Docker-образа, выигрыш в CI — секунды.
2. Дефолты uv — ловушки для джуна и AI-агентов: `uv run` тихо доставляет зависимости, venv без pip «протекает» в глобальное окружение.
3. В марте 2026 Astral (uv) куплена OpenAI; пакетный менеджер — supply-chain-критичная инфраструктура, и доверять её стороннему ИИ-вендору с неясным governance не хотим. **Ruff (тоже Astral) остаётся**: dev-time-инструмент, риск другого порядка, замена (black + flake8) возможна в любой момент.
4. Зрелость и объём обучающих материалов poetry — прямая помощь джуну; PEP 621-совместимость с версии 2.x снимает главную историческую претензию.

**Правила использования:**

- `pip install` запрещён везде — любая зависимость входит через `poetry add` в PR по правилам реестра (02-tech §1.5);
- Python: прод — официальный образ `python:3.12-slim`, локально — официальный установщик или pyenv; poetry версией Python не управляет — и не должен;
- CI: `poetry sync` с кэшем по хэшу `poetry.lock` (в poetry 2.x команды `install --sync` нет — она заменена отдельной `poetry sync`);
- lockfile коммитится всегда; конфликт в нём решается перегенерацией, не ручной правкой.

**Отвергнуто:** uv — вернёмся, если время установки зависимостей станет измеримой болью (правило 02-tech §21: изменения — через измерение, не предположение).

### 1.2. Менеджер зависимостей Node — pnpm ✅

> Принято 14.08.2026. Подтверждение решения 02-tech §1.5.

**Решение:** pnpm; `pnpm-lock.yaml` — единственный источник версий frontend-зависимостей.

**Почему:**

1. **Строгий node_modules**: пакет физически не может импортировать незаявленную зависимость (phantom dependencies). Это установочный уровень той же дисциплины, которую eslint-plugin-boundaries держит на уровне импортов, — прямо работает на границы пакетов `ui` / `api-client` / `modules/*` (02-tech §4.7).
2. Штатные **workspaces** — монорепо стоит на них (02-tech §11.3).
3. Скорость установки и экономия диска (content-addressable store).

**Правила использования:**

- версия pnpm пинится полем `packageManager` в корневом `package.json` (corepack) — у всех, включая CI, одна версия;
- `npm install` и `yarn` запрещены так же, как `pip install`;
- lockfile коммитится всегда; CI ставит с `--frozen-lockfile`.

**Отвергнуто:** npm — нет строгости, workspaces слабее; yarn berry — PnP-режим конфликтует с частью тулинга, лишняя экзотика для джуна.

### 1.3. Стили — SCSS ✅

> Принято 14.08.2026. Пересмотр решения 02-tech §11.3 (было «CSS без SCSS»).

**Решение:** собственные стили пишутся в SCSS-синтаксисе (`.scss`; компилятор `sass-embedded` в dev-зависимостях, Vite поддерживает из коробки). Indented-синтаксис Sass (`.sass`) запрещён — несовместим с копипастой CSS и хуже поддержан тулингом.

**Правила:**

1. **Токены — только CSS custom properties** (`var(--fs-14)`, `var(--sq)`…): их читает рантайм и тема Mantine. `$`-переменные для токенов запрещены — `$` существует только как compile-time сахар (миксины, функции, циклы). Файл токенов — `ui-kit/variables.scss` (блок `:root`).
2. Миксины и функции — только в пакете `ui`, для повторяющихся предметных паттернов (сетки журнала, клетки прогресса); в экранах не объявляются.
3. Вложенность — до трёх уровней; глубже — сигнал разбить компонент.
4. Стили Mantine не переопределяются файлами стилей — только темой (`theme.ts`) и styles API компонентов.

**Контекст:** команда работала на SCSS в плагине 1.0 — привычка сохранена по цене одной dev-зависимости. То, ради чего SCSS брали исторически (переменные, вложенность), теперь есть и в нативном CSS, поэтому повседневные файлы почти не отличаются от обычного CSS.

### 1.4. Генератор TS-клиента из OpenAPI — orval ✅

> Принято 14.08.2026. Закрывает выбор, отложенный в 02-tech §9.2.

**Решение:** orval. Пакет `api-client` монорепо генерируется из OpenAPI-схемы бэкенда: типы, хуки TanStack Query, MSW-моки — всё из одного контракта. Пересборка — в CI (02-tech §9.2); **сгенерированный код руками не редактируется** — любая правка перезатрётся следующей генерацией.

**Почему orval, а не hey-api:**

1. **Готовые хуки** (`useCampusGroupsList()` и т. п.) — меньше ручной обвязки и концепций для джуна; у hey-api вместо хуков options-паттерн: композиционно элегантнее, но это лишний слой для понимания.
2. **Встроенная генерация MSW-моков из OpenAPI** — волны 0–1 фронта (ui-plan §4) собирают экраны на моках до готовности бэкенда: моки приходят бесплатно из того же контракта, фронт не блокируется бэком.
3. Мультифреймворковость hey-api (React/Vue/Svelte/Angular из одного вывода) нам не нужна: фронт один, React.

**Правила:** конфиг orval — в репо; моки MSW используются в разработке экранов и тестах фронта (vitest); contract-тест «клиент компилируется против текущей схемы» — как в 02-tech §9.2.

**Отвергнуто:** hey-api — вернёмся, если понадобится второй фреймворк или orval остановится в развитии.

### 1.5. Версии платформ и их фиксация ✅

> Принято 14.08.2026.

**Решение:** версии закрепляются декларативно — там, где инструменты сами их проверяют; менеджер версий — рекомендация, не требование.

- **Прод**: версии зашиты в Docker-образы (`python:3.12-slim`, `postgres:16`, nginx) — на серверах руками не устанавливается ничего.
- **Пины в репо**: `requires-python = ">=3.12,<3.13"` в pyproject (poetry откажется работать не тем питоном); `engines.node` + `packageManager` в корневом package.json (pnpm с engine-strict откажется не той версией); файлы `.python-version` и `.nvmrc` в корне — их читают pyenv/nvm и CI-экшены, версия задаётся один раз.
- **Node** — текущий LTS (22); **PostgreSQL** — 16, мажор фиксирован до осознанного обновления.
- **Локально**: официальные установщики нужных версий + corepack — достаточный минимум (в т. ч. на Windows); mise или pyenv+nvm — по желанию.
- **Обновление версии платформы** — отдельный PR, меняющий все пины разом (Dockerfile, pyproject, package.json, `.python-version`, `.nvmrc`, CI).

### 1.6. Правила реестра зависимостей ✅

> Принято 14.08.2026. Расширяет 02-tech §1.5.

**Вход — только PR с обоснованием** по чек-листу:

1. зачем нужна и почему не хватает стандартной библиотеки или уже имеющейся зависимости;
2. живость: последний релиз < 12 месяцев, на issues отвечают;
3. лицензия MIT/BSD/Apache; copyleft (GPL и родня) — только через отдельное обсуждение;
4. для фронта — вклад в бюджет начального чанка (02-tech §11.3, §20).

**Правила:**

- один инструмент на задачу, дубли запрещены: даты — dayjs, иконки — @tabler/icons-react, редактор — TipTap;
- очередь заранее согласованных кандидатов: `@dnd-kit` (перетаскивание), `@tabler/icons-react` (иконки), KaTeX (формулы) — вносятся, когда появляется потребитель (ui-plan §5);
- **lowlight + highlight.js** (принято 27.08.2026) — подсветка синтаксиса в блоках кода редактора, через официальное расширение TipTap `@tiptap/extension-code-block-lowlight` (02-tech §1.5); потребитель — кнопка «Вставить код» в шаге «Лекция» и условии задачи (01-product §5.2, §5.4). Один инструмент, а не два: серверная подсветка не нужна — код отображается тем же расширением и в конструкторе, и в плеере;
- **обновления**: security — немедленно, вне очереди (pip-audit / npm audit красные в CI — 02-tech §15.2); минорные — ежемесячный батч-PR; мажорные — по одному, с чтением changelog и полным прогоном тестов;
- Клод зависимости не добавляет сам — только предлагает в обсуждении (правило §5.2).

### 1.7. IDE и форматирование ✅

> Принято 14.08.2026.

**Конфиги в репо — единственный источник стиля**: ruff (линт + формат, заменяет black/isort), prettier (ts/tsx/scss/md), `.editorconfig` (отступы, финальный перевод строки, кодировка — база для любого редактора).

- **CI проверяет формат** (`ruff format --check`, `prettier --check`): неотформатированный код = красный CI. Следствие: споров о стиле в ревью не существует — формат не обсуждается вообще.
- В репо лежит рекомендованный набор VS Code (`.vscode/extensions.json` + `settings.json` с формат-он-сейв) — разработчик открывает проект и получает готовую среду. JetBrains настраивается по короткой инструкции в README; `.idea` в git не кладётся.
- Правки конфигов линтеров — отдельным PR, не вперемешку с фичей.

## 2. Репозиторий

### 2.1. Раскладка монорепо ✅

> Принято 14.08.2026.

```
fs-lms/
├── backend/
│   ├── app/            # kernel/ · core/ · modules/<id>/ — слои из 02-tech §2.3, §4.1;
│   │                   # Jinja2-шаблоны публичных страниц и писем живут внутри слоёв-владельцев (02-tech §11.1)
│   ├── migrations/     # единая цепочка Alembic
│   ├── tests/
│   └── pyproject.toml
├── frontend/
│   ├── apps/app/       # SPA: /learn + /manage
│   ├── packages/ui/    # библиотека компонентов (03-design §8; сюда переезжает ui-kit)
│   ├── packages/api-client/   # генерируется orval (§1.4)
│   └── packages/modules/<id>/ # зеркалит backend/app/modules/<id>
├── deploy/             # compose-шаблон, конфиг nginx, скрипты провижининга, runbooks/
├── docs/               # 01–04, мокапы, specs/ (фиче-спеки)
└── .github/            # CI
```

**Принципы:**

- **Модуль зеркалится по имени**: `backend/app/modules/campus` ↔ `frontend/packages/modules/campus`; границы держат import-linter и eslint-boundaries с двух сторон (02-tech §4.7).
- **Сгенерированный `api-client` коммитится** — его дифф в PR и есть видимый дифф контракта API; править руками запрещено (§1.4).

### 2.1a. Карта кода для агента: вложенные CLAUDE.md ✅

> Принято 17.08.2026. Цель — агент правит код без «разведки» по всему репозиторию перед каждым фиксом.

Каждая граница слоя и модуля из §2.1 — точка, где заводится свой `CLAUDE.md`:

- `backend/app/kernel/CLAUDE.md`, `backend/app/core/CLAUDE.md`;
- `backend/app/modules/<id>/CLAUDE.md` — по одному на модуль;
- `frontend/apps/app/CLAUDE.md`, `frontend/packages/ui/CLAUDE.md`, `frontend/packages/modules/<id>/CLAUDE.md`.

Claude Code сам подхватывает ближайший вверх по дереву `CLAUDE.md` от файла, который трогает — вложенный файл не пересказывает документацию, а адресует: что это за папка, 3–5 ключевых файлов с однострочным назначением, ссылка на манифест модуля (02-tech §4) и на разделы спек. Корневой `CLAUDE.md` остаётся общим указателем (§5.3); вложенные — детализируют конкретную подсистему.

**Обязанность обновлять — часть диффа, не отдельная задача**: PR, заводящий новую папку кода или модуль, тем же диффом заводит её `CLAUDE.md`; PR, меняющий назначение файлов внутри границы, обновляет вложенный `CLAUDE.md` рядом. Пункт входит в чек-лист PR (§3.3) и в ограничения Клода (§5.2, п.10) — карта без этого правила устаревает быстрее, чем ей начинают пользоваться.

### 2.2. Что не лежит в git ✅

> Принято 14.08.2026.

- **Секреты — никогда**: в репо только шаблоны (`.env.example` с комментарием у каждой переменной). Реальные конфиги и секреты инстансов живут в конфиг-репозитории вендора (02-tech §17).
- Также вне git: дампы БД, содержимое MinIO, данные compose-волюмов, `.idea` (а вот `.vscode`-набор коммитится — §1.7).
- **Правило для каждого**: файл с паролем, ключом или токеном в диффе = стоп и вопрос, даже если «это тестовый».

### 2.3. Судьба репозитория документации ✅

> Принято 14.08.2026.

Документация **переезжает в монорепо** (`docs/`) при его постановке (фаза 0): спека и код меняются одним PR — правило «нашёл расхождение — сначала правь документ» (§4.1) работает только когда документ в том же диффе; Клоду — один контекст вместо двух репозиториев; мокапы едут туда же как референс вёрстки. Текущий репозиторий после переезда замораживается с README-ссылкой на новый; до постановки монорепо работа продолжается здесь.

## 3. Git-процесс

### 3.0. Git — только руки человека ✅

> Принято 14.08.2026.

**ИИ-агент с git не работает вообще**: не коммитит, не создаёт и не удаляет ветки, не мержит, не пушит, не откатывает. Вклад Клода — изменения в рабочем дереве и **текстовые подсказки**: черновик сообщения коммита, черновик описания PR. Любую git-операцию выполняет человек. Правило продублировано в §5.2.

### 3.1. Модель веток — trunk-based ✅

> Принято 14.08.2026.

- `main` — единственная долгоживущая ветка: всегда зелёная (CI обязателен), всегда готова к срезу релиза. Develop- и release-веток нет — релиз собирается тегом из main (02-tech §17).
- Работа — в коротких ветках от main: **одна ветка = одна фиче-спека или задача**, живёт дни. Ветка, живущая неделю, — сигнал, что срез слишком крупный.
- Именование: `тип/короткая-суть-латиницей`, тип из списка feat / fix / docs / chore / spec: `feat/campus-schedule-grid`, `fix/journal-focus`, `docs/spec-enrollment`.
- Перед PR ветка ребейзится на свежий main.

### 3.2. Коммиты ✅

> Принято 14.08.2026.

Два уровня подробности: рабочие коммиты в ветке — короткие, итоговый squash-коммит в main — полный (§3.3).

- **В ветке** — краткие отметки прогресса по фиче: `тип(область): что изменилось` — например, `fix(kege): доработка дизайна и логики страницы`. Идеальная атомарность не требуется: в main эти коммиты не попадают.
- **Типы**: feat, fix, docs, refactor, test, chore; **область** — модуль или пакет (campus, ui, api-client…). Префикс английский — по нему работает автогенерация changelog (§3.4); текст русский — его читает только команда.
- Коммитит всегда человек (§3.0); Клод может предложить текст сообщения.

### 3.3. PR и мерджи в main ✅

> Принято 14.08.2026.

- **Squash-merge**: одна ветка = один коммит в main. **Заголовок** — conventional одной строкой; **тело** — развёрнутое описание всего, что сделано с прошлого мерджа: «Исправлена гонка в AssessmentAnswerRepository: …». История main читается как список фич, каждая — с полным рассказом внутри.
- **Описание PR** и есть это развёрнутое описание — при squash оно становится телом коммита. Шаблон в `.github/`: **Что и зачем** (ссылка на фиче-спеку, для feat обязательна) · **Что изменилось** (полный список с прошлого мерджа) · **Как проверено** (тесты; для UI — скриншоты 1440/1024 против мокапа) · **Чек-лист**: спека обновлена вместе с кодом · дифф `api-client` осмотрен · миграции есть/нет и осмотрены · строки через i18n · вложенный `CLAUDE.md` заведён/обновлён при изменении границы (§2.1a).
- **Ревью**: PR джуна ревьюит лид (Клод делает предварительный текстовый проход до него); PR лида ревьюит Клод (/code-review). **Merge нажимает только человек.** Красный CI не мержится никогда — исключения «потом починим» не существует.

### 3.4. Релизы ✅

> Принято 14.08.2026.

- Единая semver-версия всего продукта (02-tech §17): PATCH — фиксы; MINOR — фичи и модули; MAJOR — редкие вехи (завершение фазы, ломающее для эксплуатации).
- Релиз = тег `vX.Y.Z` на main → CI собирает образы → накатка волнами: staging → свой инстанс (канарейка) → парк (02-tech §17).
- **Changelog двойной**: технический — автогенерация из conventional-заголовков squash-коммитов; клиентский (в админке владельца — 01-product §10.7) пишет человек человеческим языком, Клод готовит черновик.
- Security-релизы — вне очереди (02-tech §15.2).

## 4. Spec-Driven Development

_Главный процессный раздел — обещан в 02-tech §0.1._

### 4.1. Пирамида спецификаций ✅

> Принято 14.08.2026.

Три уровня:

1. **Документы 01–04** — «конституция»: меняется редко и осознанно.
2. **Фиче-спеки** (`docs/specs/`) — по одной на фичу; остаются навсегда как история решений.
3. **Код и тесты.**

**Правило направления:** код не противоречит фиче-спеке, фиче-спека — верхним документам. Расхождение чинится **сверху вниз**: сначала правится документ (можно тем же PR, что и код — §2.3), потом код. Конфликт между верхними документами: каждый главный в своей зоне — 01 в продуктовых вопросах, 02 в технических, 03 в интерфейсных; противоречие между ними — баг документации, чинится немедленно.

### 4.2. Шаблон фиче-спеки ✅

> Принято 14.08.2026.

Файл `docs/specs/NNN-имя.md`; разделы фиксированные:

1. **Шапка**: статус (черновик → принята → реализована; отменена), фаза, ссылки на разделы 01–03.
2. **Границы**: что входит и что **не** входит (анти-scope обязателен).
3. **Поведение**: сценарии, правила, крайние случаи.
4. **Модель данных**: таблицы, колонки, индексы; план миграции.
5. **API-контракт**: эндпоинты, схемы запросов и ответов, права (`require(...)`), коды ошибок — от этого раздела стартует параллельная работа (§4.3).
6. **Экраны**: ссылки на 03-design §4.x и мокапы + отличия и состояния, если фича их добавляет.
7. **События и уведомления**: что публикует, кто подписан.
8. **Тесты**: перечень проверок по цене ошибки (02-tech §20).
9. **Открытые вопросы.**

**Ограничение размера:** спека читается за 10–15 минут; не влезает — фича режется на две. **Кто пишет:** Клод — черновик по итогам обсуждения; человек вычитывает и переводит в «принята» (§5.6).

**Блокирующие разделы** (дополнено 21.08.2026). Разделы **4 «Модель данных»** и **5 «API-контракт»** — блокирующие: пока в них общие слова («добавим таблицу заявок», «эндпоинт создания»), а не таблицы с колонками и индексами и не схемы запросов/ответов с правами и кодами ошибок, спека **не переводится в «принята»**, а агент-исполнитель (§5.7) **не запускается**.

Причина: если проектных решений нет в спеке, их принимает тот, кто пишет код, — по ходу и без ревью. Так в проекте заводится «архитектор поневоле»: решения приняты, но нигде не записаны и никем не утверждены (нарушение §5.1 и §5.2 п.2). Раздел 3 «Поведение» этой роли не заменяет — он описывает, *что* видит пользователь, а не *чем* это обеспечено.

Исключения: фича, которая не трогает данные или API (правка текстов, чисто визуальное изменение экрана), — раздел помечается явным «не затрагивается», молча пустым не остаётся.

### 4.3. Жизненный цикл фичи ✅

> Принято 14.08.2026.

1. **Спека**: черновик → вычитка → «принята».
2. **Контракт**: роуты-заглушки с настоящими Pydantic-схемами → OpenAPI → генерация `api-client` + MSW-моков. С этой точки фронт и бэк не ждут друг друга.
3. **Параллельная разработка**: бэк — сервисы и тесты; фронт — экраны против моков. Контракт меняется только через спеку и PR с видимым диффом — устных договорённостей «я поле переименовал» не существует.
4. **Ревью и squash-merge** (§3.3); спека → «реализована». Расхождения, найденные по ходу, правятся в спеке тем же PR.

**DoD фичи** (02-tech §20): спека есть и актуальна → тесты по спеке зелёные → CI зелёный → дифф контракта и миграции осмотрены → для UI дополнительно DoD экрана (ui-plan §1).

### 4.4. Этапы и трекинг задач ✅

> Принято 14.08.2026.

- Иерархия: **фаза** (02-tech §23) → **фиче-спека** → **задачи**.
- Трекинг — GitHub Issues: milestone = фаза, метки = модули, задача ссылается на спеку. Фронтовые волны — по шагам ui-plan §4.
- Задач класса feat вне какой-либо спеки не существует; мелкие fix/chore — можно без спеки, но с полным описанием в PR.
- **Вертикальные срезы**: фича целиком (бэк + фронт + тесты); «сначала весь бэкенд» запрещено (02-tech §23).

### 4.5. Журнал решений ✅

> Принято 14.08.2026.

- Основной формат — **статус-блоки в документах**, как уже принято: «Статус: принято (дата)» + обоснование + отвергнутые альтернативы.
- Решения масштаба фичи — в разделах «Открытые вопросы»/«Решения» её спеки.
- Межфичевые решения, которым нет места в 01–04, — `docs/decisions/` с короткими ADR-заметками (контекст → решение → последствия). Это запасной формат: сначала решение пытаемся положить в профильный документ.

## 5. Работа с Claude

### 5.1. Роли ✅

> Принято 14.08.2026.

**Клод делает:** черновики фиче-спек по итогам обсуждения; код по принятой спеке (бэк и фронт); тесты по спеке; предварительное ревью PR джуна и ревью PR лида — текстом; черновики текстов (сообщения коммитов, описания PR, клиентский changelog); сверки документации на согласованность; **наставничество джуна** — «объясни, почему здесь так устроено» — легитимный и поощряемый запрос, ответ со ссылками на документы.

**Только человек:** все решения (продуктовые, архитектурные, зависимости, приоритеты); git целиком (§3.0) и merge; всё, что касается прода, — провижининг, миграции на живых инстансах, доступ к данным клиентов; общение с клиентами.

### 5.2. Ограничения Клода ✅

> Принято 14.08.2026.

1. **«Нет спеки — нет кода»**: feat-код пишется только по принятой спеке; исключение — мелкие fix/chore с полным описанием в PR (§4.4).
2. Новые зависимости, архитектурные решения, изменения схемы БД и контракта API — только **предложением в обсуждение**, никогда фактом в диффе.
3. Границы модулей не обходятся: красный import-linter / eslint-boundaries чинится изменением кода, а не ослаблением конфига.
4. **Git не трогает вообще** (§3.0) — только текстовые подсказки.
5. Секреты и данные клиентов не запрашивает, не логирует, не вставляет в код и тесты (фикстуры — только фабрики, 02-tech §20).
6. Статус «принято» в документах — только после явного «ок» человека; Клод не самоутверждает решения.
7. Обнаружил противоречие спеки и реальности — **останавливается и поднимает вопрос**, а не выбирает трактовку сам.
8. **Не лезет в файлы вне задачи**: правит только файлы, прямо названные задачей или очевидно входящие в её границы по фиче-спеке. Читать шире можно (поиск причины бага — легитимен), править — нет.
9. **Никаких попутных правок**: заметил рядом опечатку, устаревший код, «не тот» стиль — не чинит молча в том же диффе, а сообщает текстом или предлагает отдельной задачей. Один PR = одна фича или один фикс; посторонние файлы в диффе — красный флаг на ревью.
10. **Вложенные `CLAUDE.md` обновляются тем же диффом**, что и граница кода, которую они описывают (§2.1a) — не откладывается на «потом».

### 5.3. Контекст: CLAUDE.md ✅

> Принято 14.08.2026. Файл создан — [CLAUDE.md](CLAUDE.md); при переезде в монорепо (§2.3) едет в его корень и дополняется командами запуска.

- Содержимое: краткая карта репозитория (что где лежит); таблица «тип задачи → обязательные документы» (= §7); ограничения §5.2 сжатым списком; команды запуска dev-окружения, тестов и линтеров (появятся с монорепо).

- Долгоживущие факты о проекте — в документы и спеки, а не в приватную память агента: знание лежит в файлах, которые читает и человек (bus-factor).

### 5.4. Что человек проверяет за Клодом всегда ✅

> Принято 14.08.2026. Зоны по цене ошибки — 02-tech §20.

- каждая миграция — глазами, построчно;
- всё про деньги: ledger, payments, вебхуки, идемпотентность;
- права и области видимости: `require(...)` на каждом роуте, предикаты scope;
- дифф контракта API (`api-client` в PR);
- изменения аудита и журналирования;
- шаблоны писем, уходящих наружу.

Правило: **«Клод написал, и тесты зелёные» ≠ готово** — тесты Клода проверяют его же понимание задачи; человек сверяет поведение со спекой, а не только читает код.

### 5.5. Сессии агента: планирование отдельно, код отдельно ✅

> Принято 15.08.2026.

**Одна задача = одна сессия.** Работа с агентом делится на два типа сессий, и они не смешиваются:

- **Сессия планирования** — обсуждение фичи. Результат: черновик фиче-спеки (§4.2) и **GitHub Issue с чек-листом задач** (§4.4), где каждый пункт помечен исполнителем — человек или агент. После вычитки и «принята» сессия закрывается; её диалог больше никому не нужен — всё важное из него записано.
- **Сессия реализации** — один пункт чек-листа (или связка мелких), с чистым контекстом. Агент восстанавливает контекст из трёх мест и только из них: `CLAUDE.md` (карта и команды) → фиче-спека (что и почему) → Issue (что уже сделано — по чек-боксам). Пересказывать историю обсуждения в промпте не нужно и не следует: если для работы не хватает того, что записано, — это дыра в спеке, и чинится она правкой спеки, а не устным дополнением.

**Прогресс живёт в Issue, а не в памяти диалога**: выполненный пункт отмечается чек-боксом сразу, следующая сессия начинает с чтения актуального состояния. Файлов-скратчпадов типа `Tasks.md` не заводим — они не версионируются осмысленно, теряются и не связаны с PR.

**Зачем такое деление** (проверено практикой на плагине 1.0): длинная сессия «обсудили и сразу пишем» теряет контекст к середине кода и жжёт токены на переваривание собственной истории; разделение даёт каждой кодовой сессии короткий точный контекст, а знанию — место, где его найдёт и человек, и следующая сессия.

### 5.6. Формат работы над документами ✅

> Принято 14.08.2026.

Цикл: **обсуждение → краткое резюме в чате → вычитка человеком → развёрнутая запись в документ со статусом и датой.** Тот же цикл у фиче-спек (§4.2: черновик Клода → вычитка → «принята»). Клод не записывает в документы ничего со статусом «принято» без явного подтверждения.

### 5.7. Разделение агентов по ролям ✅

> Принято 21.08.2026. Поверх §5.1–5.6; ограничения §5.2 действуют для каждой роли без изъятий.

#### 5.7.1. Зачем это нужно

Один агент, ведущий фичу от обсуждения до мержа, к середине работы становится **единственным носителем трактовки задачи**. Он же понял спеку, он же написал код по своему пониманию, он же написал тесты, проверяющие ровно это понимание. Зелёный CI в такой схеме не означает «работает как задумано» — он означает «код согласуется сам с собой». Ошибка понимания, допущенная на первом шаге, не ловится ни на одном последующем и доезжает до человека замаскированной под готовую работу.

Разделение по ролям решает ровно одну задачу: **сделать так, чтобы задачу читали независимо минимум дважды**. Кодер и тестировщик получают один и тот же текст спеки, но не видят работу друг друга. Совпали — спека однозначна, и это подтверждено, а не предположено. Разошлись — двусмысленность найдена **до** прода, за один прогон CI, а не через месяц в поддержке.

Отсюда — три цели, ради которых схема существует:

1. **Независимая проверка понимания.** Тесты пишутся по спеке, а не по коду.
2. **Короткий точный контекст у каждой роли.** Развитие §5.5: у роли есть свой вход, свой выход и своя зона записи; лишнего она не читает и не правит.
3. **Раннее обнаружение дыр в спеке.** Красный тест от независимого тестировщика — это в равной мере сигнал «баг в коде» и «спека неполна». Обе ветки ценны, обе идут к человеку.

Чего схема **не** даёт и что не является её целью: ускорения (на малой команде она скорее замедляет отдельную фичу), экономии токенов (их расход растёт), замены человеческого ревью (§5.4 действует целиком).

#### 5.7.2. Роли и их границы

| Роль | Когда | Вход — и только он | Выход (артефакт приёмки) | Зона записи |
|---|---|---|---|---|
| **Спекер** | сессия планирования (§5.5) | обсуждение с человеком, документы 01–03 | черновик спеки (§4.2) + Issue с чек-листом (§4.4) | `docs/specs/` |
| **Кодер** | по пункту чек-листа | CLAUDE.md → принятая спека → Issue | код + юнит-тесты внутренностей, зелёный CI, заполненное описание PR | код фичи, `docs/specs/` — только при расхождении (§4.3 п.4) |
| **Тестировщик** | параллельно кодеру | принятая спека (разделы 3, 5, 8) + сгенерированный `api-client`/OpenAPI + CLAUDE.md | тесты поведения, падающие на пустой реализации | только `tests/` |
| **Ревьюер** | перед тем, как PR откроет человек | дифф + спека + §5.4 | список findings или явное «чисто» | ничего — только текст |
| **Сверщик** | после мержа, пачкой — раз в фазу или раз в неделю | смерженные диффы + 02-tech/03-design | отчёт о расхождениях; правки вложенных `CLAUDE.md` (§2.1a); черновики правок 02-tech | вложенные `CLAUDE.md` |

Пояснения к таблице:

- **Роли архитектора нет и не будет.** Проектные решения принимает человек и записывает в спеку (§4.2, блокирующие разделы 4–5); агент может предложить варианты в обсуждении — это и есть работа спекера. Агент, которому поручено «спроектировать», производит убедительно выглядящие решения, цена ошибки в которых всплывает через месяцы и ревьюить которые в момент принятия некому.
- **Тестировщик не видит реализацию.** Это единственный источник его ценности; в момент, когда он получает дифф кода, схема вырождается в одного агента с дополнительными расходами.
- **Юнит-тесты на внутреннюю механику** (расчёт пропорции возврата, парсинг, конечный автомат) пишет кодер в том же диффе — без кода их не написать, и это нормально. Тестировщик отвечает за уровень «поведение по спеке»: сервис, API, экран.
- **Сверщик — не автор документации.** Устройство проекта описано в 02-tech и 03-design; параллельный второй слой описания архитектуры не заводится ни в каком виде — он гарантированно разойдётся с первым (§5.3: указатель, а не копия). Работа сверщика — находить расхождение кода со спекой и документом; чинится оно сверху вниз (§4.1).
- **Роли — это сессии, а не одновременно живущие процессы.** «Оркестр» не означает, что четыре агента работают в один момент времени; см. §5.7.5.

#### 5.7.3. Жёсткие правила для агентов

Сверх §5.2, которая действует для всех ролей.

1. **Зелёный любой ценой запрещён.** Не используются `skip`, `xfail`, ослабление ассерта, подмена сервиса моком ради прохождения теста, правка ожидаемого значения под фактическое. Не сходится — остановиться и поднять вопрос (§5.2 п.7).
2. **Чужая зона записи неприкосновенна.** Кодер не правит тесты тестировщика ни при каких обстоятельствах. Тестировщик не правит код. Ревьюер не правит ничего.
3. **Крайние случаи не додумываются.** Спека молчит о поведении в пограничном случае — это вопрос человеку, а не «разумное решение» в коде. Придуманное поведение опаснее отсутствующего: оно выглядит осмысленно и потому проходит ревью.
4. **Контекст восстанавливается только из трёх мест** (§5.5): CLAUDE.md → спека → Issue. Ссылка на «мы это обсуждали» — признак дыры в спеке, а не разрешение действовать по памяти диалога.
5. **Терминология — только из глоссариев** (01-product §11, 04-conventions §9). Синоним, изобретённый агентом в имени сервиса, поле схемы или ключе i18n, остаётся в проекте годами.
6. **Итог сессии — не только дифф.** Текстом: что сделано, что осталось неясным, где спека оказалась неполной. Молчаливое «готово» скрывает ровно ту информацию, ради которой роли и разделены.
7. **Роль не расширяется по ходу.** «Раз уж я здесь, заодно поправлю» — прямое нарушение §5.2 п.8–9, а в схеме с ролями ещё и разрушение независимости проверки.

#### 5.7.4. Жёсткие правила для разработчиков

Половина правил, которая нарушается чаще, — эта.

1. **Нет принятой спеки — кодер не запускается.** Ни «по-быстрому», ни «спеку допишу после». Исключение — мелкие fix/chore (§4.4).
2. **Спека не дополняется устно в промпте.** Не хватает информации — правится спека, потом запускается агент. Нарушается это правило всегда под давлением срока и всегда с одним исходом: знание остаётся в чате, который потом закрыли.
3. **Промпт запуска короткий и воспроизводимый:** ссылка на Issue и номер пункта. Промпт длиннее абзаца — признак, что спека дописывается в промпт (см. п. 2).
4. **Красный тест не «чинится» указанием агенту сделать зелёным.** Сначала человек решает, где ошибка — в коде или в спеке; вторая ветка чинится правкой спеки (§4.1).
5. **Владелец PR — человек.** «Это написал агент» не аргумент на ревью и не смягчающее обстоятельство. Не готов защищать каждую строку — PR не открывается.
6. **Дифф читается глазами целиком.** Зелёный CI необходим, но не достаточен (§5.4); построчно и отдельно — миграции, деньги, права, дифф контракта.
7. **Правило трёх кругов.** Агент не справился за три итерации — стоп. Задача возвращается в спеку или режется на части. Четвёртый промпт не помогает никогда: с этого момента идёт не проектирование, а угадывание формулировки.
8. **Одна сессия — один пункт чек-листа** (§5.5). «Он уже в контексте, пусть заодно сделает» даёт дифф, который нельзя отревьюить.
9. **Чекбокс в Issue закрывает тот, кто проверил, а не тот, кто сделал.**
10. **Решения не остаются в приватной памяти агента** (§5.3): долгоживущий факт едет в документ или спеку — туда, где его найдёт человек.

#### 5.7.5. Параллельная работа и изоляция

- **Одновременно запускаются только роли с непересекающимися зонами записи.** Штатные пары: кодер и тестировщик; бэк и фронт после заморозки контракта (§4.3 п.2). Всё остальное — последовательно.
- **Обмен между ролями — только через файлы репозитория и Issue**, напрямую агенты не общаются. Следствие: любая передача читаема человеком и лежит в git.
- **Изоляция тестировщика обеспечивается конфигурацией инструментов**, а не формулировкой промпта: запрет записи вне `tests/` и отсутствие в контексте диффа реализации. Просьба «не подглядывай» не удерживается — под давлением красного теста агент подглядывает.
- Отдельные git-worktree под параллельные роли — допустимое, но не обязательное усложнение; на команде из двух разработчиков обычно не окупается.

#### 5.7.6. Чего избегаем

- **Взаимного подтверждения вместо проверки.** Агент, проверяющий работу агента по её же результату, производит уверенность, а не знание. Любая роль-проверяющий получает на вход исходное требование, а не то, что сделал предшественник.
- **Тестов, написанных по коду.** Такой тест фиксирует поведение вместе с багом и создаёт ложное покрытие — хуже, чем отсутствие теста, потому что снимает вопрос «а это точно проверено?».
- **Второго слоя документации, порождаемого агентом.** Описание устройства проекта живёт в 02-tech и 03-design; всё, что дублирует их, расходится с ними.
- **Бесконечного цикла промптов** вместо правки спеки (правило трёх кругов).
- **Агента как оправдания.** Ответственность за код персональна и не делится с инструментом.

#### 5.7.7. Как проверяем, что схема окупается

Схема принята как рабочая гипотеза и проверяется на первых фичах фазы 0–1 по одной метрике: **доля красных тестов от независимого тестировщика, которые оказались дырами в спеке, а не багами кода**.

- Доля заметна — схема работает: она улучшает спеки, а не только ловит баги, и остаётся.
- Почти все красные тесты — баги кода или шум самого тестировщика: независимая роль избыточна, её бюджет уходит ревьюеру, а тесты возвращаются кодеру.

Пересмотр — по итогам фазы 1, с записью решения сюда же.

### 6.7. Принципы проектирования: SOLID, DTO, enum ✅

> Принято 17.08.2026.

- **SOLID — следствие слоёв (§2.1) и границ модулей (02-tech §4.7), а не отдельная дисциплина**: один сервис/класс — одна ответственность (SRP); новый вариант поведения — новый класс или стратегия, а не ветвление в существующем методе (OCP); зависимость — только вниз по слоям и только от абстракции (интерфейс repository, а не ORM-модель напрямую) — DIP. Признак нарушения: сервис, который правится при любой соседней фиче, или метод длиннее экрана.
- **DTO обязателен на границах**: между слоями и наружу в API — только Pydantic-схемы (backend) и сгенерированные типы `api-client` (frontend, §1.4); ORM-модель или внутренний доменный объект за пределы своего слоя не передаются никогда. Схема на вход и схема на выход — разные типы, даже если сейчас совпадают: расхождение начнётся при первой же фиче, и откат к раздельным типам задним числом ломает контракт.
- **Enum вместо строк-магии**: статусы, типы, роли — `enum.StrEnum` в Python и `enum`/union литералов в TypeScript, значения синхронизированы со значениями `CHECK` в БД (02-tech §5) и с терминологией глоссария (01-product §11). Сравнение с голой строкой (`if status == "active"`) — повод завести enum, а не патчить точку сравнения.
- Проверяется на ревью Клода (/code-review) и человеком по чек-листу §5.4 наравне с правами и миграциями, а не «когда вспомнили».

### 6.8. Каталог паттернов ✅

> Принято 21.08.2026.

**Зачем список, а не правило «применяй, где нужно».** Формулировка «паттерн там, где это обусловлено необходимостью» ничего не запрещает и не разрешает: необходимость оценивает автор кода, и оценивает её положительно. Поэтому здесь закрытый список зафиксированных паттернов — и правило пополнения для всего, что вне списка.

**Три условия, без которых паттерн в каталог не попадает:**

1. **Живой потребитель сегодня**, а не «пригодится» (02-tech §1.2.2). Второе место применения — не гипотеза, а ссылка на раздел документа.
2. **Автоматическая проверка.** Правило, которое стережёт только внимательность ревьюера, при команде 1–2 человека не доживает до второй фазы. Линтер, тест, снапшот в CI — или паттерн остаётся рекомендацией без статуса.
3. **Ровно одно место в документах.** Механика живёт в 02-tech по месту (реестры — §4.2, outbox — §10, снимки — §6.1), каталог только называет и ссылается. Вторая формулировка того же решения разойдётся с первой при первой правке — а расхождение документов у нас баг (§4.1).

#### Отложенные — с триггером, а не «на будущее»

Записаны, чтобы не обсуждать заново и не завести раньше времени: **клиентский ключ идемпотентности** в заголовке POST — с первой операцией без естественного ключа (ручные записи в счёт, возвраты; фаза 2–3); **типизированные идентификаторы** — пока тот же класс ошибок дешевле закрывается keyword-only параметрами; **декларация режима проведения вместо ветвлений** — при третьем режиме, живых сейчас два; **серверный реестр резолверов слабых ссылок** — при первой серверной выгрузке или письме, где подпись объекта рендерит сервер (на экранах хватает словаря модуля-владельца); **веерная постановка задач вместо монолитного прогона** — при росте за эталонную ёмкость §21.

#### Отвергнутые

Не заводятся; предложение вернуться — только с новым фактом, а не с новой формулировкой: отдельный класс Unit of Work (транзакция и так одна на запрос); универсальный `BaseRepository[T]` с `get_by_id(id)` без актора — ровно та дыра, ради которой вводился предикат области; порт-абстракция над ORM «на случай смены БД» — второго потребителя нет (§1.2.2); собственный слой поверх procrastinate — очередь уже даёт расписание, ретраи и таймауты декларацией; коллектор доменных событий с хуком на коммит — неявное поведение вместо явного `publish`; автоподписка декоратором через побочный эффект импорта — противоречит сборке реестров из списка включённых модулей; обязательный маппинг в собственный DTO на каждом пересечении границы модуля — цена выше пользы, граница держится линтером (02-tech §4.7).

#### Правило пополнения

Паттерна нет в каталоге — он **не появляется в диффе**, а предлагается в обсуждение, наравне с новыми зависимостями и изменениями схемы БД (§5.2 п.2). Принятый паттерн попадает сюда строкой с обязательной колонкой проверки; если проверку придумать не удалось — это сигнал, что паттерн не готов, а не повод записать его без неё.

**Статус мокапов (`Mockups/`).** Мокапы — источник **структуры и поведения** экрана: какие элементы на нём стоят, как ходят сценарии, какие состояния существуют (демо-переключатели — спецификация состояний). ## 8. Траблшутинг

### 8.1. Dev-окружение ✅

> Принято 14.08.2026.

| Симптом | Причина и действие |
|---|---|
| compose не поднимается | порт занят / волюм сломан → `docker compose ps`, логи упавшего контейнера |
| api не стартует с ошибкой про модули | **осознанный fail-fast** (02-tech §4.4): комплектация невалидна — текст ошибки называет неудовлетворённую зависимость |
| `/ready` красный | схема БД отстала от кода → `alembic upgrade head` |
| письмо «не пришло» | оно в Mailpit (localhost:8025) — наружу из dev не уходит никогда |
| файлы не грузятся | контейнер MinIO не поднят / бакеты не созданы |
| 401 в SPA | протух refresh-токен → перелогин |
| «нет пункта меню» | это права или выключенный модуль (`/config`), а не баг вёрстки (02-tech §4.6) |

### 8.2. CI ✅

> Принято 14.08.2026.

| Симптом | Причина и действие |
|---|---|
| import-linter / eslint-boundaries красный | нарушена граница модулей — чинится изменением импорта, не конфига (§5.2.3) |
| контракт-дифф красный | пересобери `api-client`, осмотри дифф; намеренное изменение контракта обязано быть в спеке (§4.3) |
| бюджет чанка превышен | тяжёлая библиотека попала в общий чанк — нужен ленивый импорт (02-tech §11.3) |
| `ruff format --check` / `prettier --check` | запусти форматирование локально; это не предмет спора (§1.7) |
| mypy / tsc | читать первую ошибку, не последнюю — остальные часто каскад |
| тест упал, при перезапуске прошёл | flaky не перезапускается молча: issue обязателен |

### 8.3. Диагностика по trace_id ✅

> Принято 14.08.2026.

Любой ответ-ошибка API несёт `trace_id` (02-tech §9.2). По нему грепается весь путь запроса через логи api и worker, включая события и jobs (02-tech §18). В dev — `docker compose logs`; в проде логи смотрит лид в Grafana/Loki.

### 8.4. Ловушки проекта ✅

> Принято 14.08.2026. Правило пополнения: наступил дважды — запиши.

- «Задача» — два смысла: `tasks` (банк задач) и `jobs` (фоновые) — не путать (02-tech §6.9).
- Деньги — `int`, целые рубли: никаких Decimal и копеек (02-tech §5.1).
- Время — всё в UTC, показ в поясе пользователя; наивные datetime запрещены (02-tech §5.1).
- `opened_at` урока не откатывается: перенос вперёд не закрывает урок открывшим (02-tech §6.2).
- Выключенный модуль отвечает 404 — это спецификация, а не баг (02-tech §4.5).
- Повторное зачисление в ту же группу — реактивация той же записи, не новая строка (02-tech §6.5).
- Windows: перевод строк — LF через `.gitattributes` + `.editorconfig`, иначе диффы из CRLF.

### 9.1. Процесс и документы

| Semver | нумерация версий MAJOR.MINOR.PATCH; у нас одна версия на весь продукт (02-tech §17) |
| Lockfile | файл точных версий всех зависимостей (`poetry.lock`, `pnpm-lock.yaml`) — гарантия одинаковой установки у всех |

### 9.2. Backend

| Термин | Что это |
|---|---|
| FastAPI | веб-фреймворк Python: роуты, валидация, OpenAPI из коробки |
| Pydantic | описание и валидация структур данных типами Python — схемы API, payload шагов, конфиги |
| SQLAlchemy / ORM | работа с БД объектами Python вместо сырого SQL; у нас async-вариант 2.0 |
| Alembic / миграция | версионирование схемы БД: каждое изменение — ревизия в цепочке (02-tech §19) |
| Транзакция | группа операций БД «всё или ничего»; у нас одна на HTTP-запрос (02-tech §9.1) |
| DI / `Depends` | внедрение зависимостей FastAPI: сессия, актор, сервисы приходят аргументами функции |
| Outbox | событие пишется в таблицу той же транзакцией, что и данные, — «сделано, но событие потерялось» невозможно (02-tech §10) |
| Шина событий | «модуль публикует событие → подписчики реагируют»: единственная связь модулей «вверх» |
| procrastinate | библиотека фоновых задач поверх Postgres — наша очередь (02-tech §10) |
| Job | фоновая задача (рассылка, начисления); не путать с задачей банка (`tasks`) |
| LISTEN/NOTIFY | встроенные уведомления Postgres между процессами — realtime без Redis |
| SKIP LOCKED | приём Postgres: воркеры разбирают очередь, не блокируя друг друга |
| JSONB | тип Postgres «JSON с индексами» — полиморфные нагрузки (02-tech §5.1) |
| PK / FK | первичный ключ (id строки) / внешний ключ (ссылка на строку другой таблицы) |
| UUIDv7 | формат id: случайный, но сортируемый по времени; генерирует приложение |
| CHECK-констрейнт | правило на уровне БД («status — только из списка») |
| Частичный индекс | индекс по подмножеству строк (`WHERE read_at IS NULL`) — например, счётчик непрочитанного |
| Append-only | таблица только на добавление, без правок и удалений (лицевой счёт, аудит) |
| Сторно | исправление денежной операции обратной записью, а не правкой (02-tech §6.6) |
| Идемпотентность | повтор операции не меняет результат — обязательна для jobs и вебхуков |
| Capability / комплектация | набор включённых модулей и фич инстанса; заморожена на старте процесса, меняется правкой конфига и перезапуском (02-tech §4.4). В коде — `caps.has(...)`, `isModuleEnabled(...)`, `isFeatureOn(...)` |
| Permission / право | разрешённая операция актора, вычисляется на каждый запрос: `require(perm)` на роуте, `can(perm)` на фронте (02-tech §7.2). Слово `capability` про права **не** употребляется — иначе право однажды закэшируют как настройку инстанса |
| Релей outbox | периодическая job ядра: разносит события подписчикам, ставя задачу на каждую пару «событие × подписчик» (02-tech §10) |
| Вебхук | входящий HTTP-вызов от внешнего сервиса (ЮKassa сообщает об оплате) |
| EAV | антипаттерн «сущность-атрибут-значение» (meta-поля WP) — запрещён (02-tech §5.1) |
| argon2id | алгоритм хэширования паролей; пароль из хэша не восстанавливается |
| AES-GCM | симметричное шифрование — поля документов ЭДО (02-tech §15.2) |
| nh3 / санитизация | вычистка опасного HTML из rich-text на сервере — защита от XSS |
| XSS / CSRF | «внедрение чужого скрипта в страницу» / «поддельный запрос от имени залогиненного» |
| CSP / HSTS | заголовки-защиты: что странице можно загружать / только-HTTPS |
| JWT | подписанный токен с данными пользователя — access-токен (02-tech §8) |
| Access / refresh | короткоживущий токен для запросов / долгоживущий для обновления первого |
| OTP | одноразовый код из письма: подтверждение почты, сброс пароля |
| OAuth | протокол «войти через другой сервис» — привязка соцсетей |
| Rate limit | ограничение частоты запросов — защита форм и входа |
| Presigned URL | временная подписанная ссылка на приватный файл в S3 (02-tech §13) |
| SSE | сервер пушит события в открытое соединение — колокольчик (02-tech §10); WebSocket не нужен: трафик односторонний |
| Поллинг | периодический опрос сервера клиентом — деградация SSE |
