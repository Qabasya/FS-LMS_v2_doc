## 1. Стек и инструменты

_Закрепляем инструменты сборки и проверки; правила их обновления._

### 1.1. Менеджер зависимостей Python — poetry ✅

> Принято 14.08.2026. Пересмотр решения 02-tech §1.5 (был uv).

**Решение:** poetry 2.x; `pyproject.toml` по PEP 621; `poetry.lock` — единственный источник версий backend-зависимостей.

**Почему poetry, а не uv:**

1. Проект — приложение в Docker, не публикуемая библиотека: несущих преимуществ uv (скорость на больших графах, workspaces, установка Python) у нас нет — в проде Python приходит из официального Docker-образа, выигрыш в CI — секунды.
2. Дефолты uv — ловушки для джуна и AI-агентов: `uv run` тихо доставляет зависимости, venv без pip «протекает» в глобальное окружение.
3. В марте 2026 Astral (uv) куплена OpenAI; пакетный менеджер — supply-chain-критичная инфраструктура, и доверять её стороннему ИИ-вендору с неясным governance не хотим. **Ruff (тоже Astral) остаётся**: dev-time-инструмент, риск другого порядка, замена (black + flake8) возможна в любой момент.
4. Зрелость и объём обучающих материалов poetry — прямая помощь джуну; PEP 621-совместимость с версии 2.x снимает главную историческую претензию.

**Правила использования:**

- `pip install` запрещён везде — любая зависимость входит через `poetry add` в PR по правилам реестра (02-tech §1.5);
- Python: прод — официальный образ `python:3.12-slim`, локально — официальный установщик или pyenv; poetry версией Python не управляет — и не должен;
- CI: `poetry sync` с кэшем по хэшу `poetry.lock` (в poetry 2.x команды `install --sync` нет — она заменена отдельной `poetry sync`);
- lockfile коммитится всегда; конфликт в нём решается перегенерацией, не ручной правкой.

**Отвергнуто:** uv — вернёмся, если время установки зависимостей станет измеримой болью (правило 02-tech §21: изменения — через измерение, не предположение).

### 1.2. Менеджер зависимостей Node — pnpm ✅

> Принято 14.08.2026. Подтверждение решения 02-tech §1.5.

**Решение:** pnpm; `pnpm-lock.yaml` — единственный источник версий frontend-зависимостей.

**Почему:**

1. **Строгий node_modules**: пакет физически не может импортировать незаявленную зависимость (phantom dependencies). Это установочный уровень той же дисциплины, которую eslint-plugin-boundaries держит на уровне импортов, — прямо работает на границы пакетов `ui` / `api-client` / `modules/*` (02-tech §4.7).
2. Штатные **workspaces** — монорепо стоит на них (02-tech §11.3).
3. Скорость установки и экономия диска (content-addressable store).

**Правила использования:**

- версия pnpm пинится полем `packageManager` в корневом `package.json` (corepack) — у всех, включая CI, одна версия;
- `npm install` и `yarn` запрещены так же, как `pip install`;
- lockfile коммитится всегда; CI ставит с `--frozen-lockfile`.

**Отвергнуто:** npm — нет строгости, workspaces слабее; yarn berry — PnP-режим конфликтует с частью тулинга, лишняя экзотика для джуна.

### 1.3. Стили — SCSS ✅

> Принято 14.08.2026. Пересмотр решения 02-tech §11.3 (было «CSS без SCSS»).

**Решение:** собственные стили пишутся в SCSS-синтаксисе (`.scss`; компилятор `sass-embedded` в dev-зависимостях, Vite поддерживает из коробки). Indented-синтаксис Sass (`.sass`) запрещён — несовместим с копипастой CSS и хуже поддержан тулингом.

**Правила:**

1. **Токены — только CSS custom properties** (`var(--fs-14)`, `var(--sq)`…): их читает рантайм и тема Mantine. `$`-переменные для токенов запрещены — `$` существует только как compile-time сахар (миксины, функции, циклы). Файл токенов — `ui-kit/variables.scss` (блок `:root`).
2. Миксины и функции — только в пакете `ui`, для повторяющихся предметных паттернов (сетки журнала, клетки прогресса); в экранах не объявляются.
3. Вложенность — до трёх уровней; глубже — сигнал разбить компонент.
4. Стили Mantine не переопределяются файлами стилей — только темой (`theme.ts`) и styles API компонентов.

**Контекст:** команда работала на SCSS в плагине 1.0 — привычка сохранена по цене одной dev-зависимости. То, ради чего SCSS брали исторически (переменные, вложенность), теперь есть и в нативном CSS, поэтому повседневные файлы почти не отличаются от обычного CSS.

### 1.4. Генератор TS-клиента из OpenAPI — orval ✅

> Принято 14.08.2026. Закрывает выбор, отложенный в 02-tech §9.2.

**Решение:** orval. Пакет `api-client` монорепо генерируется из OpenAPI-схемы бэкенда: типы, хуки TanStack Query, MSW-моки — всё из одного контракта. Пересборка — в CI (02-tech §9.2); **сгенерированный код руками не редактируется** — любая правка перезатрётся следующей генерацией.

**Почему orval, а не hey-api:**

1. **Готовые хуки** (`useCampusGroupsList()` и т. п.) — меньше ручной обвязки и концепций для джуна; у hey-api вместо хуков options-паттерн: композиционно элегантнее, но это лишний слой для понимания.
2. **Встроенная генерация MSW-моков из OpenAPI** — волны 0–1 фронта (ui-plan §4) собирают экраны на моках до готовности бэкенда: моки приходят бесплатно из того же контракта, фронт не блокируется бэком.
3. Мультифреймворковость hey-api (React/Vue/Svelte/Angular из одного вывода) нам не нужна: фронт один, React.

**Правила:** конфиг orval — в репо; моки MSW используются в разработке экранов и тестах фронта (vitest); contract-тест «клиент компилируется против текущей схемы» — как в 02-tech §9.2.

**Отвергнуто:** hey-api — вернёмся, если понадобится второй фреймворк или orval остановится в развитии.

### 1.5. Версии платформ и их фиксация ✅

> Принято 14.08.2026.

**Решение:** версии закрепляются декларативно — там, где инструменты сами их проверяют; менеджер версий — рекомендация, не требование.

- **Прод**: версии зашиты в Docker-образы (`python:3.12-slim`, `postgres:16`, nginx) — на серверах руками не устанавливается ничего.
- **Пины в репо**: `requires-python = ">=3.12,<3.13"` в pyproject (poetry откажется работать не тем питоном); `engines.node` + `packageManager` в корневом package.json (pnpm с engine-strict откажется не той версией); файлы `.python-version` и `.nvmrc` в корне — их читают pyenv/nvm и CI-экшены, версия задаётся один раз.
- **Node** — текущий LTS (22); **PostgreSQL** — 16, мажор фиксирован до осознанного обновления.
- **Локально**: официальные установщики нужных версий + corepack — достаточный минимум (в т. ч. на Windows); mise или pyenv+nvm — по желанию.
- **Обновление версии платформы** — отдельный PR, меняющий все пины разом (Dockerfile, pyproject, package.json, `.python-version`, `.nvmrc`, CI).

### 1.6. Правила реестра зависимостей ✅

> Принято 14.08.2026. Расширяет 02-tech §1.5.

**Вход — только PR с обоснованием** по чек-листу:

1. зачем нужна и почему не хватает стандартной библиотеки или уже имеющейся зависимости;
2. живость: последний релиз < 12 месяцев, на issues отвечают;
3. лицензия MIT/BSD/Apache; copyleft (GPL и родня) — только через отдельное обсуждение;
4. для фронта — вклад в бюджет начального чанка (02-tech §11.3, §20).

**Правила:**

- один инструмент на задачу, дубли запрещены: даты — dayjs, иконки — @tabler/icons-react, редактор — TipTap;
- очередь заранее согласованных кандидатов: `@dnd-kit` (перетаскивание), `@tabler/icons-react` (иконки), KaTeX (формулы) — вносятся, когда появляется потребитель (ui-plan §5);
- **обновления**: security — немедленно, вне очереди (pip-audit / npm audit красные в CI — 02-tech §15.2); минорные — ежемесячный батч-PR; мажорные — по одному, с чтением changelog и полным прогоном тестов;
- Клод зависимости не добавляет сам — только предлагает в обсуждении (правило §5.2).

### 1.7. IDE и форматирование ✅

> Принято 14.08.2026.

**Конфиги в репо — единственный источник стиля**: ruff (линт + формат, заменяет black/isort), prettier (ts/tsx/scss/md), `.editorconfig` (отступы, финальный перевод строки, кодировка — база для любого редактора).

- **CI проверяет формат** (`ruff format --check`, `prettier --check`): неотформатированный код = красный CI. Следствие: споров о стиле в ревью не существует — формат не обсуждается вообще.
- В репо лежит рекомендованный набор VS Code (`.vscode/extensions.json` + `settings.json` с формат-он-сейв) — разработчик открывает проект и получает готовую среду. JetBrains настраивается по короткой инструкции в README; `.idea` в git не кладётся.
- Правки конфигов линтеров — отдельным PR, не вперемешку с фичей.

## 2. Репозиторий

### 2.1. Раскладка монорепо ✅

> Принято 14.08.2026.

```
fs-lms/
├── backend/
│   ├── app/            # kernel/ · core/ · modules/<id>/ — слои из 02-tech §2.3, §4.1;
│   │                   # Jinja2-шаблоны публичных страниц и писем живут внутри слоёв-владельцев (02-tech §11.1)
│   ├── migrations/     # единая цепочка Alembic
│   ├── tests/
│   └── pyproject.toml
├── frontend/
│   ├── apps/app/       # SPA: /learn + /manage
│   ├── packages/ui/    # библиотека компонентов (03-design §8; сюда переезжает ui-kit)
│   ├── packages/api-client/   # генерируется orval (§1.4)
│   └── packages/modules/<id>/ # зеркалит backend/app/modules/<id>
├── deploy/             # compose-шаблон, конфиг nginx, скрипты провижининга, runbooks/
├── docs/               # 01–04, мокапы, specs/ (фиче-спеки)
└── .github/            # CI
```

**Принципы:**

- **Модуль зеркалится по имени**: `backend/app/modules/campus` ↔ `frontend/packages/modules/campus`; границы держат import-linter и eslint-boundaries с двух сторон (02-tech §4.7).
- **Сгенерированный `api-client` коммитится** — его дифф в PR и есть видимый дифф контракта API; править руками запрещено (§1.4).

### 2.2. Что не лежит в git ✅

> Принято 14.08.2026.

- **Секреты — никогда**: в репо только шаблоны (`.env.example` с комментарием у каждой переменной). Реальные конфиги и секреты инстансов живут в конфиг-репозитории вендора (02-tech §17).
- Также вне git: дампы БД, содержимое MinIO, данные compose-волюмов, `.idea` (а вот `.vscode`-набор коммитится — §1.7).
- **Правило для каждого**: файл с паролем, ключом или токеном в диффе = стоп и вопрос, даже если «это тестовый».

### 2.3. Судьба репозитория документации ✅

> Принято 14.08.2026.

Документация **переезжает в монорепо** (`docs/`) при его постановке (фаза 0): спека и код меняются одним PR — правило «нашёл расхождение — сначала правь документ» (§4.1) работает только когда документ в том же диффе; Клоду — один контекст вместо двух репозиториев; мокапы едут туда же как референс вёрстки. Текущий репозиторий после переезда замораживается с README-ссылкой на новый; до постановки монорепо работа продолжается здесь.

## 3. Git-процесс

### 3.0. Git — только руки человека ✅

> Принято 14.08.2026.

**ИИ-агент с git не работает вообще**: не коммитит, не создаёт и не удаляет ветки, не мержит, не пушит, не откатывает. Вклад Клода — изменения в рабочем дереве и **текстовые подсказки**: черновик сообщения коммита, черновик описания PR. Любую git-операцию выполняет человек. Правило продублировано в §5.2.

### 3.1. Модель веток — trunk-based ✅

> Принято 14.08.2026.

- `main` — единственная долгоживущая ветка: всегда зелёная (CI обязателен), всегда готова к срезу релиза. Develop- и release-веток нет — релиз собирается тегом из main (02-tech §17).
- Работа — в коротких ветках от main: **одна ветка = одна фиче-спека или задача**, живёт дни. Ветка, живущая неделю, — сигнал, что срез слишком крупный.
- Именование: `тип/короткая-суть-латиницей`, тип из списка feat / fix / docs / chore / spec: `feat/campus-schedule-grid`, `fix/journal-focus`, `docs/spec-enrollment`.
- Перед PR ветка ребейзится на свежий main.

### 3.2. Коммиты ✅

> Принято 14.08.2026.

Два уровня подробности: рабочие коммиты в ветке — короткие, итоговый squash-коммит в main — полный (§3.3).

- **В ветке** — краткие отметки прогресса по фиче: `тип(область): что изменилось` — например, `fix(kege): доработка дизайна и логики страницы`. Идеальная атомарность не требуется: в main эти коммиты не попадают.
- **Типы**: feat, fix, docs, refactor, test, chore; **область** — модуль или пакет (campus, ui, api-client…). Префикс английский — по нему работает автогенерация changelog (§3.4); текст русский — его читает только команда.
- Коммитит всегда человек (§3.0); Клод может предложить текст сообщения.

### 3.3. PR и мерджи в main ✅

> Принято 14.08.2026.

- **Squash-merge**: одна ветка = один коммит в main. **Заголовок** — conventional одной строкой; **тело** — развёрнутое описание всего, что сделано с прошлого мерджа: «Исправлена гонка в AssessmentAnswerRepository: …». История main читается как список фич, каждая — с полным рассказом внутри.
- **Описание PR** и есть это развёрнутое описание — при squash оно становится телом коммита. Шаблон в `.github/`: **Что и зачем** (ссылка на фиче-спеку, для feat обязательна) · **Что изменилось** (полный список с прошлого мерджа) · **Как проверено** (тесты; для UI — скриншоты 1440/1024 против мокапа) · **Чек-лист**: спека обновлена вместе с кодом · дифф `api-client` осмотрен · миграции есть/нет и осмотрены · строки через i18n.
- **Ревью**: PR джуна ревьюит лид (Клод делает предварительный текстовый проход до него); PR лида ревьюит Клод (/code-review). **Merge нажимает только человек.** Красный CI не мержится никогда — исключения «потом починим» не существует.

### 3.4. Релизы ✅

> Принято 14.08.2026.

- Единая semver-версия всего продукта (02-tech §17): PATCH — фиксы; MINOR — фичи и модули; MAJOR — редкие вехи (завершение фазы, ломающее для эксплуатации).
- Релиз = тег `vX.Y.Z` на main → CI собирает образы → накатка волнами: staging → свой инстанс (канарейка) → парк (02-tech §17).
- **Changelog двойной**: технический — автогенерация из conventional-заголовков squash-коммитов; клиентский (в админке владельца — 01-product §10.7) пишет человек человеческим языком, Клод готовит черновик.
- Security-релизы — вне очереди (02-tech §15.2).

## 4. Spec-Driven Development

_Главный процессный раздел — обещан в 02-tech §0.1._

### 4.1. Пирамида спецификаций ✅

> Принято 14.08.2026.

Три уровня:

1. **Документы 01–04** — «конституция»: меняется редко и осознанно.
2. **Фиче-спеки** (`docs/specs/`) — по одной на фичу; остаются навсегда как история решений.
3. **Код и тесты.**

**Правило направления:** код не противоречит фиче-спеке, фиче-спека — верхним документам. Расхождение чинится **сверху вниз**: сначала правится документ (можно тем же PR, что и код — §2.3), потом код. Конфликт между верхними документами: каждый главный в своей зоне — 01 в продуктовых вопросах, 02 в технических, 03 в интерфейсных; противоречие между ними — баг документации, чинится немедленно.

### 4.2. Шаблон фиче-спеки ✅

> Принято 14.08.2026.

Файл `docs/specs/NNN-имя.md`; разделы фиксированные:

1. **Шапка**: статус (черновик → принята → реализована; отменена), фаза, ссылки на разделы 01–03.
2. **Границы**: что входит и что **не** входит (анти-scope обязателен).
3. **Поведение**: сценарии, правила, крайние случаи.
4. **Модель данных**: таблицы, колонки, индексы; план миграции.
5. **API-контракт**: эндпоинты, схемы запросов и ответов, права (`require(...)`), коды ошибок — от этого раздела стартует параллельная работа (§4.3).
6. **Экраны**: ссылки на 03-design §4.x и мокапы + отличия и состояния, если фича их добавляет.
7. **События и уведомления**: что публикует, кто подписан.
8. **Тесты**: перечень проверок по цене ошибки (02-tech §20).
9. **Открытые вопросы.**

**Ограничение размера:** спека читается за 10–15 минут; не влезает — фича режется на две. **Кто пишет:** Клод — черновик по итогам обсуждения; человек вычитывает и переводит в «принята» (§5.5).

### 4.3. Жизненный цикл фичи ✅

> Принято 14.08.2026.

1. **Спека**: черновик → вычитка → «принята».
2. **Контракт**: роуты-заглушки с настоящими Pydantic-схемами → OpenAPI → генерация `api-client` + MSW-моков. С этой точки фронт и бэк не ждут друг друга.
3. **Параллельная разработка**: бэк — сервисы и тесты; фронт — экраны против моков. Контракт меняется только через спеку и PR с видимым диффом — устных договорённостей «я поле переименовал» не существует.
4. **Ревью и squash-merge** (§3.3); спека → «реализована». Расхождения, найденные по ходу, правятся в спеке тем же PR.

**DoD фичи** (02-tech §20): спека есть и актуальна → тесты по спеке зелёные → CI зелёный → дифф контракта и миграции осмотрены → для UI дополнительно DoD экрана (ui-plan §1).

### 4.4. Этапы и трекинг задач ✅

> Принято 14.08.2026.

- Иерархия: **фаза** (02-tech §23) → **фиче-спека** → **задачи**.
- Трекинг — GitHub Issues: milestone = фаза, метки = модули, задача ссылается на спеку. Фронтовые волны — по шагам ui-plan §4.
- Задач класса feat вне какой-либо спеки не существует; мелкие fix/chore — можно без спеки, но с полным описанием в PR.
- **Вертикальные срезы**: фича целиком (бэк + фронт + тесты); «сначала весь бэкенд» запрещено (02-tech §23).

### 4.5. Журнал решений ✅

> Принято 14.08.2026.

- Основной формат — **статус-блоки в документах**, как уже принято: «Статус: принято (дата)» + обоснование + отвергнутые альтернативы.
- Решения масштаба фичи — в разделах «Открытые вопросы»/«Решения» её спеки.
- Межфичевые решения, которым нет места в 01–04, — `docs/decisions/` с короткими ADR-заметками (контекст → решение → последствия). Это запасной формат: сначала решение пытаемся положить в профильный документ.

## 5. Работа с Claude

### 5.1. Роли ✅

> Принято 14.08.2026.

**Клод делает:** черновики фиче-спек по итогам обсуждения; код по принятой спеке (бэк и фронт); тесты по спеке; предварительное ревью PR джуна и ревью PR лида — текстом; черновики текстов (сообщения коммитов, описания PR, клиентский changelog); сверки документации на согласованность; **наставничество джуна** — «объясни, почему здесь так устроено» — легитимный и поощряемый запрос, ответ со ссылками на документы.

**Только человек:** все решения (продуктовые, архитектурные, зависимости, приоритеты); git целиком (§3.0) и merge; всё, что касается прода, — провижининг, миграции на живых инстансах, доступ к данным клиентов; общение с клиентами.

### 5.2. Ограничения Клода ✅

> Принято 14.08.2026.

1. **«Нет спеки — нет кода»**: feat-код пишется только по принятой спеке; исключение — мелкие fix/chore с полным описанием в PR (§4.4).
2. Новые зависимости, архитектурные решения, изменения схемы БД и контракта API — только **предложением в обсуждение**, никогда фактом в диффе.
3. Границы модулей не обходятся: красный import-linter / eslint-boundaries чинится изменением кода, а не ослаблением конфига.
4. **Git не трогает вообще** (§3.0) — только текстовые подсказки.
5. Секреты и данные клиентов не запрашивает, не логирует, не вставляет в код и тесты (фикстуры — только фабрики, 02-tech §20).
6. Статус «принято» в документах — только после явного «ок» человека; Клод не самоутверждает решения.
7. Обнаружил противоречие спеки и реальности — **останавливается и поднимает вопрос**, а не выбирает трактовку сам.
8. **Не лезет в файлы вне задачи**: правит только файлы, прямо названные задачей или очевидно входящие в её границы по фиче-спеке. Читать шире можно (поиск причины бага — легитимен), править — нет.
9. **Никаких попутных правок**: заметил рядом опечатку, устаревший код, «не тот» стиль — не чинит молча в том же диффе, а сообщает текстом или предлагает отдельной задачей. Один PR = одна фича или один фикс; посторонние файлы в диффе — красный флаг на ревью.

### 5.3. Контекст: CLAUDE.md ✅

> Принято 14.08.2026. Файл создан — [CLAUDE.md](CLAUDE.md); при переезде в монорепо (§2.3) едет в его корень и дополняется командами запуска.

- Содержимое: краткая карта репозитория (что где лежит); таблица «тип задачи → обязательные документы» (= §7); ограничения §5.2 сжатым списком; команды запуска dev-окружения, тестов и линтеров (появятся с монорепо).
- **Принцип: CLAUDE.md — указатель, а не копия документации.** Правила живут в 01–04 и спеках, CLAUDE.md на них ссылается; продублированный текст неизбежно расходится с источником.
- Долгоживущие факты о проекте — в документы и спеки, а не в приватную память агента: знание лежит в файлах, которые читает и человек (bus-factor).

### 5.4. Что человек проверяет за Клодом всегда ✅

> Принято 14.08.2026. Зоны по цене ошибки — 02-tech §20.

- каждая миграция — глазами, построчно;
- всё про деньги: ledger, payments, вебхуки, идемпотентность;
- права и области видимости: `require(...)` на каждом роуте, предикаты scope;
- дифф контракта API (`api-client` в PR);
- изменения аудита и журналирования;
- шаблоны писем, уходящих наружу.

Правило: **«Клод написал, и тесты зелёные» ≠ готово** — тесты Клода проверяют его же понимание задачи; человек сверяет поведение со спекой, а не только читает код.

### 5.5. Формат работы над документами ✅

> Принято 14.08.2026.

Цикл: **обсуждение → краткое резюме в чате → вычитка человеком → развёрнутая запись в документ со статусом и датой.** Тот же цикл у фиче-спек (§4.2: черновик Клода → вычитка → «принята»). Клод не записывает в документы ничего со статусом «принято» без явного подтверждения.

## 6. Стиль кода

### 6.1. Python ✅

> Принято 14.08.2026.

- **Типизация обязательна везде**: сигнатуры сервисов, repository и роутеров — полностью; mypy в CI красный при пропусках.
- **Именование**: сущности в коде = имена из схем 02-tech §5 (`enrollment`, `snapshot`, `ledger_entry`) — синонимы не изобретаются, перевод домена уже сделан в модели данных. Сервисные методы — глаголы (`enroll_student`, `approve_schedule`); repository — `get_ / list_ / save_`.
- **Докстринги** — не везде, а у модулей и методов с неочевидными инвариантами: коротко «зачем и какие правила», не простыня.
- **Ошибки** — только доменные исключения (02-tech §9.1); голых `raise Exception` и HTTP-кодов в сервисах не существует.
- **Без магии**: явные импорты, никакой динамики атрибутов — код одинаково читают джун и агент.

### 6.2. TypeScript / React ✅

> Принято 14.08.2026.

- **TS strict**; `any` запрещён (обоснованный `unknown` + сужение — можно).
- **Компонент**: функциональный; интерфейс props над ним; один компонент — один файл; `PascalCase.tsx` для компонентов, `camelCase.ts` для остального.
- **Логика — в хуках `use*`**, компонент рендерит. Серверное состояние — только TanStack Query; ручные `useState` + `fetch` запрещены.
- **Импорты между пакетами** — только через публичный вход (`index.ts`); глубокие пути ловит eslint-boundaries (02-tech §4.7).
- **Стили** — `*.module.scss` рядом с компонентом; значения только из токенов (§1.3).

### 6.3. Комментарии ✅

> Принято 14.08.2026.

- **Язык — русский** (код читает только команда; идентификаторы английские, пояснения русские).
- **Стиль — «зачем, а не что»**: комментарий объясняет инвариант или причину («сторно, а не правка — журнал денег append-only, 02-tech §6.6»); ссылки на разделы документов в неочевидных местах приветствуются.
- **Запрещено**: пересказ строки, история правок («было X, стало Y»), закомментированный код, TODO без issue.

### 6.4. Тесты ✅

> Принято 14.08.2026. Приоритеты покрытия — 02-tech §20.

- **Структура** — arrange-act-assert, блоки разделены пустыми строками. Один тест — одно поведение.

## 9. Технический глоссарий ✅

> Добавлен 14.08.2026, пополняется. Доменные термины (группа, запись, снимок, лицевой счёт…) — в глоссарии 01-product §11; здесь — технические. Правило: встретил в документах термин без определения — добавь сюда.

### 9.1. Процесс и документы

| Термин | Что это |
|---|---|
| SDD (Spec-Driven Development) | код пишется только по предваряющей спецификации; уровни: 01–03 → фиче-спеки → код (§4) |
| Фиче-спека | документ на одну фичу по шаблону §4.2: границы, модель, API, экраны, тесты |
| DoD (Definition of Done) | чек-лист «когда работа считается сделанной» (§4.3; для экранов — ui-plan §1) |
| ADR | короткая заметка «решение + контекст + почему» — формат журнала решений (§4.5) |
| Вертикальный срез | фича целиком через все слои (бэк + фронт + тесты), а не «сначала весь бэкенд» |
| Walking skeleton | минимальный сквозной каркас: логин → экран с меню (02-tech §23, фаза 0) |
| Bus-factor | скольких людей должен «сбить автобус», чтобы проект встал; у нас 1 — лечится документами |
| Runbook | пошаговая инструкция эксплуатационной операции (02-tech §17) |
| CI / CD | автопроверка каждого PR (линт, тесты, сборка) / автоматическая доставка релиза |
| PR (pull request) | предложение влить ветку: ревью + зелёный CI перед merge (§3.3) |
| Trunk-based | модель веток: короткие ветки от main и быстрый merge, без долгих release-веток (§3.1) |
| Semver | нумерация версий MAJOR.MINOR.PATCH; у нас одна версия на весь продукт (02-tech §17) |
| Lockfile | файл точных версий всех зависимостей (`poetry.lock`, `pnpm-lock.yaml`) — гарантия одинаковой установки у всех |
| Монорепо / workspace | один репозиторий на бэк и фронт / именованный пакет внутри него (`ui`, `api-client`) |

### 9.2. Backend

| Термин | Что это |
|---|---|
| FastAPI | веб-фреймворк Python: роуты, валидация, OpenAPI из коробки |
| Pydantic | описание и валидация структур данных типами Python — схемы API, payload шагов, конфиги |
| SQLAlchemy / ORM | работа с БД объектами Python вместо сырого SQL; у нас async-вариант 2.0 |
| Alembic / миграция | версионирование схемы БД: каждое изменение — ревизия в цепочке (02-tech §19) |
| Транзакция | группа операций БД «всё или ничего»; у нас одна на HTTP-запрос (02-tech §9.1) |
| DI / `Depends` | внедрение зависимостей FastAPI: сессия, актор, сервисы приходят аргументами функции |
| Outbox | событие пишется в таблицу той же транзакцией, что и данные, — «сделано, но событие потерялось» невозможно (02-tech §10) |
| Шина событий | «модуль публикует событие → подписчики реагируют»: единственная связь модулей «вверх» |
| procrastinate | библиотека фоновых задач поверх Postgres — наша очередь (02-tech §10) |
| Job | фоновая задача (рассылка, начисления); не путать с задачей банка (`tasks`) |
| LISTEN/NOTIFY | встроенные уведомления Postgres между процессами — realtime без Redis |
| SKIP LOCKED | приём Postgres: воркеры разбирают очередь, не блокируя друг друга |
| JSONB | тип Postgres «JSON с индексами» — полиморфные нагрузки (02-tech §5.1) |
| PK / FK | первичный ключ (id строки) / внешний ключ (ссылка на строку другой таблицы) |
| UUIDv7 | формат id: случайный, но сортируемый по времени; генерирует приложение |
| CHECK-констрейнт | правило на уровне БД («status — только из списка») |
| Частичный индекс | индекс по подмножеству строк (`WHERE read_at IS NULL`) — например, счётчик непрочитанного |
| Append-only | таблица только на добавление, без правок и удалений (лицевой счёт, аудит) |
| Сторно | исправление денежной операции обратной записью, а не правкой (02-tech §6.6) |
| Идемпотентность | повтор операции не меняет результат — обязательна для jobs и вебхуков |
| Вебхук | входящий HTTP-вызов от внешнего сервиса (ЮKassa сообщает об оплате) |
| EAV | антипаттерн «сущность-атрибут-значение» (meta-поля WP) — запрещён (02-tech §5.1) |
| argon2id | алгоритм хэширования паролей; пароль из хэша не восстанавливается |
| AES-GCM | симметричное шифрование — поля документов ЭДО (02-tech §15.2) |
| nh3 / санитизация | вычистка опасного HTML из rich-text на сервере — защита от XSS |
| XSS / CSRF | «внедрение чужого скрипта в страницу» / «поддельный запрос от имени залогиненного» |
| CSP / HSTS | заголовки-защиты: что странице можно загружать / только-HTTPS |
| JWT | подписанный токен с данными пользователя — access-токен (02-tech §8) |
| Access / refresh | короткоживущий токен для запросов / долгоживущий для обновления первого |
| OTP | одноразовый код из письма: подтверждение почты, сброс пароля |
| OAuth | протокол «войти через другой сервис» — привязка соцсетей |
| Rate limit | ограничение частоты запросов — защита форм и входа |
| Presigned URL | временная подписанная ссылка на приватный файл в S3 (02-tech §13) |
| SSE | сервер пушит события в открытое соединение — колокольчик (02-tech §10); WebSocket не нужен: трафик односторонний |
| Поллинг | периодический опрос сервера клиентом — деградация SSE |

### 9.3. Frontend

| Термин | Что это |
|---|---|
| SPA | приложение одной страницы: браузер грузит его один раз, дальше только данные по API |

| Jinja2 | шаблонизатор Python — публичные страницы и письма |
| Mantine | библиотека React-компонентов, основа UI (03-design §8) |
| Тема (theme) | конфигурация Mantine — цвета, размеры, дефолты компонентов (`ui-kit/theme.ts`) |
| Дизайн-токены | именованные значения размеров и цветов (`--fs-14`) — единственный источник чисел (03-design §1.13) |
| CSS custom properties | переменные CSS (`var(--…)`) — форма жизни токенов в рантайме |
| TanStack Query | серверное состояние: кэш запросов, инвалидация, повторы — вместо ручных fetch + useState |
| React Router | маршрутизация SPA: адрес → экран |
| Ленивый чанк | кусок JS, загружаемый при первом заходе на экран, — изоляция модулей (02-tech §4.6) |
| Tree-shaking | выбрасывание неиспользуемого кода при сборке |
| HMR | горячая замена кода в dev без перезагрузки страницы (Vite) |
| TipTap | rich-text-редактор — все форматируемые поля (03-design §1.4) |
| i18n / i18next | слой переводов: все строки интерфейса — по ключам словаря |
| OpenAPI | машиночитаемое описание API (пути, параметры, схемы); FastAPI генерирует его сам |
| orval | генератор TS-клиента из OpenAPI: типы, хуки TanStack Query, MSW-моки (§1.4) |
| MSW | Mock Service Worker: перехватывает запросы в браузере и тестах и отвечает моками — фронт живёт без бэкенда |
| Contract-тест | проверка «сгенерированный клиент соответствует текущей схеме API» (02-tech §9.2) |
| Error boundary | React-компонент, ловящий ошибки поддерева, — падает зона, а не всё приложение |

| Debounce | задержка «подожди, пока перестанут печатать» — поиск, автосохранение |
| Skeleton | серые заглушки на месте грузящегося контента (03-design §1.10) |
